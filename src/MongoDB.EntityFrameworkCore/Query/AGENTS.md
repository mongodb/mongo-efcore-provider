# Query — AGENTS.md

## Scope

Translates `IQueryable<T>` against MongoDB-backed DbSets into MongoDB aggregation pipelines. There are **two translation paths**, chosen at compile time by the `MongoQueryMode` option (see *the gate* below):

1. **Native (default).** For the supported slice — single-collection **filter / sort / paging** over whole-entity results — the provider **generates the aggregation `BsonDocument[]` pipeline itself**, from a structured query expression tree, and runs it via `IMongoCollection<…>.Aggregate`. It does **not** go through the driver's LINQ provider for these.
2. **Driver-LINQ (gated fallback).** For everything outside the native slice (a **computed-filter, computed-leaf, or deeper-than-two-level (or owned-mixed) nested** `SelectMany` over a reference navigation — a *projected or bare-whole-inner-entity, FK-correlated* reference `SelectMany`, including one carrying an *inner-element-only filter*, a filter **correlated beyond the FK into the outer entity**, OR an exactly-**two-level** unfiltered nested collection, goes native; see the EF-347 slice 5, bare-reference-entity, filtered-inner, correlated-beyond-FK, and nested-reference notes below — a nested collection selector, or a whole-inner-entity projection — an owned-collection `SelectMany` projecting the element's members goes native, in either user-authored form — see the EF-347 slices 3–4 note below — a non-whole-entity, non-terminal, projected, or mismatched-entity-type `Intersect`/`Except` (a *whole-entity, terminal* `Intersect`/`Except` goes native via a source-tagging pipeline — see the EF-347 set-ops slice A note below; unlike everything else in this list, an out-of-scope `Intersect`/`Except` has no driver-LINQ baseline and hard-fails in every mode instead of landing here) — `VectorSearch`, a non-TPH or otherwise non-representable `OfType` — see the EF-347 note below — a bare-scalar or whole-entity `Distinct` (a *projected* `Distinct` goes native — see the EF-347 Task 2 note below) — a non-whole-entity, non-terminal, or mismatched-entity-type `Union`/`Concat` (a *whole-entity, terminal* `Union`/`Concat` goes native — see the EF-347 slice 2 note below) — the **non-native** `GroupBy` shapes — see the EF-SP6 note below — and the deferred Include shapes below), the provider still hands a driver-LINQ expression to the MongoDB C# driver's LINQ v3 provider, exactly as it always did.

> **As-built scope (EF-323 foundation + EF-329 predicate-breadth + EF-331 projection-pushdown + EF-332 layering + EF-SP4 scalar-cardinality sub-projects).** Native = filter/sort/paging, with **predicate breadth**: nullable equality/`== null` (IS NULL), collection `Contains` → `$in`/`$nin`, `string.StartsWith`/`EndsWith`/`Contains` → `$regularExpression`, and field-to-field/arithmetic comparisons → `$expr`. Native now also covers **terminal anonymous-type / DTO member-access projections** — a final `Select` whose body is a `new {...}`/DTO construction over top-level member accesses only — which emits a native `$project` stage instead of falling back; **bare scalar** projections (`Select(p => p.Name)`), **mixed** entity+scalar shapes, and **non-terminal** `Select`s (followed by more query operators) still fall back to driver-LINQ. **Numeric arithmetic computed leaves** (`Select(p => new { Total = p.Price * p.Qty })`) **now also go native — see the dedicated "Native arithmetic computed projections (EF-347)" note below.** The remaining **computed long tail** — method calls (string transforms `ToUpper`/`Substring`/…, date-part extraction, `Math.*`) and type-changing casts — is explicitly **out of scope for this sub-project**; it is a follow-on, not a gap left by predicate breadth.
>
> **Native arithmetic computed projections (EF-347).** Native now also covers a terminal projection leaf that is **numeric arithmetic** (`+ - * / %`) over member/constant/parameter operands, e.g. `Select(o => new { Total = o.Price * o.Qty })` — the leaf renders as an aggregation operator document (`{ $multiply: [...] }`) via the existing `MongoAggregationExpressionRenderer`, and the DOM shaper reads it back raw by alias; no emit-side or read-back changes were needed. **Entry point:** `MongoExpressionTranslator.TryTranslateValue` delegates to the existing, EF-329-tested `TranslateOperand` operand machinery (member field-ref / constant / parameter / nested arithmetic), called with `allowNumericWidening: true` so mixed-numeric-type arithmetic (`int * double`) unwraps the compiler-inserted implicit-widening `Convert` the same way C# itself would — unlike the two `TranslateComparison` call sites, which keep `allowNumericWidening: false` so the EF-329 comparison path is byte-identical. `TryTranslateValue` deliberately does NOT `Unwrap` its own top-level node before recursing (unlike most of this file's entry points) — `Unwrap` strips ANY `Convert`/`ConvertChecked` unconditionally, which would silently drop a top-level NARROWING cast (`(int)o.Weight`) and return the wider raw value; the raw body is passed through so `TranslateOperand`'s narrowing-aware `Convert` branch can reject it instead. **Gate:** `NativeProjectionBinder.TryTranslateLeaf` accepts a projection leaf only when the top node is itself a `BinaryExpression` with an arithmetic `NodeType` (`Add`/`Subtract`/`Multiply`/`Divide`/`Modulo`) AND `TryTranslateValue` succeeds — narrower than "any numeric value", so a bare constant/parameter leaf (`new { X = 5 }`) stays on the fallback path. **This note USED TO SAY that leaf "would render as a bare value that `$project` misreads as an inclusion flag (`{X: 1}`), not a literal"; that mechanism was MEASURED FALSE and is corrected here.** The measurement is the count branch's (see the count-projection note below): relaxing the count gate to plain `TryTranslateValue` success admits exactly the set that dropping this branch's `BinaryExpression` requirement would, and what it produced was `new { b.Title, X = 5 }` and a captured-parameter leaf returning **correct** values (folded client-side by `Visit`, with a junk `X: 5` in the emitted `$project`), while `X = 0`/`X = false` **aborted the aggregate** with `MongoCommandException: Invalid $project :: caused by :: Cannot do exclusion on field X in inclusion projection`. The binary-top-node gate is still the right narrowing; the hazard it keeps out is a hard abort on a falsy constant, not a silent misread. **Guard A (integer-result division):** `ContainsIntegerDivision` rejects a `Divide` anywhere in the subtree whose result type is an integer type — MongoDB's `$divide` is non-truncating (spike-confirmed divergence from C#'s truncating integer division); integer `Modulo` needed NO guard (MongoDB's `$mod` matches C#'s truncating/dividend-sign semantics exactly, including negative dividends). **Guard B (converter/representation):** `AllFieldsDefaultSerialized` walks the translated tree and rejects any operand field lacking default serialization (`NativeGroupByBinder.HasDefaultKeySerialization` reused as-is) — a computed value over a value-converted or non-default-`BsonRepresentation` stored form would diverge from CLR arithmetic if computed from the raw stored value. **Shaper-side fix (silent-wrong-data, NOT just a rejection gap):** `MongoProjectionBindingExpressionVisitor.Visit` needed a NEW `BinaryExpression` arithmetic case (gated `when _queryExpression.Select.Route == NativeRoute.Projection`) registering the whole binary node as ONE projection-member slot — without it, the visitor's pre-existing walk decomposed `c.Age * c.Score` into two separate `MemberExpression` visits that clobbered the SAME `ProjectionMember` slot, silently producing wrong data (`(Age*Score)²`) under BOTH `Native` and `NativeOnly` (caught by a live spike before shipping, not merely inferred). The `Route == Projection` guard is load-bearing: it confines the new case to the fully-native path and lets a MIXED shape (`Select(c => new { c, Total = c.Age * c.Score })` — an entity leaf alongside a computed one) fall through unaffected to the mixed shaper — that mixed-whole-entity-plus-computed combination is a **separate, pre-existing** carried bug (not introduced or fixed by this slice; still falls back as before). **Disposition — graceful decline to fallback, not a hard failure:** an out-of-scope leaf (string concat, a method call, a rejected guard) simply fails `TryTranslateLeaf` and the whole projection falls back to driver-LINQ exactly as before this slice — correct results under `Native`/`DriverLinq`, `NativeTranslationNotSupportedException` only under `NativeOnly`. **The set-op binder reuse (global, not scoped to plain `Select`):** because `NativeProjectionBinder.TryTranslateLeaf` is the one shared entry point for EVERY `Select.Projection` population site — a plain terminal `Select`, a trailing projection after a whole-entity `Union`/`Concat`/`Intersect`/`Except` (EF-347 slice C2), AND a projected set-op OPERAND (EF-347 slice C1, gated only on `IsPlainProjectedSelect`'s `Route == Projection && Projection.Count > 0`, with no leaf-shape restriction of its own) — an arithmetic computed leaf now also goes native in ALL of these positions, not just a bare terminal `Select`; see `NativeSetOpsTests.Computed_leaf_projection_after_union_goes_native`/`Computed_leaf_projection_after_intersect_goes_native_result_set`/`Computed_leaf_operand_union_goes_native`. **Deferred (out of scope for this slice):** a computed leaf inside a `SelectMany` collection/result selector was originally deferred here entirely, planned as a follow-on slice; a LATER EF-347 slice narrowed that — a **single-scope** arithmetic computed leaf inside a SelectMany's TRAILING projection now ALSO goes native, via a new branch in `NativeSelectManyBinder.TryBindTransparentIdentifierProjection` — see the dedicated "Native SelectMany computed-leaf (EF-347)" note below; a **cross-scope** leaf (operands spanning two different SelectMany scopes) and the inner-`Select` form's own separate `TryBind` binder (which structurally rejects any computed leaf nested inside the collection selector itself) remain deferred, per that note. The long tail of non-arithmetic computed leaves (string methods, date-part extraction, `Math.*`, type-changing casts) — unaffected, still fall back exactly as before.
>
> **Integer division — corrected disposition (this is NOT "graceful fallback with correct values"):** an integer-result `Divide` is guarded OUT of native by Guard A above, so it always falls back to driver-LINQ. But the driver-LINQ path is **not a safe haven either**: MongoDB's `$divide` operator is non-truncating (it always returns a double), and the C# driver's own BSON deserializer rejects a non-exact-integer double when materializing into an `int`/`long` result field — so for a NON-exact quotient (e.g. `7 / 2`), BOTH `Native` and `DriverLinq` throw `MongoDB.Bson.TruncationException` at materialization time, and `NativeOnly` throws `NativeTranslationNotSupportedException` at translation time (before the driver is ever reached). An EXACT quotient (e.g. `10 / 2 == 5.0`, a whole number) round-trips fine in both modes. This corrects an earlier (wrong) design assumption that "Native & DriverLinq return correct truncated ints" for integer division — there is no truncation anywhere in this path; the guard exists precisely because there is no way to reproduce C#'s truncating integer division through `$divide` short of an explicit `$trunc`/`$toInt` wrap, which is out of scope for this slice.
>
> **Scalar cardinality (EF-SP4).** Native now also covers **entity reducers** (`First`/`FirstOrDefault`/`Single`/`SingleOrDefault`) via a synthesized `$limit` (1, or 2 for the `Single` family so the server-side reducer can still distinguish "more than one" from "exactly one") plus EF Core's own base cardinality reduction over the returned `IEnumerable<T>` — this is a DOM shaper, not a streaming one; and **scalar aggregates** (`Count`/`LongCount`/`Any`/`All`/`Sum`/`Min`/`Max`/`Average`) via a synthesized `$count`/`$group` stage plus a DOM scalar shaper and an explicit empty-input contract (`MongoEmptyAggregateBehavior`: default-value for `Count`/`LongCount`/`Any`/`All`/`Sum`, return-null for nullable `Min`/`Max`/`Average`, throw for non-nullable `Min`/`Max`/`Average`, matching the BCL LINQ contract). **What still falls back:** `Contains`/`ElementAt`/`Last` (no native form); computed aggregate selectors (`Sum(x => x.V * 2)` — the selector must be a plain member access); and reducer/aggregate **streaming** (deferred — the `BsonRowReader` null/non-nullable-list gap means these still materialize via the DOM shaper, not the streaming one). (An aggregate that injects a predicate as a `$match` — `All`, or `Count`/`Any` with an unnormalized predicate — occurring AFTER a `Take`/`Skip` already applied to the same select USED TO force a fallback here; EF-347 Task 3 removed that guard once the ordered-op-list IR made tail-append always correct — see the Non-canonical Skip/Take note below.) Two retired cutouts from earlier sub-projects: the `ExecuteScalar` short-circuit is now gated on `NativePipeline == null` (rather than being unconditional), and the `resultCardinality != Enumerable` gate was relaxed to admit the new scalar/reducer cardinalities. (native `GroupBy` landed in EF-SP6; native `OfType` and projected `Distinct` in EF-347 slice 1; native whole-entity terminal `Union`/`Concat` in EF-347 slice 2; native whole-entity terminal `Intersect`/`Except`, via a source-tagging pipeline, in EF-347 set-ops slice A — see the notes below.) **`All` with a comparison predicate is NO LONGER on the falls-back list above — ticket EF-335 is closed.** `All(x => x.V > 0)`, including `&&`/`||` combinations, now goes native via the shared predicate negator — see the dedicated "Owned-collection `All` quantifier predicates + the shared predicate negator (EF-322, closing EF-335)" note below for the mechanism and the root-scope tests.
>
> **OfType discriminator narrowing (EF-347, SP6-remaining slice 1).** Native now also covers `OfType<TDerived>()` over a TPH hierarchy: `TranslateOfType` builds a discriminator conjunct — a single-value `$eq` when `TDerived` is a leaf type, an `$in` over the discriminator subtree (`TDerived` and its own derived types) otherwise — via `TryBuildDiscriminatorPredicate`, and adds it to the tail `$match` through `AddPredicateConjunct` (composing with any other `Where` predicate already on the select), instead of unconditionally calling `MarkNotNativelyRepresentable()`. This works with **no shaper changes**: TPH entities are already streaming-ineligible and materialize through the DOM shaper via EF's own discriminator-based `MaterializationCondition`, which already picks the correct derived CLR type — the only thing native was missing was the `$match`/`$in` conjunct that keeps sibling-type rows out of the result. **Rejected by a guard → fall back (the guard PREVENTS native divergence from driver-LINQ):** `TryBuildDiscriminatorPredicate` returns `false` — so `MarkNotNativelyRepresentable()` is still called and the query falls back (throwing only under `NativeOnly`) — when (a) the target type has no discriminator property (non-TPH `OfType`, e.g. an unrelated-hierarchy narrowing), OR (b) the discriminator property has a **value converter or a non-default `BsonRepresentation`** (`GetValueConverter()`/`GetTypeMapping().Converter`/`GetBsonRepresentation()` — mirroring `NativeGroupByBinder.HasDefaultKeySerialization`). The value-converter/representation case is a correctness guard, not just an optimization gap: the driver-LINQ discriminator filter serializes the discriminator value RAW (`MongoEFDiscriminator.GetDiscriminatorsForTypeAndSubTypes` → `BsonValue.Create(GetDiscriminatorValue())`, bypassing the conversion), whereas the native predicate serializes it THROUGH the property serializer (applying the conversion), so an unguarded native `$eq`/`$in` would return a **different row set** than the established driver-LINQ path — violating `Native == DriverLinq`. The plain-string discriminators used by the default/shadow mapping modes have no converter/representation and stay native.
>
> **Projected `Distinct` (EF-347, SP6-remaining slice 2).** Native now also covers `Distinct()` applied to a terminal anonymous/DTO projection (`Select(new {...}).Distinct()`): `TranslateDistinct` calls `NativeGroupByBinder.TryBindDistinctFromProjection`, which converts each already-populated `Select.Projection` entry (alias → field-ref, from the SP3 `$project` pushdown) into a **degenerate `$group`** — a composite (or scalar) key made of those same field-refs, with **zero accumulators** — replacing `Projection` with a flattening projection that reads each value back out of `_id.<alias>` (`_id` for a single-part key), exactly mirroring the GroupBy flatten mechanism. `Route` resolves to `NativeRoute.GroupBy` (a grouping with no accumulators is still a grouping), so the lowerer's existing group branch emits `$group` → flatten `$project` with no special-casing. **No shaper changes**: the shaper was already built by the preceding `Select` to read the top-level result aliases by name, and those same aliases survive the flatten. `TryBindDistinctFromProjection` also sets a **separate** `Select.IsDistinct = true` provenance flag on success (NOT `IsGroupBy`) so the **existing** post-group guards (`NativeSlotPopulator`'s post-group slot-operator guard **and** `NativeCardinalityBinder.TryBindAggregate`/`TryBindReducer`, all now keyed on `IsGroupBy || IsDistinct`) also cover an operator applied **after** this `Distinct` — without it, e.g. a `Where` whose member name happens to match a real entity property name would resolve against the entity and get hoisted to a pre-group `$match` instead of being rejected. **Why a separate flag, not `IsGroupBy`:** the QMTEV `TranslateJoinCore` join-decline is grouping-semantics-specific — a genuine `GroupBy` joined via driver-LINQ returns silently-wrong (empty) joins, so it **hard-declines** (`MarkGroupByFallbackUnsafe` → throws under both `Native` and `NativeOnly`). A projected `Distinct` is just a flat row set the driver-LINQ path joins **correctly**, so `Distinct`-then-`Join` must fall back **gracefully** (`TranslateJoinCore` calls `MarkNotNativelyRepresentable` for an `IsDistinct`-and-not-`IsGroupBy` join side — runs correctly under `Native`/`DriverLinq`, throws only under `NativeOnly`). Reusing `IsGroupBy` for Distinct would have hard-thrown `Distinct().Join(...)` under `Native` — a correct-results→throw regression. Note the lowerer's group branch returns early after the `$group`+flatten `$project`, so a native `Distinct`+`Join` would silently drop the join — hence it must fall back (never go native), just gracefully. **Falls back to driver-LINQ:** a **bare-scalar** projection (`Select(o => o.Country).Distinct()` — bare-scalar `Select` never populates `Projection` in the first place, so `TryBindDistinctFromProjection`'s `Projection.Count == 0` guard rejects it) and a **whole-entity** `Distinct()` (same reason). **Rejected by a guard → fall back (correctness, not just an optimization gap):** a projected key backed by a property with a value converter or non-default `BsonRepresentation` — `HasDefaultKeySerialization` is reused as-is from the GroupBy binder (same generic-`_id`-readback divergence risk). `IsNativeRepresentableSlotOperator` gained `Distinct` so the slot-populator catch-all doesn't clobber `TranslateDistinct`'s own decision (mirroring how `Select`/`OfType` are listed). **A `GroupBy` applied AFTER a projected `Distinct` (`Select(new{..}).Distinct().GroupBy(k)`) falls back** via a dedicated guard at the top of `TranslateGroupBy`: because `GroupBy` has its own `Translate` override it bypasses the `IsGroupBy || IsDistinct` post-group guards in `NativeSlotPopulator`/`NativeCardinalityBinder`, so without this guard `TryBindGroupKey` would OVERWRITE the Distinct's key-only `Grouping` with the GroupBy's own key — silently DROPPING the Distinct and emitting a `$group` that counts ALL rows instead of distinct rows (a silent wrong-data bug). `TranslateGroupBy` therefore checks `IsDistinct || IsGroupBy || Grouping != null` first and, if set, marks the query non-native (and sets `IsGroupBy` for the join-decline machinery) WITHOUT rebinding — falling back to driver-LINQ. (The reverse, `Distinct` after `GroupBy`, is already safe: `TryBindDistinctFromProjection` returns `false` when `Grouping != null`.) **EF-347 slice 5 fix (whole-branch review, silent-null Distinct-after-SelectMany):** `TryBindDistinctFromProjection`'s guard also declines when `select.UnwindSource != null` — a projected `SelectMany` (owned or reference) is itself a terminal, and without this guard `Distinct` after one would convert the SelectMany's `Projection` into a degenerate `Grouping` while `UnwindSource` stayed set; `MongoSelectLowerer.Lower` checks `UnwindSource` BEFORE `Grouping` and returns early, so the `$group` this Distinct built was silently never emitted — the flatten `$project` read `_id.<alias>` fields that had nothing to read, producing `[null, null, null]` under BOTH `Native` and `NativeOnly` (the bug this guard fixes; see `NativeSelectManyTests.Reference_form_followed_by_Distinct_hard_fails_in_every_mode` / `Explicit_result_selector_form_followed_by_Distinct_falls_back_gracefully_except_under_NativeOnly`). This is the same family as the `Grouping != null` check on the same line — `TryBindDistinctFromProjection` now declines after ANY prior terminal (`Grouping` or `UnwindSource`), not just a prior `GroupBy`.
>
> **Include (EF-339, SP5 — flat collection Includes).** Native now covers **single-level collection `Include`** (`Include(x => x.Orders)`), plus a **projected collection `.Count`** (`Select(c => new { c.Orders.Count })` → server-side `$size` over the `$lookup` array). The lowerer emits a flat `$lookup` (no `$unwind`) after the canonical `$match → $sort → $skip → $limit` (so filter/sort/paging are pushed **ahead** of the join — the observable MQL change this sweep rebaselined); the DOM shaper then materializes the joined array. Collection `Include` is native via the **DOM** shaper (collection navs are ineligible for streaming, gated off by `StreamingEligibility`). **Reference `Include` remains deferred/fallback, unchanged by this sub-project** — it still nav-expands to a `LeftJoin` that the gate treats as non-native, so it falls back to driver-LINQ (correct results; throws under `NativeOnly`), exactly as before EF-339. Its native lookup/streaming machinery (lowerer `$lookup`/`$unwind`, `GetStreamingReferenceLookups`, streaming-Include eligibility) stays **built but dormant**, awaiting a future streaming sub-project. Native-vs-driver is decided by the lowerer (`TryBuildNativeFactory`) — collection Include goes native the moment the lowerer stops rejecting the flat `$lookup` shape, no separate gate flag. The `IsNativeCollectionLookup` discriminator (`As == LookupExpression.GetLookupAlias(Navigation)`, i.e. the un-prefixed `_lookup_<Nav>` alias) is what admits the flat single-level collection shape while still excluding the (still-fallback) reference-Include `_outer`/`_inner` shape and the collection-of-collection `_lookup_<Nav>._lookup_<Coll>` shape (which keeps prefixed aliases and stays fallback). **Still deferred/fallback:** reference `Include`, nested/transitive `ThenInclude`, filtered `Include`, collection-of-collection, and collection-array **streaming** materialization (SP5b / SP7). EF-334 later centralized the **is-native** gate decision into one `ClassifyNativeDisposition` classification (`Route` + vector-search + GroupBy-unsafe); `AllPendingLookupsAreStreamable` deliberately stayed a **separate** streaming-vs-DOM axis (it is not an is-native signal). The residual `$lookup`-state relocation off `MongoQueryExpression` is tracked under EF-317 (a driver-`LeftJoin`-gated removal), independent of EF-334.
>
> **GroupBy (EF-SP6 / EF-344).** Native now also covers **`GroupBy(key).Select(aggregate)`** → a server-side `$group` followed by a **flattening `$project`** that lifts the grouped output (the `_id` scalar key, each `_id.<Name>` composite sub-key, and each accumulator output field) up to top-level result aliases. The grouped rows materialize through the **existing DOM projection shaper** (`MongoProjectionBindingRemovingExpressionVisitor`) reading those flattened aliases by name — there is **no** bespoke grouping shaper and **no** `IGrouping` materializer (the gate compiles it DOM-only, `allowStreaming: false`, via the `NativeRoute.GroupBy` branch). **Keys:** a scalar key (`_id: "$field"`) or a composite/anonymous key (`_id: { Name: "$field", … }`), each part a plain field-ref. **Accumulators:** `Count`/`LongCount` → `$sum: 1` (including a *lone* `Count()` projection, `GroupBy(k).Select(g => new { g.Key, Count = g.Count() })` — this is **not** fused by EF into a `resultSelector`-bearing `GroupBy` and goes native); `Sum`/`Average`/`Min`/`Max` over a plain field-ref selector → `$sum`/`$avg`/`$min`/`$max`. **Mechanism:** `MongoGrouping` IR on `MongoSelectDefinition.Grouping` (with the transient `PendingGroupKey` holding the key while it is parsed ahead of the aggregate `Select`), `NativeRoute.GroupBy`, `NativeGroupByBinder` (`TryBindGroupKey` called from the QMTEV's `TranslateGroupBy` — which builds the grouped `ShapedQueryExpression` + `GroupByShaperExpression` **directly**, since the base `TranslateGroupBy` is abstract; `TryBindGroupProjection`/`TryBindAccumulator` called from the grouped-source branch of `TranslateSelect`), `MongoGroupStage` + `MongoPipelineFactory.RenderKeyedGroup`, and the `MongoSelectLowerer` group branch. The provider's own `EnumerableMethods` port was extended with the aggregate-selector members (EF Core's is `internal`).
>
> **Behavior change (not a break).** Before EF-344, `GroupBy` **hard-failed** translation (`NotTranslatedExpression`). Now supported shapes go native and **unsupported shapes fall back to driver-LINQ** (throwing only under `NativeOnly`), except the one declined family below. Per the versioning rubric this — and the emitted MQL — is **not** a breaking change: query results are unchanged; the change is hard-throw → native / graceful-fallback.
>
> **Falls back to driver-LINQ (correct results under default `Native`):** computed keys (`g => g.OrderDate.Year`) and other non-member key expressions that `TryBindGroupKey`'s switch rejects — it accepts only a plain `MemberExpression` or an anonymous-of-members `NewExpression`, so e.g. an `EF.Property<T>(o, "…")` key (a `MethodCallExpression`) falls back, computed accumulator operands (`g.Sum(x => x.A * x.B)`), **bare** `GroupBy(key)` / `GroupBy(key, elementSelector)` that terminate on the `IGrouping` sequence (`Route` stays `Fallback` while `PendingGroupKey` is set but `Grouping` is never finalized), a user-supplied `GroupBy(key, resultSelector)` (the QMTEV's `TranslateGroupBy` declines a non-null `resultSelector`), **post-group slot operators** (`Where`-as-HAVING / `OrderBy` / `OrderByDescending` / `ThenBy` / `ThenByDescending` / `Skip` / `Take` applied **after** the grouping) — these fall back **because of an explicit guard**, not by luck: `NativeSlotPopulator.PopulateNativeSlots` calls `MarkNotNativelyRepresentable()` and returns for these seven operators once `MongoSelectDefinition.IsGroupBy` is set (`IsPostGroupSlotOperator`), forcing a clean driver-LINQ fallback. Without the guard the post-group predicate/sort would be resolved against the **entity** type by member name (the translator is built from `CollectionExpression.EntityType`) and emit a **pre-`$group`** `$match`/`$sort` — and when an aggregate alias collides with a real property name (e.g. `Amount`) it silently returned wrong data. The guard is keyed on `IsGroupBy` (set unconditionally by `TranslateGroupBy`) rather than the finalized `Grouping`, and is scoped to the seven slot operators only so the supported `GroupBy(key).Select(aggregate)` (whose aggregate `Select` reaches `PopulateNativeSlots` with `IsGroupBy` already `true`) still goes native. **Post-group scalar aggregates and reducers** (`Count`/`LongCount`/`Sum`/`Min`/`Max`/`Average` / `First`/`Single`/`Any`/`All` applied **after** the grouping) fall back the same way, via a symmetric `IsGroupBy` guard at the top of BOTH `NativeCardinalityBinder.TryBindAggregate` **and** `NativeCardinalityBinder.TryBindReducer` (EF-344 pass-2). Without it, setting `Cardinality` on an already-grouped select flips `Route` to `ScalarAggregate` (which is prioritized above `GroupBy`) while the lowerer's grouping branch still emits `[$group, $project]` with no terminal `$count`/aggregate/limit stage — the scalar shaper then reads a nonexistent element and crashes with `KeyNotFoundException` instead of falling back. **Invariant: EVERY post-group / post-terminal operator entry point must gate on `IsGroupBy` (and, since EF-347, `IsDistinct`)** — currently `NativeSlotPopulator.PopulateNativeSlots` (the seven slot operators, on `IsGroupBy || IsDistinct`), `NativeCardinalityBinder.TryBindAggregate`/`TryBindReducer` (scalar aggregates / reducers, on `IsGroupBy || IsDistinct`), **`TranslateGroupBy`** (a `GroupBy` after ANY prior terminal — gates on the full `HasTerminalOperator`, captured as `hadTerminalGrouping` BEFORE the unconditional `IsGroupBy = true`, and falls back WITHOUT rebinding, else it overwrites the existing `Grouping`), **`TranslateSelectMany`** (a `SelectMany` after ANY prior terminal — gates on `HasTerminalOperator` at the top and returns `null` → clean hard-fail in every mode; see the SelectMany-after-terminal note below), and **`TranslateSelect`'s non-grouped projection branch** (a second projected `Select` after a native `Distinct`/`GroupBy` — gates on `Grouping != null || IsGroupBy || IsDistinct` and skips `TryPopulateNativeProjection`, else it appends a field-ref onto the terminal's `Projection` while `Grouping` is set → the lowerer emits a flatten `$project` over fields gone after the `$group` → silent nulls). `TryBindDistinctFromProjection` ITSELF is a fifth member of this family, though its own guard checks state directly rather than a flag: it always declined when `Grouping != null` (a prior `GroupBy`), and — since the EF-347 slice 5 whole-branch-review fix — also declines when `select.UnwindSource != null` (a prior projected `SelectMany`, owned or reference), i.e. `Distinct` now correctly declines after ANY prior terminal, not just a prior `GroupBy`; the missing `UnwindSource` check was the exact silent-null bug this fix closes (see the "Projected `Distinct`" note above). **EF-347 slice 4 adds a member to this family that runs the OPPOSITE way round — a check that must fire BEFORE the post-terminal guard, to correctly ADMIT a native shape rather than reject one:** `TranslateSelect`'s pending-SelectMany-projection branch, gated on `UnwindSource != null && Projection.Count == 0`, calls `NativeSelectManyBinder.TryBindTransparentIdentifierProjection` and — on success — returns early with the SelectMany's own result shaper, all before reaching the ordinary `IsTransparentIdentifierSelector`/`IsTransparentIdentifierMemberAccessSelector` post-terminal else-if chain below it. This ordering is load-bearing: a bare-nav owned `SelectMany` (`TryBindBareNavUnwind`, see the SelectMany note below) sets `UnwindSource`, which already satisfies `HasTerminalOperator` — so without binding the trailing projection FIRST, the ordinary post-terminal guard would reach this same `Select` first and wrongly call `MarkNotNativelyRepresentable()` on a shape that is, in fact, natively representable. **`Select`, `GroupBy`, `OfType`, and `SelectMany` are the own-`Translate`-override operators that need the explicit guard** (they bypass the `NativeSlotPopulator`/`NativeCardinalityBinder` catch-all guards) — `OfType` gates on `mongoQueryExpression.Select.HasTerminalOperator` at the top of its discriminator-predicate branch in `TranslateOfType`, added as a final-review fix once `Union`/`Concat` (EF-347 slice 2) made a whole-entity terminal reachable before `OfType` for the first time (previously `OfType` was only ever reached pre-terminal, so the gap was latent). Without it, `OfType` after a `Union`/`Concat` adds its discriminator conjunct to the OUTER select's tail `$match`, which the lowerer emits as a pre-`$unionWith` `$match` that filters only the outer rows — the `$unionWith` operand's own nested pipeline gets no discriminator filter, so sibling-type rows from the operand leak into the result (see `NativeSetOpsTests.OfType_after_union_falls_back`, which reproduces this as an `InvalidOperationException` at materialization — a leaked base-type document reaching a shaper fixed to the derived type — rather than a silently-wrong result, but the underlying leak is the same class of bug). `Distinct` is covered incidentally, not by an explicit `HasTerminalOperator` check: `TryBindDistinctFromProjection`'s `Projection.Count == 0` guard already rejects a whole-entity/post-terminal source, so it falls back for an unrelated reason that happens to also cover this case. **`SelectMany` also needs the explicit guard, and it was the one own-override operator that originally lacked it** (composition-seam audit finding): its binders (`NativeSelectManyBinder.TryBind*`) set `UnwindSource` on pure collection-selector STRUCTURE, with no post-terminal check, and `SelectManyWithCollectionSelector` is whitelisted in `IsNativeRepresentableSlotOperator` so the catch-all does not back it up either. Without the guard, `Union`/`Concat`-then-`SelectMany` (`Union(a,b).SelectMany(o => o.Items.Select(...))`) set `UnwindSource` alongside the already-attached `SetOperation`; because the lowerer checks `SetOperation` BEFORE `UnwindSource` (its fixed terminal precedence `SetOperation > UnwindSource > Grouping > Projection > Cardinality`), the `$unwind`/`$project` was SILENTLY DROPPED — the query returned whole outer union rows (wrong row count, or a shaper crash when a projected alias is absent at top level) under BOTH `Native` and `NativeOnly` (`Route` stayed non-`Fallback`, so `NativeOnly` did not even throw). The fix gates the 2-arg `TranslateSelectMany` on `HasTerminalOperator` at the top and returns `null` (not `MarkNotNativelyRepresentable()`): a graceful fallback is NOT viable here because the native SelectMany builds a by-index `ProjectionBindingExpression` shaper the driver-LINQ fallback cannot re-read — the SAME shaper-rebuild limitation that makes operators composed AFTER a SelectMany hard-fail in every mode — so `null` (EF's own translation-failure path, a clean hard-fail in every mode) is the correct, contract-consistent decline. See `NativeCompositionSeamAuditTests`. (A related latent-but-currently-unreachable gap: `IsPlainWholeEntitySelect` — the set-op operand guard — does not check `UnwindSource`, so `Union` AFTER a bare-nav `SelectMany` is not explicitly rejected; unreachable today because the trailing projected `Select` sets `Projection` → `Route = Projection` first, which `IsPlainWholeEntitySelect`'s `Route == WholeEntity` check already rejects.) `Cast` needs no guard: `TranslateCast` is a pure shaper reshape (`ReshapeShaperExpression`) that mutates no outer slot or predicate. A future own-override operator applied after a terminal must add the same gate. (Empirical note for the `TranslateSelect` case: in the current provider this shape additionally throws at shaper build — `MongoProjectionBindingExpressionVisitor` cannot read a prior anonymous projection's members — in *all* modes, so the null-data symptom is not presently reachable; the guard is defense-in-depth for a future shaper-builder that makes chained-projection shapers buildable.) Any future reducer/aggregate/operator added after a group must add the same guard, or it reopens this class of bug (the post-group operator resolves against the base entity / picks the wrong route). **EF-347 slice 3 adds a further entry point to this family — a guard against a wrong REJECTION rather than a wrong RESULT:** `Visitors/MongoProjectionBindingExpressionVisitor`'s `ProjectionBindingExpression { Index: not null }` case in `Visit` passes an already-resolved-by-index projection member straight through, gated on `_queryExpression.Select.Route == NativeRoute.Projection`. It exists specifically so EF's mandatory unwrap-`Select` (`.Select(ti => ti.Inner)`, always synthesized right after a native SelectMany's `TransparentIdentifier(Outer, Inner)` result-selector — see the SelectMany note above) can re-enter the shaper this visitor already built for the SelectMany's own projection, instead of falling into the ordinary `MemberExpression` re-binding path (which would try to derive a brand-new projection mapping for a member access that no longer resolves against any real CLR type) — a case the other post-terminal guards in this family never had to handle, because none of them re-enter this visitor a second time on the same already-bound expression. The `Route == Projection` gate is deliberately narrower than `HasTerminalOperator`: `GroupBy`/`Distinct` flip `Route` to `Fallback` (via `MarkNotNativelyRepresentable()`) BEFORE this visitor ever runs for a projected `Select` applied after either of them, so that case still correctly falls through to the translate-failed throw instead of being passed through here — passing through unconditionally would silently defeat the established `TranslateSelect`/`TranslateGroupBy` guards documented above (see the load-bearing comment at the case itself, which also cross-references the `StructuralTypeShaperExpression` precedent this mirrors). Also falling back: the broader long tail the driver-LINQ provider already handles (`Distinct`/`Union`/join-then-group/nav-key groupings) — all reachable now precisely because `GroupBy` no longer hard-throws.
>
> **Rejected by guards → fall back (the guards PREVENT native wrong-results):** a grouping key with a value converter or a non-default `BsonRepresentation` (`NativeGroupByBinder.HasDefaultKeySerialization`) — the generic `_id` readback (the flattened `_id` has no backing `IProperty`) would diverge from the property's configured serializer; and an accumulator whose source is **not** the grouping parameter `g` (a correlated cross-collection subquery, a navigation, a different collection) (`NativeGroupByBinder.IsGroupingSource`) — binding it to a `$group` accumulator would silently drop the subquery and collapse e.g. a subquery `Count` to `$sum:1`.
>
> **Declines to a clean `NativeTranslationNotSupportedException` — NO fallback, under both `Native` and `NativeOnly`:** a **group-first** `GroupBy` combined with a `Join`/`GroupJoin`/`LeftJoin` (a join taken over a grouped source, e.g. the spec's `GroupBy_Aggregate_Join`). Its driver-LINQ fallback returns **silently wrong** data (the joined entity is empty for every group), so the provider declines rather than route to a known-wrong result: `MongoSelectDefinition.MarkGroupByFallbackUnsafe()` (set in the QMTEV `TranslateJoinCore` when either join side `IsGroupBy`) trips a dedicated gate check in `MongoShapedQueryCompilingExpressionVisitor.VisitShapedQuery`. **Explicit `MongoQueryMode.DriverLinq` still executes it** (the user's opt-in, carrying the same wrong-data caveat). **Join-then-group** (an aggregate over a join result) falls back **correctly** and is unaffected — do not conflate the two orderings.

> **Set operations — `Union`/`Concat` (EF-347 slice 2).** Native now also covers a **whole-entity, terminal** `Union`/`Concat` over the SAME entity type: `TryTranslateSetOperation` (backing both `TranslateUnion` and `TranslateConcat`) attaches a `MongoSetOperation` (`Kind` + the second operand's own `MongoSelectDefinition` + its collection name) to source1's `Select.SetOperation` when both operands are a plain whole-entity select (`IsPlainWholeEntitySelect` — filter/sort/paging only, no projection/grouping/cardinality/lookups/`VectorSearch`/own set-op) of the matching `CollectionExpression.EntityType`; otherwise it calls `MarkNotNativelyRepresentable()` and returns source1 unchanged — `TryTranslateSetOperation` **always** returns non-null (mirroring `TranslateGroupBy`'s contract), so an out-of-scope shape falls back gracefully rather than hard-failing translation. The lowerer (`MongoSelectLowerer.Lower`) renders the attached `SetOperation` as a terminal `MongoUnionWithStage` — the operand's own canonical `$match`/`$sort`/`$skip`/`$limit` stages, lowered independently via the same `AppendCanonicalStages` helper the outer query uses — appended **last**, after the outer query's own canonical stages and any `$lookup`. `MongoPipelineFactory.RenderUnionWith` renders the operand's nested pipeline into the aggregation `$unionWith` stage using the **same shared `PlaceholderTable`** as the outer query, so a parameter captured in the operand's own predicate (e.g. `set1.Union(set2.Where(c => c.X == capturedLocal))`) is substituted correctly at `Build(parameterValues)` time. `Union` additionally emits a `$group{_id:"$$ROOT"}` + `$replaceRoot` dedup stage after the `$unionWith` (full-document de-duplication, matching BCL `Union` set semantics); `Concat` does not. **`IsSetOp` joins `HasTerminalOperator`** (`IsGroupBy || IsDistinct || IsSetOp || Grouping != null`) — the same centralized post-terminal gate `GroupBy`/`Distinct` use. **Invariant: set operations are terminal-only** — every post-terminal entry point (`NativeSlotPopulator`'s seven slot operators, `NativeCardinalityBinder`'s aggregates/reducers, `TranslateGroupBy`'s rebind guard, and `TranslateSelect`'s two guards — the hoisted-shared-Include guard and the non-grouped-projection guard) already gated on `HasTerminalOperator` before this slice, so `Union`/`Concat` need **no new guard code** to be covered — they only need `IsSetOp` folded into the shared predicate, which is exactly what `HasTerminalOperator` does. **EF-347 slice B relaxed this at exactly the two CATCH-ALL guard sites** — `NativeSlotPopulator`'s post-group/post-terminal slot guard and `NativeCardinalityBinder.TryBindReducer`/`TryBindAggregate` — both now check `HasTerminalOperator && !IsSetOpTerminalOnly` instead of `HasTerminalOperator` alone. `IsSetOpTerminalOnly` (`MongoSelectDefinition`) is `IsSetOp && !IsGroupBy && !IsDistinct && Grouping == null && UnwindSource == null` — narrowly true only when a set op is the SOLE terminal seen so far. With the relaxation, `Where`/`OrderBy`/`ThenBy`/`Skip`/`Take` and scalar aggregates/reducers (`Count`/`Sum`/`Min`/`Max`/`Average`/`First`/`Single`/…) composed AFTER a set op fall through to their ordinary arms and record into a **second** ordered op list, `MongoSelectDefinition.TrailingOps` (mirroring `PipelineOps`), via the same five merge methods (`AddPredicateConjunct`/`StartOrReplaceSort`/`AppendThenBy`/`AppendSkip`/`AppendLimit`) — those methods target a private `ActiveOps` property that is `PipelineOps` normally but flips to `TrailingOps` the instant `SetOperation` is attached, so the flip point is single and well-defined. `MongoSelectLowerer.Lower` emits `PipelineOps` (source1's pre-terminal ops), then the set-op stage (`$unionWith`/`$group`/`$replaceRoot` for `Union`, or the source-tagging pipeline for `Intersect`/`Except` — see the slice A note below), then `TrailingOps` verbatim, then falls through to the ordinary cardinality-stage tail — so a trailing filter/sort/page or a terminal reducer/aggregate now operates on the COMBINED set-op result, not source1's pre-set-op rows (see `NativeSetOpsTests.Where_after_union_goes_native`/`OrderBy_after_union_goes_native`/`Paging_after_union_goes_native`/`Count_after_union_goes_native`/`First_after_union_ordered_goes_native`). **`IsSetOpTerminalOnly` relaxes ONLY those two catch-all sites** — every deferred own-`Translate`-override operator (`Select`/`Distinct`/`GroupBy`/`SelectMany`/`OfType`) and a chained set op keep their OWN untouched `HasTerminalOperator` check (no `!IsSetOpTerminalOnly` escape hatch anywhere else), so they remain terminal after a set op exactly as before slice B — the relaxation surface is deliberately these two sites and nowhere else, since every other post-terminal entry point already decides representability itself via its own guard. A **chained** `set1.Union(set2).Union(set3)` therefore still falls back gracefully, unaffected by slice B: `IsPlainWholeEntitySelect` rejects source1 once its `Select.IsSetOp` is `true`, so the second `Union` marks it non-native rather than nesting `$unionWith` stages — chaining is declined in `TryTranslateSetOperation`'s own scope gate, not one of the two relaxed catch-alls. **`Intersect`/`Except` now also go native for the same whole-entity, terminal shape — and share the identical slice-B trailing-ops relaxation — via a different rendering and a different guard-decline path — see the set-ops slice A note immediately below.** **EF-347 slice C2: a trailing anonymous/DTO member-access `Select` after a whole-entity set op now ALSO goes native** — `Union(A,B).Select(x => new {...})` emits a `$project` after the set-op stage, via the SAME slice-B `TrailingOps`/`ActiveOps` fall-through plus the pre-existing SP3 projection binder (`NativeProjectionBinder.TryPopulateNativeProjection`) — no lowerer or shaper change was needed, since the lowerer already appends `Projection` last and the SP3 shaper is set-op-agnostic. **Mechanism (seam closure):** `IsSetOpTerminalOnly` gained a `Projection.Count == 0` conjunct — this ADMITS the trailing projection (`Projection` is still empty at the moment `TranslateSelect`'s post-terminal guard runs, since a set-op-only terminal with nothing else attached is still "terminal-only") and, symmetrically, CLOSES post-projection composition: once `Projection` is populated, `IsSetOpTerminalOnly` flips to `false`, so a `Where`/aggregate/second `Select` applied AFTER the trailing projection no longer qualifies for the two catch-all-relaxation sites and falls back (Union/Concat) or hard-fails (Intersect/Except) exactly like any other post-terminal operator. **Empirical finding (Task 2, verified via captured MQL, not assumed):** for a predicate/selector that is a PURE, invertible pass-through of the trailing projection's own member(s) (e.g. `.Select(i => new{N=i.Value}).Where(x=>x.N>=2)`, or two consecutive member-access Selects), EF Core's own query compiler (the `NavigationExpandingExpressionVisitor` pending-selector mechanism) pushes/fuses the composition BEFORE the Select ever reaches this provider's translator — so these two specific shapes never actually exercise the post-projection-composition seam at all; they translate as an ordinary trailing-`Where`-then-trailing-`Select` (or a single fused Select) and go fully native with correct results. This is a general EF Core LINQ-compilation behavior, not something this provider controls or something specific to set operations — the same fusion is observed for a plain aggregate (`Sum(x => x.N)`) too (see `NativeSetOpsTests.Where_after_trailing_projection_on_union_goes_native_via_ef_predicate_pushdown`/`Second_projection_after_union_goes_native_because_ef_fuses_the_two_selects` — named for the observed behavior, not the originally-assumed fallback — and the corresponding Intersect variants). **Settled finding (an exhaustive follow-up probe, recorded here so it is not re-litigated):** no public-LINQ shape has been found that actually reaches the `Projection.Count == 0` seam. The probe tried seven post-projection operators — `Distinct`, `GroupBy`, a chained set op, `Skip`, `Take`, `Count`, `First` — against BOTH sites `IsSetOpTerminalOnly` actually gates (`NativeSlotPopulator`'s slot operators, `NativeCardinalityBinder`'s aggregates/reducers): every lambda-bearing or parameterless per-row operator (`Skip`/`Take`/`Count()` included) gets the identical EF pending-selector pushdown described above before the translator ever sees post-projection composition, and every operator that genuinely forces materialization of the projected row (`GroupBy`, a chained set op) is declined by its OWN independent `IsSetOp`/`HasTerminalOperator` guard, unconditional on `IsSetOpTerminalOnly` — while `Distinct` in that same position is bound natively (see the reconciled trailing-`Distinct` note below), again without ever consulting `IsSetOpTerminalOnly`. So the `Projection.Count == 0` conjunct's seam-closure half is **defensive-only** — it hardens `IsSetOpTerminalOnly` against a hypothetical future internal composition path, not against anything reachable today via ordinary LINQ — while its **essential** half (admitting the trailing projection at push-down, described above) is the one every functional test in this file actually exercises. The seam-closure half's sole proof, and the one expected to remain its sole proof, is the IR-level unit test `MongoSelectDefinitionTrailingOpsTests.IsSetOpTerminalOnly_false_when_a_projection_is_populated`. **Falls back to driver-LINQ (correct results under default `Native`):** a **bare-scalar or entity-ref** set-op OPERAND (`Select(a => a.Name).Union(...)`) — SP3 never pushes these down, so the operand is not a plain projected select (contrast the SUPPORTED anonymous/DTO member-access projected-**OPERAND** shape — a DIFFERENT thing from the slice-C2 trailing projection above — which now goes native; see the dedicated projected-operand set-ops note below). **A numeric-arithmetic computed-leaf OPERAND (`Select(a => new { X = a.Value * 2 }).Union(...)`) is NO LONGER in this fallback list** — EF-347's arithmetic computed projections (see the dedicated note above) populate `Projection` for this shape too, so `IsPlainProjectedSelect` now accepts it and it goes native, same as the member-access projected-operand shape (see `NativeSetOpsTests.Computed_leaf_operand_union_goes_native`); a non-arithmetic computed leaf (a method call, e.g. `Select(a => new { X = a.Name.ToUpper() }).Union(...)`) still falls back for the same reason it always did. A **mixed** whole-entity/projected operand pair (one operand whole-entity, the other projected — fails both scope gates), an operand carrying an `Include` (EF Core itself hoists a shared `Include` to apply AFTER the combinator, reaching `TranslateSelect` as `Union(A,B).Select(x => Include(x))` — caught by its `HasTerminalOperator` guard, untouched by slice B), mismatched operand entity types (defensive; unreachable in practice because EF Core's own `NavigationExpandingExpressionVisitor` rejects incompatible set-operation sources upstream), and — still deferred as of slice C2 — a **bare-scalar** trailing projection (`Select(i => i.Value)` — SP3 never pushes a bare scalar, set-ops or not); a **numeric-arithmetic** computed-leaf trailing projection is NO LONGER on this deferred list (EF-347; see `NativeSetOpsTests.Computed_leaf_projection_after_union_goes_native`/`Computed_leaf_projection_after_intersect_goes_native_result_set` and the dedicated arithmetic-computed-projections note above) — a **non-arithmetic** (method-call) computed-leaf trailing projection remains deferred, an **entity-ref** trailing projection, a hypothetical genuine **post-projection composition** (a `Where`/aggregate/second `Select` whose predicate/selector is NOT a pure pass-through of the projection) — the shape the `Projection.Count == 0` conjunct is designed to decline, though (per the settled finding above) no such shape has been shown reachable via ordinary LINQ composition — a **bare `Distinct`** applied directly to a whole-entity set-op result with NO trailing projection (`Union(A,B).Distinct()` — `TryBindDistinctFromProjection`'s own `Projection.Count == 0` check rejects this, confirmed empirically), a **chained** set op, and **`GroupBy`/`OfType`/`SelectMany` composed after a set op** (each still trips its own untouched `HasTerminalOperator` guard and falls back gracefully — throws only under `NativeOnly` — since Union/Concat retain their driver-LINQ baseline; see `NativeSetOpsTests.Bare_scalar_projection_after_union_falls_back_gracefully`/`Computed_leaf_projection_after_union_falls_back_gracefully`/`Chained_union_falls_back`/`GroupBy_after_union_falls_back`/`OfType_after_union_falls_back`). **A `Distinct` applied AFTER the slice-C2 trailing projection instead goes NATIVE with correct results** — confirmed empirically (`Union(A,B).Select(i=>new{N=i.Value}).Distinct()` under `NativeOnly` succeeds, `[1,2,3,4,5]`): `TryBindDistinctFromProjection` (`NativeGroupByBinder`) converts whatever `Projection` is already populated into a degenerate `$group`, unconditional on `IsSetOp`/`IsSetOpTerminalOnly`, so it "just works" for a set op's trailing projection exactly as for any other terminal projection — a pre-existing, `IsSetOpTerminalOnly`-independent capability, not something slice C2 itself added. **Deferred (out of scope, unchanged by slice C2):** a bare-scalar/entity-ref/non-arithmetic-computed-leaf set-op OPERAND (a numeric-arithmetic computed-leaf operand now goes native — see the correction above), or a mixed whole-entity/projected operand pair (both just described above — a projected/DTO-member-access OPERAND pair now goes native, see the dedicated slice C1 note below) — and `SelectMany` combined with a set op — neither is a gap discovered later, both are the intentional remaining terminal-only scope.
>
> **Set operations — `Intersect`/`Except`, source-tagging (EF-347, set-ops slice A).** Native now also covers a **whole-entity, terminal** `Intersect`/`Except` over the SAME entity type, reusing the SAME `TryTranslateSetOperation`/`IsPlainWholeEntitySelect` scope gate as `Union`/`Concat` above — but MongoDB has no direct intersect/except pipeline stage, so the lowerer renders a different, **source-tagging** MQL shape instead of a plain `$unionWith`, and the guard-decline path (below) also differs. **Mechanism:** both operands are the SAME collection (entity type ⇒ one collection), so documents on both sides have identical shape, making full-document `$$ROOT` value-equality well-defined — the same assumption `Union`'s own dedup already relies on. `MongoSelectLowerer.Lower` renders the attached `SetOperation` as a `MongoSetDifferenceStage` (instead of `MongoUnionWithStage`) for these two kinds, and `MongoPipelineFactory.RenderSetDifference` renders: dedup the outer operand (`$group{_id:"$$ROOT"}`) then tag it (`$project` with `_id:0`, the real document moved to `_doc`, plus literal `_a:true, _b:false`); render the inner operand into the SAME shared `PlaceholderTable` (so a captured parameter still substitutes correctly), dedup and tag it `_a:false, _b:true`; `$unionWith` the two; re-unify by full document (`$group{_id:"$_doc", _a:{$max:"$_a"}, _b:{$max:"$_b"}}` — `$max` over a boolean collapses to "present on that side"); discriminate with a final `$match`; then `$replaceRoot{newRoot:"$_id"}` to restore the plain document. `_a`/`_b` are siblings of `_doc`, never real entity fields, so there is no field-name-collision risk (verified by `NativeSetOpsTests.Intersect_with_real_element_named_underscore_a_is_not_corrupted_by_the_source_tag`). **`Intersect` vs `Except` differ ONLY in the final `$match`:** `{_a:true, _b:true}` (present on both sides) vs `{_a:true, _b:false}` (present in the first operand only) — every stage upstream of that `$match` is identical between the two kinds. **Result order is not guaranteed** — the re-unifying `$group` stages reorder rows, matching a database set operation and matching `Union`'s already-documented lack of an ordering guarantee. **No driver-LINQ baseline, unlike `Union`/`Concat`:** `TryTranslateSetOperation`'s guard-decline branch is kind-conditional — for `Union`/`Concat` an out-of-scope shape still calls `MarkNotNativelyRepresentable()` and returns `source1` (the graceful fallback documented above), but for `Intersect`/`Except` it returns `null` instead, because the C# driver's own LINQ v3 provider does not translate a cross-view `Intersect`/`Except` either (confirmed empirically by a throwaway probe test before this slice was built). `null` reaches EF Core's own `NotTranslatedExpression` failure path directly — a clean hard-fail in **every** `MongoQueryMode` (`Native`/`DriverLinq`/`NativeOnly`) for an out-of-scope set-op shape. This mirrors reference `SelectMany`'s no-baseline decline (EF-347 slice 5): a `null` return, not a graceful `MarkNotNativelyRepresentable()`, is the correct decline whenever there is no working driver-LINQ path to land on. **EF-347 slice B: `Where`/`OrderBy`/`ThenBy`/`Skip`/`Take` and scalar aggregates/reducers composed AFTER a native `Intersect`/`Except` now go NATIVE too**, via the identical `TrailingOps`/`ActiveOps`/`IsSetOpTerminalOnly` relaxation documented in the `Union`/`Concat` note above — both set-op kinds share the one `SetOperation`/`IsSetOp` mechanism, so the relaxation at the two catch-all guard sites (`NativeSlotPopulator`, `NativeCardinalityBinder.TryBindReducer`/`TryBindAggregate`) is kind-agnostic. E.g. `{1,2,3}.Except({3,4,5})` then `.Where(Value >= 2)`, or `.Intersect(...).OrderBy(...).Take(n)`, or `.Intersect(...).Count()` now all emit the trailing `$match`/`$sort`/`$skip`/`$limit`/aggregate stage AFTER the source-tagging pipeline above, over the COMBINED Intersect/Except result — see `NativeSetOpsTests.Except_then_Where_goes_native`/`Intersect_then_paging_goes_native`/`Count_after_intersect_goes_native`. **EF-347 slice C2: a trailing anonymous/DTO member-access `Select` after a whole-entity Intersect/Except now ALSO goes native**, exactly as documented for Union/Concat immediately above — same `Projection.Count == 0` seam-closure mechanism, same `NativeProjectionBinder` reuse, no lowerer/shaper change — this now ALSO includes a numeric-arithmetic computed-leaf trailing projection (EF-347; confirmed via `NativeSetOpsTests.Computed_leaf_projection_after_intersect_goes_native_result_set`), not just member-access. same query under default `Native` also succeeds with the identical result) — via the same `IsSetOp`-agnostic `TryBindDistinctFromProjection` mechanism documented in the Union/Concat note above. (A `Distinct` applied AFTER the trailing projection is instead a demonstrated native capability, for all four set operators — see above; it was never gated by `IsSetOpTerminalOnly` in the first place.) **Projected-operand set operations, for all four operators, are DONE (slice C1)** — see the dedicated note immediately below. With slice C1 complete, the set-ops decomposition (A → B → C1/C2) is now COMPLETE.

> **Set operations — projected operands (EF-347 slice C1, the FINAL set-ops slice).** Native now also covers a set operation whose OPERANDS are themselves a terminal SP3 anonymous/DTO member-access projection — `A.Select(new{...}).Union(B.Select(new{...}))` and the `Concat`/`Intersect`/`Except` equivalents — distinct from slice C2's trailing projection (`Union(A,B).Select(new{...})`), which projects the COMBINED result AFTER the set op rather than each operand BEFORE it. The two operands may be the SAME or DIFFERENT collections/entity types, provided their projected shapes (top-level alias sets) match. **Gate:** `TryTranslateSetOperation` adds a second acceptance branch alongside the existing whole-entity one — `IsPlainProjectedSelect(mongo)` (the projected analogue of `IsPlainWholeEntitySelect`: `Route == NativeRoute.Projection && Projection.Count > 0`, no grouping/cardinality/own-set-op/SelectMany/lookups/join/`VectorSearch`) on BOTH operands, plus `ProjectionShapesMatch` (equal top-level alias SETS between the two operands' `MongoProjection`s — same count, same alias names) — a CORRECTNESS guard, not just an optimization, since the dedup/source-tagging stages below compare whole projected documents by value and a mismatched alias set would compare structurally-different documents. The `CollectionExpression.EntityType`-equality check the whole-entity path uses does NOT apply on this path — that is exactly what admits different-collection operands (EF Core's own `NavigationExpandingExpressionVisitor` already rejects operands with incompatible shapes upstream, so `ProjectionShapesMatch` is defense-in-depth, not the primary safety net). On acceptance, `MongoSetOperation` gets a new `OperandsProjected` (`bool`) provenance flag, set `true`. **Lowerer:** `MongoSelectLowerer.Lower`, when `OperandsProjected`, emits source1's `$project` (`select.Projection`) immediately BEFORE the set-op stage (ahead of `$unionWith`/the set-difference pipeline) and the operand's own `$project` (`setOp.OperandSelect.Projection`) as the LAST stage of the nested operand pipeline — then suppresses the ordinary trailing-`Projection` fall-through (stage 6) so source1's projection is not double-emitted. `Union`'s dedup (`$group{_id:"$$ROOT"}`) and `Intersect`/`Except`'s source-tagging pipeline are UNCHANGED — they still operate on `$$ROOT`, which is now a projected document rather than a whole entity. **Dedup semantics — deliberately DIFFERENT from C2:** C1 `Union` dedups over the PROJECTED values (two distinct entities that project to equal values collapse to one row), matching BCL `A.Select(p).Union(B.Select(p))`; C2 dedups whole entities BEFORE projecting (see `NativeSetOpsTests.Projected_operand_union_dedups_over_projected_values_not_whole_entities`). **Different-collection operands have NO driver-LINQ oracle** — the provider's own cross-DbSet guard in the driver-LINQ fallback bridge (`MongoEFToLinqTranslatingExpressionVisitor`) throws for two different entity roots, so a different-collection projected-operand query is native-only by construction; proven via `NativeOnly` plus an expected-result-set assertion rather than `Native == DriverLinq` parity (same-collection operands DO have a driver oracle and ARE asserted for parity — see `NativeSetOpsTests.Different_collection_projected_operand_union_goes_native`/`Projected_operand_union_with_per_operand_filter_and_parameter_goes_native`). **Terminal-only, same as every other set-op shape:** because `Projection` is already populated at attach time, `IsSetOpTerminalOnly` (which requires `Projection.Count == 0`) is `false` from the start, so **no new guard code** is needed to close post-composition — every existing post-terminal entry point declines it automatically. For `Union`/`Concat` (same collection) this is a GRACEFUL fallback (correct results under `Native`, throws only under `NativeOnly`); `Intersect`/`Except` hard-fail in every mode (no oracle) — the same pattern as slice B. **Exception — a crash, not a graceful fallback:** a trailing SECOND `Select` (`A.Select(p).Union(B.Select(p)).Select(x => ...)`) crashes with a raw `InvalidOperationException` ("The LINQ expression 'ProjectionBindingExpression: Value' could not be translated") in EVERY mode, including explicit `DriverLinq` — a `ReplacingExpressionVisitor` `NewExpression`-fold reaches a `ProjectionBindingExpression` leaf that `MongoProjectionBindingExpressionVisitor` cannot read. This is an unsupported shape that never worked via driver-LINQ either (confirmed empirically: the identical exception fires under explicit `DriverLinq`, bypassing native translation entirely) — not a regression, and per the versioning rubric the exception TYPE of an unsupported shape is not part of the contract (see `NativeSetOpsTests.Second_select_after_projected_operand_union_hard_fails_in_every_mode`). **The `Distinct`-decline (regression fix):** `NativeGroupByBinder.TryBindDistinctFromProjection` declines — `select.SetOperation is { OperandsProjected: true }` — when a trailing `Distinct` is applied directly atop a projected-operand set op, because for THIS shape `select.Projection` is operand-1's OWN pre-combine projection (needed by the lowerer above), not a trailing post-combine projection; converting it into a degenerate `$group` in place would corrupt operand-1's pipeline (this was the original regression — a malformed pipeline that crashed at BSON deserialization — fixed by narrowing the decline to `OperandsProjected: true` specifically). So `A.Select(p).Union(B.Select(p)).Distinct()` now falls back gracefully for `Union`/`Concat`, and hard-fails every mode for `Intersect`/`Except` (no oracle), exactly like any other post-composition operator — see `NativeSetOpsTests.Distinct_after_projected_operand_union_falls_back_gracefully`/`Distinct_after_projected_operand_concat_falls_back_gracefully`/`Distinct_after_projected_operand_intersect_hard_fails_in_every_mode`/`Distinct_after_projected_operand_except_hard_fails_in_every_mode`. The guard is deliberately narrowed to `OperandsProjected: true` rather than a blanket `SetOperation != null`, to PRESERVE the pre-existing, unrelated C2 native capability: `Union(A,B).Select(p).Distinct()` (`OperandsProjected == false` — a genuine trailing projection over the combined result) still converts to a native `$group` exactly as before slice C1 (see `NativeSetOpsTests.Trailing_distinct_after_whole_entity_union_still_goes_native`). **Deferred, unchanged:** bare-scalar/entity-ref/non-arithmetic-computed-leaf operands (a numeric-arithmetic computed-leaf operand now goes native — EF-347, see the Union/Concat note's correction above) and a mixed whole-entity/projected operand pair (see the Union/Concat and Intersect/Except notes above), and post-composition generally (auto-closed, as described above). **New IR, no new stage:** `MongoSetOperation.OperandsProjected` (`bool`, `Expressions/MongoSetOperation.cs`); new predicates `IsPlainProjectedSelect`/`ProjectionShapesMatch` (`Visitors/MongoQueryableMethodTranslatingExpressionVisitor.cs`) — the existing `MongoUnionWithStage`/`MongoSetDifferenceStage` are reused unchanged; only the `$project` PLACEMENT changes. **With slice C1 done, the set-ops decomposition is COMPLETE: A (whole-entity terminal, `Intersect`/`Except`) → B (post-composition, all four) → C1 (projected operands, all four) / C2 (trailing projection, all four).**

> **Owned-collection `SelectMany` — both user-authored forms (EF-347 slices 3–4).** Native now covers owned-collection `SelectMany` projecting the collection element's members, as a `$unwind` + `$project`, in BOTH shapes EF's nav-expansion can produce. **Inner-`Select` form (slice 3):** `q.SelectMany(o => o.Items.Select(i => new {o.X, i.Y}))` — the projection is nested inside the collection selector itself. **Explicit-result-selector / query-syntax form (slice 4):** `SelectMany(o => o.Items, (o, i) => new {o.X, i.Y})` / `from o in q from i in o.Items select new {o.X, i.Y}` — nav-expansion normalizes BOTH of these user spellings to a BARE owned-nav collection selector (no nested `Select`) plus a SEPARATE trailing `Select` over the `TransparentIdentifier(Outer, Inner)` result. **This remains ADDITIVE, not a behavior change to an existing contract:** before slice 3, `SelectMany` hard-failed translation **unconditionally, in every `MongoQueryMode`** (no driver-LINQ fallback attempt at all — the QMTEV's `TranslateSelectMany` override simply returned `null`, reaching EF Core's own translation-failure path directly); each slice can only ever add newly-native shapes, never regress a previously-working one (the one behavior REFINEMENT, not a regression, is the whole-inner-entity clean decline below, which replaces an internal crash with a clean exception — the shape was never supported either way). **Mechanism, inner-`Select` form:** `TranslateSelectMany` calls `NativeSelectManyBinder.TryBind(mongoQueryExpression, collectionSelector)`, which — for the accepted shape only — sets `MongoSelectDefinition.UnwindSource` (the owned nav's element path) and populates `Projection` via the **two-scope** binder: outer (closed-over) members translate against `CollectionExpression.EntityType` to a root field ref (`$X`); inner (the nested `Select`'s own parameter) members translate against the owned nav's target entity type and get the unwind path prefixed (`$Items.Y`) — the two translators are kept **structurally separate** (not just parameterized) so a member name shared between the outer and inner types (e.g. both having a `Name`) can never resolve against the wrong scope (see `NativeSelectManyTests.Shared_outer_inner_member_name_resolves_to_distinct_values`). **Mechanism, explicit-result-selector / query-syntax form:** the SAME bare-nav shape reaches `TranslateSelectMany` for both the explicit 2-arg overload and the query-syntax equivalent (they normalize identically). `TranslateSelectMany` first tries `NativeSelectManyBinder.TryBindBareNavUnwind` — it accepts a bare owned-collection nav selector (`o => o.Items.AsQueryable()`, no nested `Select`) purely on STRUCTURE, sets `UnwindSource`, and hands EF the `TransparentIdentifier(Outer, Inner)` shape this overload always expects (an item shaper built from a `StructuralTypeShaperExpression` over the owned nav's target entity type — never itself materialized when the trailing projection binds natively; it exists only so this method's return type-checks, and so an UNSUPPORTED trailing projection still folds through EF's own `ReplacingExpressionVisitor` mechanism for the driver-LINQ fallback). The REAL projection is bound separately: `TranslateSelect`'s pending-SelectMany-projection branch (see the post-terminal-invariant note above — it runs BEFORE the ordinary post-terminal guard, load-bearing for exactly this reason) checks `UnwindSource != null && Projection.Count == 0` and calls `NativeSelectManyBinder.TryBindTransparentIdentifierProjection`, which two-scope-binds each `ti.Outer.<m>`/`ti.Inner.<m>` leaf — re-rooting onto a synthetic per-scope parameter first, since `MongoExpressionTranslator.TryTranslateField` only accepts a `MemberExpression` whose own `Expression` is a bare `ParameterExpression` — using the SAME two structurally-separate translators the inner-`Select` form uses. **Both forms:** `Route` resolves to `NativeRoute.Projection` exactly like a plain projected `Select` (only the new `MongoUnwindFieldStage`, emitted immediately before the `$project`, is SelectMany-specific). `UnwindSource != null` joins the shared `HasTerminalOperator` gate (`IsGroupBy || IsDistinct || IsSetOp || Grouping != null || UnwindSource != null`) — a native SelectMany is terminal-only, exactly like `Distinct`/`GroupBy`/`Union`/`Concat`. **The mandatory unwrap-`Select`.** Because EF always wraps the result in `TransparentIdentifier(Outer, Inner)`, a `.Select(ti => ti.Inner)` (inner-`Select` form) or the trailing projected `Select` (explicit form, bound as above) unconditionally follows in the same translated tree; both forms build their `TransparentIdentifier` shaper up front so this reaches `TranslateSelect`/`MongoProjectionBindingExpressionVisitor` with no further bespoke unwrap-handling code needed beyond what's described above. **Whole-inner-entity projection hard-declines cleanly, and this covers all three equivalent user spellings:** `SelectMany(o => o.Items, (o, i) => i)`, `from o in q from i in o.Items select i`, and the bare 1-arg `SelectMany(o => o.Items)` all normalize to the identical tree — `UnwindSource` set, `Projection` still empty, trailing selector a bare `ti => ti.Inner` member access. This is neither an anonymous/DTO construction (`TryBindTransparentIdentifierProjection` rejects it) nor left to the ordinary post-terminal guard (`IsTransparentIdentifierMemberAccessSelector(selector)` is true for exactly this shape, so that else-if is skipped too) — a dedicated check ("`UnwindSource` set, `Projection` still empty, AND the selector is this whole-inner-entity shape") throws a plain `NotSupportedException` directly, at TRANSLATION time, before `MongoQueryMode` is even consulted, so the SAME exception fires in `Native`, `DriverLinq`, and `NativeOnly` alike, regardless of tracking. This is a **behavior improvement, not a new limitation**: a prior pass called `MarkNotNativelyRepresentable()` here (the ordinary graceful fallback), but empirically neither the native path (a bare owned entity has no whole-unwind shaper) nor the "graceful" driver-LINQ fallback (its shaper has no owning-entity `bsonDoc` context either) can materialize this shape — both crashed with an internal `KeyNotFoundException("The given key 'bsonDoc' was not present in the dictionary")` instead of declining cleanly; the clean `NotSupportedException` replaces that crash in every mode, the shape remaining exactly as unsupported as before. **Composition after the SelectMany is a separate, narrower story, and — empirically (EF-347 Task 3) — DIFFERS BETWEEN THE TWO FORMS** (see `NativeSelectManyTests`' `*_after_SelectMany_*`/`Explicit_result_selector_form_followed_by_*` tests, one per operator per form): for the **inner-`Select` form**, `Where`/`OrderBy`/`Skip`/`Take`/`GroupBy`/another `SelectMany` composed after it ALL still hard-fail in every mode — their own guards correctly reach `HasTerminalOperator` and call `MarkNotNativelyRepresentable()`, but the driver-LINQ fallback that guard would normally permit cannot rebuild a shaper that re-reads this form's already-by-index-resolved projection (its captured method chain carries an EF-synthesized `.Select(ti => ti.Inner)` unwrap over an internal `TransparentIdentifier` CLR type the driver's own LINQ bridge cannot map) — except a **cardinality-only** operator like `Count`, which needs no shaper at all, so its fallback succeeds for real and returns the correct result under `Native`/`DriverLinq`, throwing only under `NativeOnly`. For the **explicit-result-selector / query-syntax form**, `Where`/`OrderBy`/`Skip`/`Take`/`Count` composed after it instead fall back GRACEFULLY (correct results under `Native`/`DriverLinq`, throwing only under `NativeOnly`) — the difference is structural: nav-expansion produces exactly `SelectMany(bareNav, trivialResultSelector).Select(ti => new{...}).<op>(...)`, a chain the driver's own LINQ v3 provider already knows how to translate on its own, with no extra `ti.Inner`-unwrap hop over an internal type to trip over. `GroupBy` and a further `SelectMany` composed after the explicit form, however, still hard-fail in every mode, same as the inner-`Select` form — `GroupBy` for the same shaper-rebuild reason (its own `TranslateGroupBy` override bypasses the ordinary catch-all guards, and its fallback still cannot re-read the prior projection), and a further `SelectMany` because its OWN collection-selector shape is independently rejected/untranslatable regardless of what precedes it. A computed/non-member projection leaf also differs by form: the inner-`Select` form rejects it structurally at `TryBind` (hard-fails in every mode — `Computed_leaf_hard_fails_in_every_mode`), while the explicit form's bare-nav bind succeeds on structure alone before the trailing projection is even examined, so only the SEPARATE trailing-`Select` bind rejects the computed leaf and calls the ordinary `MarkNotNativelyRepresentable()` — falling back gracefully with correct results under `Native`/`DriverLinq` (`Explicit_result_selector_form_computed_leaf_falls_back_gracefully_except_under_NativeOnly`). **Deferred (out of scope, both forms):** a **nested** SelectMany (an owned collection inside another owned collection) still keeps hard-failing exactly as before, not a gap newly introduced by either slice. (A **correlated** collection selector — referencing anything beyond the owner/element pair — is **NO LONGER deferred**: a later EF-347 slice made it go native too, for both forms; see the dedicated correlated-beyond-outer-OWNED note further below.) The explicit-result-selector / query-syntax form and the bare 1-arg `SelectMany(o => o.Items)` are **no longer deferred** as of slice 4 — see the mechanism and whole-inner-entity notes above for how each now resolves. A `SelectMany` over a **cross-collection reference** (non-owned) navigation is covered separately by **EF-347 slice 5** — the projected, FK-correlated form now goes native (see the note immediately below); a bare-entity reference result and an inner-element-only filtered reference form also go native (Tasks 4 and 5 respectively, see their dedicated notes); a correlated-beyond-FK inner ALSO now goes native (see the dedicated correlated-beyond-FK note below) — only a computed filter/projection leaf and a three-or-more-level (or owned-mixed) nested reference SelectMany stay deferred — an exactly-two-level, unfiltered nested reference SelectMany is NO LONGER deferred either; see the dedicated nested-reference note below.

> **Bare whole owned-collection-element `SelectMany` (EF-347, `selectmany-bare-owned` slice).** Native now ALSO covers the whole-inner-entity shape the note immediately above declines with a `NotSupportedException` — but only for an OWNED (embedded) collection, and only when the element itself carries no further navigations. All three equivalent user spellings — `from o in q from i in o.Items select i`, `SelectMany(o => o.Items, (o, i) => i)`, and the bare 1-arg `SelectMany(o => o.Items)` — normalize to the identical tree (`UnwindSource` set, `Projection` empty, trailing selector a bare `ti => ti.Inner`/`Include`-wrapped `ti.Inner` member access recognized by `TryGetWholeEntityMemberAccess`, which unwraps through any `IncludeExpression` layers first). **Gate:** in `TranslateSelect` (`Visitors/MongoQueryableMethodTranslatingExpressionVisitor.cs`), when `wholeEntityMember is { Member.Name: "Inner" }` AND `wholeElementCandidateUnwind.Kind == MongoUnwindSourceKind.Owned` AND `IsWholeElementRepresentable(innerEntityType, kind)` all hold, the code sets `UnwindSource.WholeElement = true` and falls through to the ordinary shaper fold, instead of throwing — the whole-OUTER (`select o`/`(o,i)=>o`) shape still falls to the `else if` and throws the SAME `NotSupportedException` as before (see `IsWholeElementRepresentable`'s XML doc and `Whole_outer_entity_form_still_declines_cleanly_in_every_mode` above). **(EF-347 Task 4 extends this SAME gate + `IsWholeElementRepresentable` to admit a REFERENCE-kind whole-inner result too — superseding the "REFERENCE-kind whole-inner result... still declines" wording that used to appear at this point; see the dedicated Task 4 note below.)** **Mechanism:** the lowerer emits `$unwind(includeArrayIndex: true)` then `$replaceRoot($mergeObjects)` (`MongoReplaceRootStage`) so the unwound owned element becomes the ROOT document, with the owner's key and the array ordinal merged in under sentinel fields `MongoReplaceRootStage.OwnerKeyField` (`"__ownerKey"`) / `.OrdinalField` (`"__ord"`) — carried along so the owned key can still materialize non-null (EF Core's own no-tracking null-owned-key guard would otherwise reject a partially-null owned key). `MongoShapedQueryCompilingExpressionVisitor.VisitShapedQuery` (`Visitors/MongoShapedQueryCompilingExpressionVisitor.cs`) checks `mongoQueryExpression.Select.UnwindSource is { WholeElement: true }` **before** its ordinary `projectedEntityType == null` fallback branch (load-bearing for a SHARED-TYPE owned element: `FindEntityType(clrType)` returns `null` for a CLR type reused by multiple owners, but `UnwindSource.InnerEntityType` — the binder's own `navigation.TargetEntityType` — is correct regardless) and roots the STANDARD `MongoProjectionBindingRemovingExpressionVisitor` at the owned element's `IEntityType` (not the owner's), forcing the DOM shaper (`allowStreaming: false` — collection elements are streaming-ineligible regardless, and `StreamingEligibility` would otherwise wrongly evaluate against the OUTER root). No new shaper type: this is the SAME projection-binding-removing visitor every whole-entity root query uses, just constructed with a different root entity type. `CreateGetValueExpression` (`Visitors/MongoProjectionBindingRemovingExpressionVisitor.cs`) reads the owned key back from the sentinel fields directly — gated on `entityType == _rootEntityType`, which is true only in this re-rooted case (the query root, `CollectionExpression.EntityType`, is always a document-root type, never an owned type) — reading the ordinal sentinel as `long` (`includeArrayIndex`'s BSON type) and converting, and the owner-key sentinel at the property's own CLR type. **Mandatory `AsNoTracking()`, and why:** a TRACKING query for this shape still throws — now `InvalidOperationException`, EF Core's OWN "owned entities cannot be tracked without their owner" guard (fires at shaper-materializer-injection time, BEFORE the native-vs-fallback split has any bearing), not a provider-authored guard — see `Bare_SelectMany_tracking_query_throws_InvalidOperationException_in_every_mode`. The provider does nothing to force `AsNoTracking()`; it is EF Core's existing contract for owned entities projected without their owner, applying here exactly as it would to any other bare-owned-entity projection. **No driver-LINQ oracle:** the same shape crashes the "graceful" fallback with the identical internal `KeyNotFoundException("...'bsonDoc'...")` the pre-existing decline note above documents, so this shape (like reference SelectMany and Intersect/Except) is proven via `MongoQueryMode.NativeOnly` succeeding plus an expected-in-memory-result-set assertion, not `Native == DriverLinq` parity — see `Bare_owned_whole_inner_element_goes_native_all_three_spellings`/`..._owner_with_zero_items_contributes_no_rows`/`..._reads_root_relative_not_owner_scoped`. **Shared-type owned collections** (one owned CLR type reused by multiple owners/navigations) also go native via this mechanism — see `Bare_owned_whole_inner_element_over_shared_clr_type_goes_native`. **`IsWholeElementRepresentable`** (`Query/Visitors/MongoQueryableMethodTranslatingExpressionVisitor.cs`) narrows acceptance with two empirically-found guards, each a clean decline rather than silent corruption or a confusing crash: (1) `!innerEntityType.GetNavigations().Any()` — a NESTED owned reference/collection under the element does not materialize correctly (the re-rooted element shaper still binds through the query's ROOT `ProjectionMember`, which resolves to the OUTER/owner entity's own `EntityProjectionExpression`, not the re-rooted element's; The trailing projection binder, `TryBindTransparentIdentifierProjection`, was generalized from 2 scopes (`ti.Outer`/`ti.Inner`) to N scopes: it counts `Outer`/`Inner` hops in a leaf's accessor chain against `UnwindSources.Count` to resolve `ti.Outer.Outer.<m>` (root/owner), `ti.Outer.Inner.<m>` (level-1 scope, `_lookup_Mids` prefix), and `ti.Inner.<m>` (level-2 scope, `_lookup_Leaves` prefix) — byte-identical for the existing N=1 (single-level) shapes, proven by the pre-existing 2-scope unit tests staying green unmodified. **Bare-entity result:** `select l` reuses the SAME whole-element gate the single-level reference bare-entity note documents (`IsWholeElementRepresentable`, keyed off the `UnwindSource` shim — now the LAST/level-2 source) with NO code change. **No driver-LINQ oracle** (same as every reference SelectMany), so every accepted shape is proven via `MongoQueryMode.NativeOnly` succeeding plus an expected in-memory result set, and every decline hard-fails in EVERY mode (`Native`/`DriverLinq`/`NativeOnly`). **Still deferred/declines cleanly:** three-or-more levels of nesting (the THIRD SelectMany's own carve-out check, `IsSingleReferenceUnwindTerminalOnly`, is `false` once `UnwindSources.Count == 2`, so it falls straight to the unmodified `HasTerminalOperator` guard); owned or mixed nesting (owned-in-owned, owned-in-reference, reference-in-owned); any inner `.Where` filter or correlation-beyond-FK on either level (the binder matches only the exact unfiltered single-`Where` spike shape — an outer `Where` layer wrapping the FK correlation, the filtered-inner shape, does not match and declines structurally); a computed projection leaf; and the whole-OUTER shape at either level (`select o` / `select m`), which still declines via the unchanged whole-outer guard. **Multi-version:** no `#if` — identical EF8/EF9/EF10 behavior. > **Filtered inner-element OWNED `SelectMany` (EF-347).** Native now ALSO covers an OWNED-collection `SelectMany` whose collection selector carries a **user filter on the inner element only** — the projected inner-`Select` form (`o.Items.Where(i => i.Price > 6).Select(i => new {o.Name, i.Price})`), the projected explicit-result-selector / query-syntax form (`SelectMany(o => o.Items.Where(pred), (o, i) => new {...})`), the **bare whole-element** result (`SelectMany(o => o.Items.Where(pred))`, requires `AsNoTracking()` like every bare-owned-element shape), and **stacked** `Where`s (`o.Items.Where(p1).Where(p2)`, ANDed into one conjunct) — emitting the SAME owned `$unwind` as the unfiltered slices 3–4 / bare-owned notes above, followed by a `$match` applying the user filter AFTER the unwind. **Mechanism (contrast with the reference filtered-inner note above):** an owned collection nav-expands to a **bare member access** (`o.Items`), NOT an FK-correlated subquery, so there is **no FK-correlation `Where` to isolate** and **no** `NativeCorrelationMatcher`/`TrySplitCorrelation` involved — `NativeSelectManyBinder.PeelOwnedInnerWhere` simply peels EVERY `Where` layer off the bare owned nav (each is an inner-element user filter) down to the member access, and `TryBuildOwnedInnerFilter` translates each peeled predicate against the owned target `IEntityType`, prefixes its field refs with the owned unwind path (`Price` → `Items.Price`) via the reused `MongoFieldPrefixRewriter`, ANDs them, and stores the result on the reused `MongoUnwindSource.Filter`. Both owned binders (`TryBind` for the inner-`Select` form, `TryBindBareNavUnwind` for the explicit / query-syntax / bare-element forms) call these helpers. The filter is built AFTER the projection list is validated but BEFORE any mutation, preserving the no-partial-mutation-on-decline invariant. **Lowering unchanged:** `MongoSelectLowerer.Lower`'s `Filter` `$match` block is kind-agnostic — it already emitted the `$match` after the owned `$unwind` and before `$replaceRoot`/`$project`, so it needed NO logic change (only a comment correction). **Driver-LINQ oracle depends on the PROJECTION shape, not the inner `Where` — true for this NON-correlated filtered-inner case specifically** (corrects an over-broad "no oracle for any filtered owned SelectMany" reading of the Task 1 spike — the spike only probed OUTER-referencing projections; the real determinant, verified by `Filtered_owned_computed_projection_leaf_falls_back_gracefully_except_under_NativeOnly`, is what the result projects; a **correlated-beyond-outer** inner filter is a different story again — it has NO oracle for ANY projection shape, uniformly, because the correlation itself is what the driver cannot translate, not the projection — see the dedicated correlated-beyond-outer note below): the C# driver's LINQ v3 provider CANNOT translate a filtered owned SelectMany whose result references the OUTER entity (`(o, i) => new {o.Name, i.Price}` — a cross-scope owner flatten it does not support for an owned collection) or returns the whole element (`select i` — the `'bsonDoc'` crash the bare-owned note documents), so those shapes have **no oracle** and are proven via `MongoQueryMode.NativeOnly` succeeding + an expected-in-memory-result-set assertion (no `Native == DriverLinq` parity); but it CAN translate one whose projection reads ONLY the inner element (`(o, i) => new {X = i.Price * 2}` flattens to `Items.Where(...).Select(i => i.Price * 2)`), so that shape HAS a working oracle. The inner `Where` alone never removes the oracle. **Decline disposition, for the remaining (non-correlated) declines, also depends on the projection:** a decline whose projection is outer-referencing (or bare whole-element) hard-fails in **every** mode (`TranslateSelectMany` returns null, no fallback to land on) — a **computed/unsupported** inner operator (`i.Name.ToUpper() == "..."`, `TryTranslate` returns false) hard-fails because its test pairs the declined filter with an outer-referencing projection (`new {o.Name, i.Price}`); whereas a decline whose projection is inner-only (e.g. a **computed projection leaf** `new {X = i.Price * 2}` the trailing `TryBindTransparentIdentifierProjection` rejects) falls back **gracefully** — `Native`/`DriverLinq` return the CORRECT computed values, only `NativeOnly` throws. **A correlated-beyond-outer filter (`i.Name != o.Name`) is NO LONGER a decline at all** — a later EF-347 slice turned the `ReferencesParameter` check that used to reject it here into a router instead (load-bearing identity-not-name routing, same hazard the guard always flagged: `Item.Name` deliberately shadows `Owner.Name`) — see the dedicated correlated-beyond-outer note below, which also explains why THAT shape's disposition does NOT depend on the projection (uniform hard-fail on decline, for every projection shape — no oracle for the correlation itself, unlike the non-correlated case documented in this note). See `NativeSelectManyTests.Inner_select_form_filtered_goes_native`/`Explicit_result_selector_form_filtered_goes_native`/`Filtered_owned_selectmany_emits_match_after_unwind_before_project` (MQL asserts `$unwind`+`$match`+`Items.Price`)/`Bare_owned_whole_inner_element_filtered_goes_native`/`Filtered_owned_stacked_where_ands_together_goes_native`/`Filtered_owned_excluding_all_children_contributes_no_rows`/`Filtered_owned_composes_with_parametrized_outer_predicate`; the hard-fail decline `Filtered_owned_computed_operator_hard_fails_in_every_mode`; and the graceful-fallback decline `Filtered_owned_computed_projection_leaf_falls_back_gracefully_except_under_NativeOnly`. **Multi-version:** no `#if` — identical EF8/EF9/EF10 behavior (all touched types `internal`). **Still deferred (not native):** a computed projection leaf (declines — falls back gracefully, per the test above) and a nested owned `SelectMany`.

> **Correlated-beyond-outer OWNED `SelectMany` (EF-347).** Native now ALSO covers an OWNED-collection `SelectMany` whose inner filter reaches PAST the owner/element pair into the OUTER entity — `q.SelectMany(o => o.Items.Where(i => i.Name == o.Name), (o, i) => new {o.Name, i.Price})` — for the projected inner-`Select` and explicit-result-selector/query-syntax forms, a **bare-whole-element** result (`SelectMany(o => o.Items.Where(pred))`, still requires `AsNoTracking()`), **stacked** `Where`s, and comparison/arithmetic breadth on the correlated pair — emitting the SAME owned `$unwind` as the unfiltered/filtered-inner notes above, followed by a `$match` whose correlated conjunct renders as `$expr`. **Mechanism — the guard becomes a router, same pattern as the reference form's correlated-beyond-FK note above:** `TryBuildOwnedInnerFilter` gained an `outerEntityType` parameter, and its existing `ReferencesParameter(userPredicate.Body, outerParam)` check — previously (implicitly) a path that would mis-scope or that the filtered-inner note's tests paired only with a hard-fail — is now the signal that ROUTES a peeled owned inner-`Where` layer to a two-scope `MongoExpressionTranslator(innerEntityType, outerParam, outerEntityType, unwindPath)` instead of the ordinary single-scope translate + blanket-prefix path; an inner-only layer keeps that existing path unchanged. Both owned binders (`TryBind`, the inner-`Select` form, and `TryBindBareNavUnwind`, the explicit/query-syntax/bare-element forms) reach this same helper, so all owned result shapes are covered by one shared change. **Identity, not name, decides scope:** exactly as in the reference form, `ReferencesParameter` matches by `ReferenceEquals` against the outer `SelectMany` parameter, never by member name — a member rooted on the outer parameter resolves against `outerEntityType` at document ROOT (`$Name`); every other member resolves against the owned target entity type with the unwind path prefixed (`$Items.Name`) — so `Item.Name` and `Owner.Name` (the test fixture's `Item`/`Owner` classes both declare a `Name` property specifically to prove this) never conflate. The two-scope result is used directly, NOT blanket-prefixed by `MongoFieldPrefixRewriter` (that rewriter is for single-scope inner-only conjuncts only). **Lowerer/renderer UNCHANGED:** the correlated conjunct is stored on the SAME `MongoUnwindSource.Filter` field the filtered-inner note introduced, and `MongoSelectLowerer.Lower`'s `UnwindSource` block emits it as a `$match` stage the SAME way it always has (`if (unwind.Filter is { } filter) stages.Add(new MongoMatchStage(filter))`, ~MongoSelectLowerer.cs:135) — in the owned case this `$match` sits after the owned `$unwind` (there is no `$lookup`/`AppendLookupStages` involvement at all for an owned nav); rendering goes through the existing dialect-mixing `MongoQueryLanguageRenderer`, unmodified, so `$Items.Name` vs `$Name` renders as `$expr` with no renderer change needed. **Uniform hard-fail, no oracle for ANY projection shape — this is the key contrast with the NON-correlated filtered-inner note above:** a spike (EF-347, this slice) confirmed that a correlated-beyond-outer owned filter has **no driver-LINQ oracle regardless of what the result projects** — inner-only, outer-referencing, and bare-whole-element projections ALL fail identically, because it is the CORRELATION itself (not the projection shape) that the driver's LINQ v3 provider cannot translate for an owned collection. This differs from the non-correlated filtered-inner case, where an inner-only projection DOES have a working oracle (see that note's "Driver-LINQ oracle depends on the PROJECTION shape" paragraph, now scoped to the non-correlated case only). Every decline (a computed/unsupported inner operator, e.g. `i.Name.ToUpper() == o.Name`) hard-fails in **every** mode (`Native`/`DriverLinq`/`NativeOnly`) — there is no fallback to land on — so success for every accepted shape is proven via `MongoQueryMode.NativeOnly` succeeding plus an expected-in-memory-result-set assertion, not `Native == DriverLinq` parity. **Known interaction (EF-221):** the correlated field-to-field comparison inherits the provider's existing, intentional value-equality semantics for mismatched-CLR-type comparisons, exactly as the reference form's correlated-beyond-FK note documents — not a new guard, and purely additive (the shape hard-failed in every mode before this slice). **Multi-version:** no `#if` — identical EF8/EF9/EF10 behavior. See `NativeSelectManyTests.Owned_correlated_beyond_outer_inner_select_form_goes_native`, `Owned_correlated_beyond_outer_explicit_form_goes_native`, `Owned_correlated_beyond_outer_bare_whole_element_goes_native`, `Owned_correlated_beyond_outer_stacked_where_goes_native`, `Owned_correlated_beyond_outer_excluding_all_children_contributes_no_rows`, `Owned_correlated_beyond_outer_composes_with_parametrized_outer_predicate`, and `Owned_correlated_beyond_outer_emits_expr_match_after_unwind` (MQL asserts `$unwind`+`$match`+`$expr`+`Items.Name`+`$Name`).

> **Native SelectMany computed-leaf (EF-347).** Native now ALSO covers a **single-scope** numeric-arithmetic (`+ - * / %`) computed leaf in a SelectMany's TRAILING projection — e.g. `SelectMany(o => o.Items, (o, i) => new { X = i.Price * 2m })` — for every form whose real projection binds through `NativeSelectManyBinder.TryBindTransparentIdentifierProjection` (the owned explicit-result-selector/query-syntax form, the owned bare-nav/bare-whole-element form — same trailing-`Select` bind, per the mechanism note above — a FILTERED owned inner, the reference form, and the nested (2-level) reference form). **Mechanism:** `TryBindTransparentIdentifierProjection`'s per-leaf loop gained a second acceptance branch — when a leaf is not a plain scope-rooted `MemberExpression` (the pre-existing bare-member branch), it now also accepts a `BinaryExpression` whose `NodeType` is arithmetic (`Add`/`Subtract`/`Multiply`/`Divide`/`Modulo`) via the new private `TryTranslateSingleScopeComputedLeaf` helper — anything else (a non-arithmetic method call, string concat, etc.) still falls straight to the existing `return false`. **`ScopeRerootingVisitor`:** an `ExpressionVisitor` that rewrites EVERY scope-rooted `ti.Outer…`/`ti.Inner…` member access found anywhere in the leaf onto that scope's synthetic per-scope parameter (`scopeParams[scope]`, the SAME array `TryBindTransparentIdentifierProjection` already builds — one per `UnwindSources` level plus the root), using the SAME `TryResolveScopeDepth` the bare-member branch already relies on — so scope is resolved by COUNTING `Outer`/`Inner` hops (depth), never by member name; a member access that is not itself scope-rooted (a captured local, a constant) is left untouched via `VisitMember`'s `base.VisitMember` fallthrough. It records the single `ResolvedScope` seen and sets `CrossScope` the moment a SECOND, DIFFERENT scope is encountered (e.g. `o.Threshold * r.Score` — an outer-rooted operand alongside an inner-rooted one). **Gate:** `TryTranslateSingleScopeComputedLeaf` declines (returns `false`, with NO mutation of `mongoQ`) when `CrossScope` is set or no scope was resolved at all — a genuinely cross-scope leaf is a DEFERRED follow-on, not a silently-wrong translation: the whole projection declines exactly like any other `TryBindTransparentIdentifierProjection` rejection (see `Cross_scope_computed_leaf_declines_and_hard_fails_in_every_mode`). **Reuse, not new machinery:** on a single resolved scope, the re-rooted subtree is handed to the SAME `MongoExpressionTranslator.TryTranslateValue` the plain-`Select` arithmetic note above documents — inheriting Guard A (integer-result `Divide` rejected — see `Integer_division_computed_leaf_declines_and_hard_fails_in_every_mode`) and Guard B (converter/non-default-`BsonRepresentation` operand rejected) UNCHANGED — then, for an inner scope (`scope > 0`), the translated result is prefixed onto the unwind path via `MongoFieldPrefixRewriter.Rewrite(computed, sources[scope - 1].InnerScopePath)` — the SAME rewriter the reference-form correlated-beyond-FK/owned correlated-beyond-outer notes above already use — exactly mirroring how the pre-existing bare-member branch prefixes a single field ref; a root-scope (`scope == 0`) leaf is used unmodified. **Nested (2-level) reference SelectMany "for free":** because `TryResolveScopeDepth`/`scopeParams`/`translators` were already generalized to N scopes by the nested-reference slice (see that note above), the computed-leaf branch needed NO further change to reach the DEEPEST scope of a two-level chain — `Nested_reference_single_scope_computed_leaf_goes_native` proves a leaf at `k=2` (`l.Height * 2`) prefixes correctly onto `_lookup_Leaves.Height` via `sources[1].InnerScopePath`. **Shaper-free:** unlike the plain-`Select` arithmetic slice, NO shaper change was needed here — a Task 1 spike confirmed the SelectMany trailing-projection shaper already reads a populated `Projection` entry back FLAT, by index, with no per-member decomposition — so there is no analogue of the `MongoProjectionBindingExpressionVisitor` `(Age*Score)²`-clobber bug the plain-`Select` note documents. **Disposition:** for the OWNED forms (explicit/query-syntax, bare-nav, filtered-inner) — which DO have a driver-LINQ oracle for an inner-only-or-mixed projection, per the earlier owned-SelectMany notes — the tests assert `Native == DriverLinq` parity across all three `MongoQueryMode`s (`Explicit_result_selector_form_computed_arithmetic_leaf_goes_native`, `Two_field_single_scope_computed_leaf_goes_native`, `Mixed_member_and_computed_leaf_projection_goes_native`, `Filtered_owned_computed_arithmetic_leaf_goes_native`); for the REFERENCE and nested-reference forms — which have NO driver-LINQ oracle at all (a cross-collection `SelectMany` is rejected outright by the driver's own LINQ v3 provider, per the slice-5 note above) — the tests instead prove success via `MongoQueryMode.NativeOnly` succeeding plus an expected-in-memory-result-set assertion (`Reference_form_computed_arithmetic_leaf_goes_native`, `Nested_reference_single_scope_computed_leaf_goes_native`). **Multi-version:** no `#if` — identical EF8/EF9/EF10 behavior (all touched types `internal`). **Deferred, precisely:** a CROSS-SCOPE leaf (e.g. `o.Discount * i.Price`, `o.Threshold * r.Score`) — `ScopeRerootingVisitor.CrossScope` declines it and the whole projection falls through to whatever that form's normal decline disposition already is (hard-fail in every mode for the reference/no-oracle forms — see `Cross_scope_computed_leaf_declines_and_hard_fails_in_every_mode` — graceful fallback for an owned form with an oracle); the INNER-`Select` form's own SEPARATE `TryBind` binder — untouched by this slice, still structurally rejects any computed leaf nested inside the collection selector itself, unconditionally, in every mode (`Computed_leaf_hard_fails_in_every_mode`) — only the TRAILING-projection binder (`TryBindTransparentIdentifierProjection`, reached by the explicit/bare-nav/filtered/reference/nested forms) gained this branch; the non-arithmetic long tail (string transforms, date-part extraction, `Math.*`, type-changing casts) — unaffected, `TryTranslateValue` rejects them exactly as it does for a plain `Select`; and an integer-result `Divide` — guarded out by the REUSED Guard A, same non-truncating-`$divide`-vs-truncating-C#-division divergence the plain-`Select` note's "Integer division — corrected disposition" paragraph explains, with the identical `TruncationException`-in-every-materializing-mode consequence for the reference/no-oracle forms (`Integer_division_computed_leaf_declines_and_hard_fails_in_every_mode`).

> **Owned single-reference whole-entity queries (EF-322 Task 2).** Native now also covers a whole-entity query over an entity with an owned SINGLE-REFERENCE navigation (`OwnsOne`, possibly nested, e.g. `Blog { Address { Geo } }`) — previously this ALWAYS fell back to driver-LINQ. **Root cause:** owned navigations are always eager-loaded by EF Core convention, so EF's nav-expansion auto-injects a synthetic `Select(x => IncludeExpression(x, ownedNav))` for the auto-include; that `Select`'s body is an `IncludeExpression`, which matched none of `TranslateSelect`'s existing pass-through predicates (`IsTransparentIdentifierSelector`/`IsSingleLevelCollectionIncludeSelector`/`IsTransparentIdentifierMemberAccessSelector` — the last of these requires a COLLECTION, non-embedded navigation, the opposite of an owned single-ref), so it fell into the projection else-branch, `NativeProjectionBinder.TryPopulateNativeProjection` rejected the `IncludeExpression` body (not an anonymous/DTO construction), and the query was marked `MarkNotNativelyRepresentable()` → `Route = Fallback`. **Fix:** a new predicate, originally named `IsOwnedEmbeddedReferenceIncludeSelector` and since generalized/renamed to `IsOwnedEmbeddedIncludeSelector` (`Visitors/MongoQueryableMethodTranslatingExpressionVisitor.cs`, added to the `TranslateSelect` pass-through guard alongside the three above), recognizes a selector body that is a chain of one-or-more `IncludeExpression` layers where EVERY navigation is `IsEmbedded()` and the innermost `EntityExpression` is the lambda's own parameter — i.e. one or more nested owned navigations auto-included off the root, in any order/depth. When it matches, the `Select` is left alone (no projection populated, not marked non-representable) and falls through to the ordinary whole-entity shaper fold, so `Route` stays `WholeEntity`. **No pipeline/lowerer/shaper changes were needed** — owned data is embedded in the same document as its owner, so the existing whole-entity DOM **and** one-pass streaming shapers already read it back correctly; only the gate was rejecting the shape. **Deliberately narrow — what stays excluded, unchanged:** a non-owned/reference navigation (`!navigation.IsEmbedded()` — single-level reference `Include` has no native representation yet), an owned sub-property predicate/projection (`Where(e => e.Address.City == ...)`, `Select(e => new { e.Address.City })` — a different code path, `MongoExpressionTranslator`/`NativeProjectionBinder`'s own member-rooted-on-parameter requirement, untouched by this predicate), and a TPH hierarchy that also owns a single reference (no special-case needed: it already routes native via the **DOM** shaper, same as plain TPH — `StreamingEligibility` independently excludes TPH from the *streaming* decision). **At Task 2 time an owned COLLECTION navigation in the chain (`OwnsMany`) was still excluded** — the predicate originally also required `!IsCollection` on every layer, rejecting the shape as a WHOLE (including a chain mixing an owned collection with an owned reference, e.g. `OwnsOne(ShipTo)` + `OwnsMany(Lines)` on the same entity). **That restriction was subsequently dropped** — see the dedicated "Owned-collection whole-entity queries (EF-322)" note immediately below, which covers the gate generalization to admit collections, the companion `StreamingEligibility` narrowing it required, and the streaming-vs-DOM split for that shape; an owned collection now also goes native. See `NativeOwnedReferenceWholeEntityTests` and the EF-322 Task 1 spike doc, `.superpowers/sdd/EF-322-owned-ref-whole-entity-spike.md`, which found this exact gate site and admit condition and verified zero spec flips / zero regressions before implementation.

> **Owned-collection whole-entity queries (EF-322).** Native now also covers a whole-entity query over an entity with one or more owned COLLECTION navigations (`OwnsMany`, e.g. `Blog { List<Post> Posts }`), possibly mixed with owned single-references and/or nested — previously this ALWAYS fell back to driver-LINQ, exactly like the owned single-reference shape before Task 2. **Root cause:** identical mechanism to the single-reference case above — the owned-collection auto-include lowers to the SAME plain `IncludeExpression { Navigation, EntityExpression: param }` chain shape, but the Task 2 predicate's `!navigation.IsCollection` clause rejected any layer whose navigation was a collection, so the chain fell through to `MarkNotNativelyRepresentable()` → `Route = Fallback` exactly as an unrecognized shape would. **Fix (two small pieces, confirmed end-to-end by the Task 1 spike, `.superpowers/sdd/EF-322-owned-collection-whole-entity-spike.md`, before being made permanent):** (1) **Gate.** The predicate was renamed `IsOwnedEmbeddedReferenceIncludeSelector` → `IsOwnedEmbeddedIncludeSelector` and its `IsCollection` rejection dropped — it now admits an `IncludeExpression` chain where EVERY navigation is `IsEmbedded()` (collection OR reference) and the innermost `EntityExpression` is the lambda parameter, so a mixed owned-ref + owned-collection chain is admitted as a WHOLE; `Route` stays `WholeEntity`. (2) **Streaming eligibility narrowing.** `StreamingEligibility.IsEligible`'s collection-element guard was narrowed from `.Any(n => n.IsCollection)` to `.Any()` — a collection whose element itself carries ANY navigation (a nested owned single reference just as much as a nested collection) is now streaming-INELIGIBLE, routing it to the native DOM shaper instead. Reason: the streaming rewriter's forward-only reader has no `IncludeExpression` case for a collection element (`FindCollectionShaper` cannot descend into one), so without this narrowing a collection-of-owned-ref-elements would be (wrongly) attempted as streaming and throw `NativeTranslationNotSupportedException` at shaper-compile time — caught-and-fallback under `Native`, but propagating under `NativeOnly`, i.e. NOT natively representable even though the gate alone says it should be. **No pipeline/lowerer/renderer/rewriter LOGIC change was needed** — the native `{}` pipeline already returns the embedded array as part of the document, and `StreamingEligibility` + `MongoStreamingEntityMaterializerRewriter.BuildPlan` already had code to admit and build owned collections; their doc-comments were simply stale (claiming collections were unsupported/still-falling-back) and have been corrected in place, not rewritten. **Streaming-vs-DOM split:** flat, mixed (owned-ref + owned-collection), shared-CLR-type, and empty owned collections **stream** via the SP7 one-pass materializer (root = the owner entity, per the note below); a collection element that itself owns a further navigation ("nested-in-element") and a collection-of-collections both route to native **DOM** instead, per the eligibility narrowing above. Both the streaming and DOM shapes were verified to materialize correctly with `Native == DriverLinq` parity across the full edge matrix (empty, populated with order preserved, nested-in-element, mixed, shared-CLR-type, collection-of-collection, and tracked round-trip). **Stays excluded, unchanged:** a non-owned/reference collection `Include` (still the separate `$lookup` path, untouched by this slice); an owned-collection SUB-PROPERTY predicate/projection (`Where(e => e.Posts.Count > 3)`, `Select(e => e.Posts.Count)` — a different code path, unaffected); and a TPH hierarchy that also owns a collection (already routes native via the DOM shaper, same as plain TPH, unaffected by this slice). **Not a break, functional-only flip:** per the versioning rubric (top of this file), a fallback → native transition with unchanged results is not a breaking change; the EF10 `NativeOnly` spec sweep is unchanged (Northwind has no owned-collection whole-entity coverage, so nothing there changes routing). Flipped: two `NativeOwnedReferenceWholeEntityTests` assertions that asserted the old fallback (owned-collection, and mixed owned-ref + owned-collection) now assert native routing + parity instead, and a stale "STILL falls back" note in `NativeMaterializerOnePassTests.Owned_reference_and_owned_collection_materialize_correct_nested_values` was corrected to reflect that the mixed shape now streams.

> **Owned single-reference sub-property dotted-path predicates/sorts/projections (EF-322 Tasks 2–3).** Native now also covers a predicate, sort key, or projection leaf that reaches THROUGH one or more owned single-reference (`OwnsOne`) navigations to a scalar leaf property — `Where(e => e.Home.City == "NYC")`, `OrderBy(e => e.Home.Geo.Country)`, `Select(e => new { e.Name, e.Home.City })` — previously these ALWAYS fell back to driver-LINQ, because a member rooted on anything other than the query parameter (or an `EF.Property` hop) fell outside `TryResolveMember`'s single-hop fast path. **Mechanism:** a new resolver, `MongoExpressionTranslator.TryResolveOwnedFieldPath`, is delegated to from `TryResolveMember`'s fallback branch (any member-access node that is NOT a plain `param.Foo` shape) — the single shared gate (`TryResolveMember`/`TryTranslateField`) that both the predicate/sort path and `NativeProjectionBinder.TryTranslateLeaf` already call, so all three surfaces (predicate, sort key, projection leaf) picked up the new resolution for free with no separate per-surface wiring. The resolver walks the access chain outer-to-inner accepting either a `MemberExpression` hop or an `EF.Property(root, "Nav")` call (the shadow-nav-safe form EF's nav-expansion sometimes produces), requires the chain to be rooted at the query parameter, requires every non-leaf hop to resolve to an `IsEmbedded()`, non-collection navigation (an owned COLLECTION intermediate, or a cross-collection/reference nav, declines the whole chain), and requires a mapped scalar `IProperty` leaf. On success it builds the dotted document path from `scopeType.GetDocumentPath()` (root-relative containing-element names) + `leaf.GetElementName()` — the same path convention the whole-entity owned shaper already reads. **Single-scope only:** the resolver declines outright (`_outerParam is not null || _innerPrefix is not null`) in two-scope mode (a `SelectMany`-unwind translator) — `GetDocumentPath()`'s root-relative path does not compose with unwind-scope prefixing, so a two-scope owned dotted access is deferred, not supported. **Composite-PK decline:** mirrors the existing single-hop guard in `TryResolveMember` — a leaf that is itself a component of a composite primary key is stored nested under `_id` and is not addressable by its own top-level element name, so `IsPrimaryKey() && FindContainingPrimaryKey()!.Properties.Count > 1` declines and the query falls back rather than emit a `$match`/`$sort`/`$project` against a non-existent field. **Projection converter guard (closes a DOM-shaper raw-read divergence):** `NativeProjectionBinder.TryTranslateLeaf` separately declines a projection leaf whose resolved `MongoFieldExpression.ElementName` contains a `.` (i.e. an owned dotted path, not a top-level field) AND whose property lacks default serialization (`NativeGroupByBinder.HasDefaultKeySerialization` reused as-is — flags a value converter or a non-default `BsonRepresentation`) — the DOM shaper's field-access resolver is single-hop and cannot apply a converter across a nested owned chain, so an unguarded value-converted owned leaf would read back the RAW stored value instead of the converted CLR value (verified live: `NativeOwnedSubPropertyTests.Converted_owned_subproperty_projection_matches_driver_linq`). This guard is projection-only — a top-level (non-dotted) leaf already round-trips converters correctly and is unaffected; the predicate/sort path has no analogous read-back step (a `$match`/`$sort` field-ref is compared/sorted server-side, never deserialized into a CLR value) so it needs no equivalent guard. **Deferred (out of scope for this slice):** an owned-COLLECTION sub-property access that is NOT an `Any` quantifier — e.g. an array-projection of a collection sub-property (`Select(e => e.Posts.Select(p => p.Title))`) — the intermediate-navigation guard above declines any collection hop, so these still fall back (an `Any` quantifier over the same collection, e.g. `Where(e => e.Posts.Any(p => p.Title == ...))`, is a DIFFERENT resolver and now DOES go native — see the dedicated "Owned-collection `Any` quantifier predicates" note below); a two-scope (cross-scope, inside a `SelectMany`) owned dotted access; and a BARE-SCALAR trailing projection of an owned leaf (`Select(e => e.Home.City)` — the pre-existing bare-scalar projection limitation, unrelated to this slice, still applies). See `NativeOwnedSubPropertyTests` and `NativeGateRoutingTests` Shape B for the routing/parity coverage. **Not a break, functional-only flip; spec sweep unchanged:** per the versioning rubric (top of this file), fallback → native with unchanged results is not a breaking change; the EF10 `NativeOnly` spec sweep is unchanged end-to-end (4589 pass/0 fail/19 skip under `Native`, 2192 pass/2397 fail/19 skip under `NativeOnly` — identical to the pre-slice baseline, because Northwind has no owned sub-property predicate/sort/projection coverage). Flipped: `NativeGateRoutingTests.B_owned_subproperty_where_equals_routing`, `.B_owned_subproperty_order_by_routing`, and the renamed `.B_owned_subproperty_projection_now_goes_native` now assert native routing instead of the old fallback (done in Task 2; no further test flips were found — see Task 4's grep sweep).

> **Owned-collection `Any` quantifier predicates (EF-322).** Native now also covers an existential quantifier over an owned (embedded) collection navigation — `Where(b => b.Posts.Any())`, `Where(b => b.Posts.Any(p => p.Heading == "x"))`, negated forms (`!b.Posts.Any(...)`), nested `Any`-within-`Any` (`b.Posts.Any(p => p.Comments.Any(c => ...))`), and a collection reached through one or more owned single-reference hops (`b.Home.Notes.Any(...)`) — previously these ALWAYS fell back to driver-LINQ. **Rendering:** a predicated `Any` renders to `$elemMatch` (`{ArrayPath: {$elemMatch: {...}}}`, or `{ArrayPath: {$not: {$elemMatch: {...}}}}` when negated); a bare `Any()` renders as an array-index existence test (`{"path.0": {$exists: true}}`, `false` when negated) rather than `{$ne: []}` — the index form is correct for BOTH an empty array and a MISSING/explicit-`null` field (none of those has an index-0 element), which `{$ne: []}` would get wrong for the missing/null cases. **Mechanism:** a new AST node, `MongoElemMatchExpression` (`ArrayPath`/`ElementPredicate`/`Negated`), recognized by `MongoExpressionTranslator.TryMatchQuantifierMethod` (**renamed from `TryMatchAnyMethod`** when the owned-collection `All` slice generalized it to report which quantifier matched — see the dedicated `All` note below; it matches `Enumerable.Any`/`Queryable.Any` in the 1-arg bare or 2-arg predicated form, unwrapping an optional `Quote` around the lambda and an optional `AsQueryable()` around the source via `UnwrapAsQueryable`) and resolved by the new `TryResolveOwnedCollectionPath`. **Correction to this note's original tree-shape claim, which was an overreach:** it said the quantifier is "empirically always the `Queryable` overload, 1-arg bare or 2-arg with a `Quote`-wrapped lambda, source always wrapped in exactly one `AsQueryable()` call inserted by EF's own normalization". That holds for an owned-**entity** collection quantifier, but **not** universally — a PRIMITIVE-element collection quantifier arrives as `Enumerable.All(<MemberAccess>, <bare unquoted lambda>)`, i.e. the `Enumerable` spelling, an UNQUOTED lambda, and **no `AsQueryable()` wrapper at all** (spike-measured; see the `All` note below and `NativeOwnedCollectionAllTests.Primitive_collection_All_with_equality_reaches_the_matcher_and_declines_at_path_resolution`). So both unwraps in `TryMatchQuantifierMethod` are genuinely CONDITIONAL rather than belt-and-braces, and its `declaringType != typeof(Enumerable) && declaringType != typeof(Queryable)` check accepts `Enumerable` as a first-class case, not as defence-in-depth. `UnwrapAsQueryable` returns an unwrapped source unchanged, which is what makes the primitive shape a clean decline one step later rather than a crash, then rendered by `MongoQueryLanguageRenderer.RenderElemMatch` for the PREDICATED form. **Correction — the bare-`Any()` mechanism, superseded by the later `.Count`-in-a-predicate slice:** this note originally described bare `Any()` as ALSO producing a `MongoElemMatchExpression` (with a `null` element predicate) and rendering through `RenderElemMatch`. That is no longer how it works: bare `Any()` is now represented as `Count >= 1` — a `MongoBinaryExpression(GreaterThanOrEqual, MongoSizeExpression(arrayPath, nullSafe: true), 1)` — rendered by `MongoQueryLanguageRenderer.TryRenderSizeComparison`'s array-index form, one representation for array cardinality instead of two, and `MongoElemMatchExpression.ElementPredicate` is consequently NON-NULLABLE (it no longer needs to represent an absent predicate). The emitted MQL is UNCHANGED (`{"path.0": {$exists: true}}`, `false` when negated) — see the dedicated `.Count` note below for the full mechanism and the negator implication. A negated form flips `Negated` in place inside the pre-existing `Not` arm of `TranslateNode` (mirroring how `!Contains`/`!StartsWith` flip their own node's `Negated` flag) rather than wrapping in a generic `Not` node. The element predicate is translated by a FRESH, element-scoped `MongoExpressionTranslator(elementType)` — so its field paths come out ELEMENT-relative, exactly what `$elemMatch` requires — and that same element-scoped translator is what makes a nested `Any`-within-`Any` correct: the inner quantifier's own array path resolves relative to the OUTER element (`Comments`), not the document root (`Posts.Comments`). **The scope-relative path decision, and why it differs from the sibling `TryResolveOwnedFieldPath` (the dotted-path scalar resolver, immediately above):** that resolver builds its path from `GetDocumentPath()` — always relative to the TRUE document root — so it declines both in two-scope mode (`_outerParam is not null || _innerPrefix is not null`) AND, separately, whenever its own translator is not built on the document root (`!_entityType.IsDocumentRoot()`, a guard added in the previous slice specifically to stop a root-relative path double-prefixing when the translator is built on a non-root scope, e.g. an owned-collection element type). `TryResolveOwnedCollectionPath` instead joins each hop navigation's own `GetContainingElementName()`, so the resulting path is relative to the TRANSLATOR'S OWN scope type by construction — which composes correctly with `MongoFieldPrefixRewriter` PREPENDING a further prefix (rather than fighting it), and is exactly what lets a nested `Any`'s inner array path resolve to `Comments` (element-relative) rather than `Posts.Comments` (root-relative, which the enclosing `$elemMatch` does not expect). Relativizing the sibling scalar resolver the same way is an open follow-on that would supersede its blanket decline. Two-scope mode (inside a `SelectMany` unwind translator) is still declined outright (`_outerParam is not null || _innerPrefix is not null`) — a cross-scope quantifier is out of scope for this slice. **`MongoFieldPrefixRewriter` invariant:** its `MongoElemMatchExpression` case prefixes `ArrayPath` ONLY (`prefix + "." + e.ArrayPath`) and passes `ElementPredicate` through untouched — the element predicate is element-relative by construction, and rewriting it would mis-address every field inside the `$elemMatch`. **`IsQueryDialectRenderable` must stay in sync with `RenderNode`, and this is a CORRECTNESS gate, not an index preference:** `$expr` is not usable inside `$elemMatch` (`Command find failed: $expr can only be applied to the top-level document`), so `TryMatchQuantifierMethod`'s caller declines at translate time (no query built, clean fallback) whenever the translated element predicate is not query-dialect-renderable — a node that slipped through would make the WHOLE query throw at execution time, under `Native` as well as `NativeOnly`, not just fail to use an index. **Emergent new capability (spike-confirmed, now test-covered):** an owned `SelectMany` whose inner filter is itself an owned-sub-collection `Any` — `SelectMany(b => b.Posts.Where(p => p.Comments.Any(c => c.Text == "t")), (b, p) => new { p.Heading })` — hard-failed in EVERY mode before this slice (no driver-LINQ oracle, and the owned inner-filter translator could not handle `Any`). The native `$elemMatch`/`"path.0": {$exists}` forms have no such limitation: a missing or null array simply doesn't match, exactly like an empty one. This is why the functional tests use two seeds — the full state-matrix seed (missing/null/empty/no-match/match) proven via `NativeOnly` routing plus hand-verified expected titles (no driver-LINQ oracle over that matrix), and a second, well-formed-only seed (the same three non-null-array rows) proven via `NativeOnly == DriverLinq` parity — see `NativeOwnedCollectionPredicateTests`. **Deferred/still falls back** (**`All` is NO LONGER on this list** — `Posts.All(p => ...)` went native in the immediately following slice; see the dedicated owned-collection `All` note below; **`.Count` used in a predicate is ALSO NO LONGER on this list** — `Posts.Count > 1` went native in the later `.Count`-in-a-predicate slice, see the dedicated note below): embedded-collection projections are a MIXED picture, corrected here — an ARITHMETIC projection leaf containing a count (`Select(b => new { X = b.Posts.Count * 2 })`) now goes NATIVE too (an unplanned incidental widening: the count is recognized as an ordinary operand, see the `.Count` note below), but the BARE form (`Select(b => b.Posts.Count)`, an array projection) is NOT "deferred" in this note's usual sense of falling back to driver-LINQ and working — it HARD-FAILS in every query mode (`ArgumentException`, from a `MongoProjectionBindingExpressionVisitor` gap) and did so on `main` long before any of this EF-322 native-query work began, so it is a pre-existing limitation, neither caused nor fixed by this work stream, now pinned by a documenting test and tracked as **EF-357**. **Corrected in place by the count-PROJECTION slice (owned-data slice 7) — the sentence above is wrong on one point and stale on another.** WRONG: by naming only the BARE form as the hard-fail, it left the anonymous-WRAPPED count (`Select(b => new { b.Title, N = b.Posts.Count })`) implicitly among the "falls back to driver-LINQ and works" shapes. > **Owned-collection `All` quantifier predicates + the shared predicate negator (EF-322, closing EF-335).** Native now also covers a UNIVERSAL quantifier over an owned (embedded) collection navigation — `Where(b => b.Posts.All(p => p.Rank > 5))`, the negated form `!b.Posts.All(...)`, nested quantifiers in EITHER order (`All`-in-`Any`, `Any`-in-`All`, `All`-in-`All`), and a collection reached through one or more owned single-reference hops (`b.Home.Notes.All(...)`) — and, at document-root scope, the **top-level `All` aggregate** (`ctx.Blogs.All(b => b.Rank > 0)`), including `&&`/`||` predicates. That root-scope half **closes ticket EF-335**, recorded as a known gap in the scalar-cardinality note above ("`All` with a comparison predicate — negating a comparison into query-native form is unsupported"). Both halves previously fell back to driver-LINQ. **Rendering, and why the enclosing form is correct for an empty/missing/null array:** `All(pred)` is true iff NO element satisfies `¬pred`, so an owned-collection `All` renders as `{"<arrayPath>": {$not: {$elemMatch: <¬pred>}}}` — e.g. `b.Posts.All(p => p.Rank > 5)` → `{Posts: {$not: {$elemMatch: {Rank: {$not: {$gt: 5}}}}}}` — and a conjunctive predicate De-Morgans into an `$or` ARRAY (`All(p => p.A == 1 && p.B > 2)` → `{Posts: {$not: {$elemMatch: {$or: [{A: {$ne: 1}}, {B: {$not: {$gt: 2}}}]}}}}`). For an EMPTY, MISSING, or explicit-BSON-`null` array nothing satisfies the `$elemMatch`, so the enclosing `$not` matches and `All` is `true` — exactly what LINQ's `All` over an empty sequence returns (EF materializes a missing embedded array as an empty list), so none of the three states needs special-casing. **No new AST node:** the pre-existing `MongoElemMatchExpression` is reused with `Negated: true`, and `!All(...)` needs no new code at all — it is the SAME `Negated` flip in `TranslateNode`'s `Not` arm that `!Any(...)` already used. `MongoExpressionTranslator.TryMatchAnyMethod` was generalized/renamed to **`TryMatchQuantifierMethod`**, additionally matching `All` and reporting which quantifier matched via the private `MongoQuantifierKind` enum; **`All` has only the 2-arg form** (there is no parameterless `All`), so the matcher explicitly rejects a 1-arg `All` rather than treating it as a bare existential. > **`MongoExpressionNegator` — the contract is EXACT COMPLEMENT OR DECLINE, never an approximation.** One new file, `NativeTranslation/MongoExpressionNegator.cs`, `internal static`, one entry point: `TryNegate(MongoExpression, [NotNullWhen(true)] out MongoExpression?)`. It is pure — no entity-type, scope, or state knowledge — and operates on the ALREADY-TRANSLATED, already-scope-resolved `MongoExpression` tree rather than the LINQ tree, so it cannot reintroduce a scoping mistake and its admitted set is a closed set of node kinds that maps one-to-one onto what the renderer can express. `AndAlso`/`OrElse` De Morgan (recursing, with a child decline propagating and producing NO partial output), `MongoInExpression`/`MongoRegexExpression`/`MongoElemMatchExpression` flip their own `Negated` flag, `MongoUnaryExpression{Not}(X)` collapses to `X` (double negation), and a bare non-nullable `bool` field becomes `Not(field)` → `{f: {$ne: true}}`. Everything else declines. **THE ONE FACT A FUTURE EDITOR MOST NEEDS: why `$eq`/`$ne` may be INVERTED while the four relational operators must be `$not`-WRAPPED.** MongoDB's relational operators are type-bracketed and match neither a missing nor an explicitly-null field, so `{Rank: {$gt: 5}}` and `{Rank: {$lte: 5}}` do **not** partition the value space — an element with no `Rank` is matched by NEITHER. Inverting `>` to `<=` would therefore render `All(p => p.Rank > 5)` as `{Posts: {$not: {$elemMatch: {Rank: {$lte: 5}}}}}`, which for a document containing an element with no `Rank` matches (nothing satisfied the `$elemMatch`) and so reports `All == true`, where LINQ evaluates `null > 5` as `false` and answers `false` — **silent wrong data, under default `Native`, on an extremely ordinary input.** `$not` over the OPERATOR DOCUMENT is the exact complement (spike-measured legal and exact inside `$elemMatch` as well as at document root, and for a foreign-BSON-type value too, which behaves like missing/null under numeric operators via type bracketing), and costs exactly one renderer arm. `$eq`/`$ne`, by contrast, DO partition every BSON value including missing and null, so for that one pair mirroring is exact — which is why the common case still renders as idiomatic `{f: {$ne: v}}` rather than `{f: {$not: {$eq: v}}}`. Confining inversion to the one pair whose mirrored form provably partitions is the entire safety argument of this slice. Unit-covered row by row, plus every decline, in `MongoExpressionNegatorTests` — see `.Equality_is_inverted_not_wrapped_because_eq_and_ne_partition`, the four `.Relational_operators_are_not_wrapped_never_inverted_*`, `.Nullable_bool_field_declines`, `.Field_to_field_comparison_declines`, `.Arithmetic_node_declines`, `.A_declining_child_declines_the_whole_conjunction_with_no_partial_output`, and `.Negation_is_an_involution_on_the_supported_set`.

> **Two domain invariants, and the sync requirement is now THREE-WAY.** (1) *Input domain* — the negator's admitted set is a SUBSET of `MongoQueryLanguageRenderer.IsQueryDialectRenderable`'s, enforced directly: `TryNegate` gates on `IsQueryDialectRenderable(node)` before dispatching, so every "not query-native" decline (field-to-field comparison, arithmetic, an unsupported `$in` values node) falls out of one check instead of being re-derived per case. (2) *Output domain* — every node the negator PRODUCES is itself admitted by `IsQueryDialectRenderable` and renders through `RenderNode` **without** falling through to the `$expr` catch-all and **without** throwing. The output invariant is the load-bearing one: this negation is emitted inside `$elemMatch`, where `$expr` is a hard server error (not a slow path), so a negator producing an `$expr`-bound node would make the whole query throw at execution time under `Native` as well as `NativeOnly`. Pinned directly by `MongoExpressionNegatorTests.Every_successful_negation_is_query_dialect_renderable_and_renders_without_expr` and `.Node_that_is_not_query_dialect_renderable_declines_even_when_its_own_case_would_flip_it`. **Consequence: `MongoExpressionNegator` ↔ `IsQueryDialectRenderable` ↔ `RenderNode` must now change TOGETHER.** The renderer file already carried the "these two must change together" contract between the classifier and `RenderNode`; the negator is a third party to it, because a node kind added to the classifier but not the negator merely loses coverage, whereas a node kind added to the negator but not correctly renderable is a hard failure at execution time.

> **`IsQueryNativeComparison` widened `private` → `internal`, and the negator must gate on it ITSELF.** `MongoQueryLanguageRenderer.IsQueryNativeComparison` (bare field on the left, constant/parameter on the right) is the single definition of "query-native", now shared with the negator rather than duplicated. The negator checks it directly rather than relying on the downstream dialect gate, and that is a correctness requirement, not a scope statement: a field-to-field comparison has NO query-dialect rendering at all, so mirroring `Equal`→`NotEqual` on one would produce a node `RenderNode` sends to the `$expr` catch-all — a hard server error inside `$elemMatch`, i.e. a runtime failure rather than a decline — and `$not`-wrapping one would produce a node the new `RenderUnary` arm throws on. (Given `TryNegate`'s `IsQueryDialectRenderable` gate the per-case check is now redundant, and is deliberately kept explicit in `TryNegateCore` because this is the one case where getting it wrong is silent wrong data.)

> **One new `RenderUnary` arm, and the two ILLEGAL MQL FORMS that make its shape mandatory rather than stylistic.** `MongoQueryLanguageRenderer.RenderUnary` gained a case for a `Not` whose operand is a query-native comparison, rendering `{<elementName>: {$not: {<op>: <value>}}}` by reusing `RenderComparison` (so element naming, value serialization, and parameter-placeholder recording are identical to the un-negated form); `IsQueryDialectRenderable` gained the matching arm; the pre-existing bare-bool-field arm and the throw-for-everything-else are untouched. Both illegal forms were found live against a real server, and both are now load-bearing constraints: (1) **`{field: {$not: <bareValue>}}` is a HARD SERVER ERROR** — *"$not argument must be a regex or an object"*. `RenderComparison` emits `Equal` as a BARE `{field: value}`, so an arm that reused that output directly inside `$not` would emit exactly this illegal form — hence the explicit `{$eq: …}` wrap, applied by testing whether the rendered value is a document whose first element name starts with `$` (rather than assuming). **The reachable document-valued case this check guards against is NOT "equality against a document-valued property"** — the translator only ever hands `RenderComparison` a mapped SCALAR `IProperty` leaf, so that input never occurs. The genuinely reachable case is `PlaceholderTable`'s parameter sentinel, `{__mongoef_param__: N}`, produced whenever the compared value is a captured local / EF query parameter rather than a constant (e.g. `!(x.A == capturedLocal)`) — a `BsonDocument`, but not `$`-prefixed, so the check correctly treats it as a bare value and applies the `$eq` wrap. This correctness depends on `PlaceholderTable.SentinelKey` never starting with `$` (see that constant's own doc comment); pinned by `MongoQueryLanguageRendererTests.Not_over_a_parameterized_equality_wraps_the_sentinel_in_eq` and the functional `NativeExprComparisonTests.Negated_equality_against_a_captured_local_goes_native`. This is REACHABLE in practice, via `Where(x => !(x.A == 1))` (an inline constant) and via a captured local alike, which EF does not normalize away — it is not a theoretical concern. > **EF-335: the root-scope half swapped LINQ-level negation for tree-level negation.** `NativeCardinalityBinder.TryBindAggregate`'s `All` branch previously did `Expression.Not(predicate.Body)` and then translated. `TryTranslate` SUCCEEDED for a comparison operand (the translator's `Not` arm falls through to `MongoUnaryExpression(Not, operand)` for anything that is not an `In`/`Regex`/`ElemMatch`/bare-field operand), so the conjunct was accepted and the failure surfaced later, at RENDER time, where `RenderUnary` threw and the gate fell back. It now translates the body and calls `TryNegate`, declining (`return false`, no mutation) if either step fails. Negating after translation is also what makes De Morgan available at root scope, so a conjunctive/disjunctive `All` predicate goes native too. The negated conjunct still goes through `AddPredicateConjunct`, so the EF-347 tail-append semantics (a predicate-injecting aggregate after `Take`/`Skip` evaluates over the paged rows) are unaffected. **Behaviour-preserving for the shapes already native before the swap:** `All_top_level`'s `StartsWith` predicate flips the same `MongoRegexExpression.Negated` either way, and its spec MQL is byte-identical after the swap (verified — `NorthwindMiscellaneousQueryMongoTest.All_top_level` passed unchanged in both `Native` and `NativeOnly` across the before/after sweeps); `NativeCardinalityTests.All_with_a_regex_predicate_is_unchanged_by_the_negator_swap` pins the same property functionally. `All_top_level_column` is field-to-field and stays declined **by design** (the negator refuses it), so it is unchanged too.

> **Risk profile — unlike the recent slices, this one COULD have changed results, which is why the differential test is the gate.** Every recent slice here has been "fallback→native, results structurally unchanged". This one is not structurally incapable of changing results: a wrong complement returns wrong rows under default `Native`, where the pre-slice fallback was correct — a fallback→native transition that CHANGES RESULTS, precisely what the versioning rubric's not-a-break carve-out does not cover, and precisely the failure mode the `Any` slice shipped a critical fix for. > **Owned-collection `.Count` in a predicate (EF-322).** Native now also covers an owned (embedded) collection's element COUNT compared against a threshold in a predicate — `Where(b => b.Posts.Count > 2)`, `.Count()`, `.LongCount()`, either operand order (`2 < b.Posts.Count`), a constant OR a parameterized threshold, a count reached through one or more owned single-reference hops (`b.Home.Notes.Count`), and a count nested inside a quantifier's element predicate (`b.Posts.Any(p => p.Comments.Count > 1)`) — for all SIX comparison operators (`>`, `>=`, `<`, `<=`, `==`, `!=`). Previously this always fell back to driver-LINQ. **Mechanism — one dialect-neutral shape, two rendering tiers.** Recognition happens in `TranslateOperand` (an ordinary OPERAND position, not a dedicated comparison arm), via `TryMatchCountExpression` + `TryResolveOwnedCollectionPath`, producing a dialect-neutral `MongoSizeExpression(arrayPath, nullSafe: true)` that says nothing about `$exists` or `$expr` — the RENDERER decides the tier. **Tier 1 (query dialect, `TryRenderSizeComparison`):** an integer-CONSTANT threshold renders as an array-INDEX EXISTENCE test, `{"path.k": {$exists: true|false}}` — `C > n` → `{"path.n": {$exists: true}}` (`n ≥ 0`); `C >= n` → `{"path.(n-1)": {$exists: true}}` (`n ≥ 1`); `C < n` → `{"path.(n-1)": {$exists: false}}` (`n ≥ 1`); `C <= n` → `{"path.n": {$exists: false}}` (`n ≥ 0`); `C == n` (`n ≥ 1`) → the two single-key forms merged by the existing `CombineAnd`; `C == 0` → `{"path.0": {$exists: false}}`; `C != n` (`n ≥ 1`) → the two forms `CombineOr`'d; `C != 0` → `{"path.0": {$exists: true}}`. A degenerate threshold (tautology `C >= 0`, contradiction `C < 0`, non-integral `C > 2.5`) or a PARAMETERIZED one needs no clamping or decline — it simply isn't admitted by this tier and falls through. **Tier 2 (`$expr`, the aggregation dialect):** everything Tier 1 doesn't admit — a parameterized threshold, a degenerate constant, count-vs-count, or a count composed inside arithmetic — renders as `{$expr: {<op>: [{$size: {$ifNull: ["$path", []]}}, <value>]}}` via the existing `MongoAggregationExpressionRenderer`, which gained one new arm for the null-safe `$size`. **Why query-dialect `$size` was REJECTED outright, never even attempted:** `{path: {$size: 0}}` does NOT match a document whose array is MISSING or explicitly BSON `null` — exactly the class of error that sank `{path: {$ne: []}}` for bare `Any()` in the earlier slice. The array-index form is correct for all three states (empty, missing, explicit null) for free, because none of them has an element at any index. **Why `$ifNull` in the Tier-2 `$expr` form is MANDATORY, not defensive:** `$size` evaluated against a missing or explicitly-null array is a HARD SERVER ERROR that aborts the whole aggregate command, not merely a wrong answer — so every `$expr`-tier count MUST wrap the path in `$ifNull: [..., []]`, mapping both states to an empty array (count 0), matching what LINQ's `Count == 0` answers for a missing embedded array. **The negator exception, prominently — an array-count comparison is INVERTED, not `$not`-wrapped, the OPPOSITE rule from the `All` slice immediately above for the SAME reason applied in the opposite direction.** The `All` note's rule is "ask whether the RENDERED pair partitions the value space", and for THIS family it does: the Tier-1 rendered form is `$exists`, which partitions every document (it either has `path.k` or it doesn't) — so inverting the OPERATOR (`GreaterThan ↔ LessThanOrEqual`, `GreaterThanOrEqual ↔ LessThan`, `Equal ↔ NotEqual`) on the SAME count comparison is the EXACT complement, the admitted set is closed under inversion (each pair preserves "every required array index `>= 0`"), and `MongoExpressionNegator` handles it as a dedicated case (`MongoBinaryExpression { Left: MongoSizeExpression }`) alongside its `$eq`/`$ne` inversion case — contrast the four RELATIONAL operators on a scalar field, which the SAME negator must `$not`-WRAP rather than invert, because `{$gt}`/`{$lte}` do NOT partition (neither matches a missing/null field). This is why `!(b.Posts.Count > 2)` goes native via the negator with no dedicated `$not`-over-array-index renderer arm — the negator produces `Count <= 2` directly, and `TryRenderSizeComparison` computes the resulting index form as usual. **The one accepted asymmetry:** a PARAMETERIZED threshold declines when negated (`!(b.Posts.Count > @threshold)`), because the negator's `TryNegate` gates on `IsQueryDialectRenderable`, and a parameterized threshold has no Tier-1 (query-dialect) form to invert — a coverage gap, not a correctness one; `A_negated_parameterized_count_declines_and_falls_back_to_correct_rows` pins it. **The classifier calls the renderer, so drift is structurally impossible:** `IsQueryDialectRenderable`'s size-comparison arm calls `TryRenderSizeComparison` directly rather than re-deriving the admissibility condition, extending the same "these two/three must change together" contract the `All` slice established for the negator. **The bare-`Any()` unification:** bare `Any()` no longer has its own rendering path — it is now represented as `Count >= 1` (`MongoBinaryExpression(GreaterThanOrEqual, MongoSizeExpression(nullSafe: true), 1)`), the SAME array-index form (`{"path.0": {$exists: true}}`), so there is now ONE representation for array cardinality rather than two; `MongoElemMatchExpression.ElementPredicate` is consequently now NON-NULLABLE (it used to admit a `null` element predicate to represent bare `Any`); and `!Any()` falls out of the SAME negator inversion with no dedicated code, rather than its own `$exists: false` special case. The emitted MQL is UNCHANGED — this is a representation unification, not a behavior change (see the correction to the `Any` note above). **`MongoSizeExpression` is SHARED, not duplicated,** with the pre-existing projected reference-collection `Count` (`Select(c => new { c.Orders.Count })`, EF-339/SP5's `$lookup`-alias `$size`) — the two uses are distinguished by the `NullSafe` property, whose DEFAULT is `false`: a `$lookup` always writes an array, so the reference-collection path's rendering is untouched, byte-identical `{$size: "$path"}`; only the NEW owned-predicate call site passes `nullSafe: true`. **Why a name-based count matcher is safe — and the claim that was CORRECTED.** `TryMatchCountExpression` matches by NAME (`.Count` property or `.Count()`/`.LongCount()` call) with no type-identity check, so it must not be fooled by a mapped entity SCALAR property literally called `Count`. The protection is STRUCTURAL, in `TryResolveOwnedCollectionPath`: the chain must be rooted at the query parameter with at least one hop, and its FINAL hop must be an embedded COLLECTION NAVIGATION — a mapped scalar's receiver is an ENTITY, never a collection, so a same-named scalar can never resolve to an array path (`o.Count` declines on the zero-hop check; `b.Address.Count` declines on the final-hop check). An earlier draft of this comment claimed the call-site ORDERING — count recognition running AFTER `TryResolveMember` in `TranslateOperand` — was what prevented the collision. That was MEASURED FALSE during Task 6 fix round 1: moving count recognition ahead of `TryResolveMember` turned NO test red. REWRITTEN, not patched, because the original version of this note stated a root cause that measurement disproved.** It used to say the operative split was whole-entity-vs-projection: whole-entity materialization normalizes a missing/explicitly-null embedded array to an empty list, the projection path does not. **That framing is WRONG and must not be repeated.** What was actually measured: pre-fix, *nothing* normalized, on *any* path. `MongoProjectionBindingRemovingExpressionVisitor.IncludeCollection` skips its fixup loop entirely when `relatedEntities` is `null`, so a materialized navigation retained whatever the CLR class's own field initializer left behind — `null` for a plain `{ get; set; }` auto-property, `[]` for one written `= []`. Do not re-file it as a non-break by analogy with the `Route`-flip carve-out; that carve-out is about which execution path a query takes, and this is a materialized-value change.

> **The mechanism is THREE edits — two on the DOM shaper, one on the streaming materializer.** (This note originally said "two edits", covering only the DOM shaper, and the uniformity claim above was consequently FALSE as first shipped: `ToList()` over a flat, streaming-eligible owned collection still answered `null` while `First()` over the same document answered empty, and `Native` diverged from `DriverLinq` for a supported query. The third edit, added at the final whole-branch review, is what makes the uniformity claim true.) (3) **The streaming path** — `MongoStreamingEntityMaterializerRewriter.BuildFillLoop` now emits a post-loop normalization per owned collection: `if (accumulator == null) accumulator = new List<TElement>()`. Two absent states reach that point with the accumulator still null, and neither was covered before: a **MISSING** array element (the forward name-dispatch loop never matches its element name, so `BuildCollectionLoop` never runs at all — the accumulator keeps the `Expression.Default` value `CollectLocals` initialized it to) and an **explicit BSON Null** (`BuildCollectionLoop`'s null branch consumes the null via `ReadNull` and assigns nothing). Normalizing once, post-loop, rather than in the BSON-Null branch, is deliberate: it is the only placement that covers the missing case, so the two states cannot be fixed asymmetrically. The same loop also now resets each accumulator to null pre-loop, mirroring the existing required-scalar presence-flag reset, so a reused owned-collection element plan cannot inherit the previous iteration's accumulator. As on the DOM path the `List<TElement>` is only the ACCUMULATOR handed to `IncludeCollection`; the collection assigned to the navigation is still built by its own `IClrCollectionAccessor.GetOrCreate`, so a non-`List` navigation type is correct for free. `BuildCollectionLoop`'s own doc comment used to assert the disproven claim ("the collection is left empty … `IncludeCollection` still creates an empty CLR collection") — corrected in place, not preserved. Coverage lives in `StreamingCollectionNormalizationTests`, whose fixture is deliberately un-masked in both ways that matter (no `= []` initializer on the navigation, and no navigation on the collection ELEMENT — an element navigation makes the shape streaming-INELIGIBLE and routes it to the DOM shaper, which is exactly how every other fixture on this branch masked the streaming gap); each test asserts `StreamingEligibility.IsEligible` directly rather than assuming it. (1) The null-collapse conditional was deleted from `BsonDocumentInjectingExpressionVisitor`'s `CollectionShaperExpression` case — that visitor no longer special-cases a missing/null stored array at all; the assignment expression it produces is byte-identical otherwise. (2) A `Coalesce` to an empty `BsonArray` was added at the POINT OF USE, in `MongoProjectionBindingRemovingExpressionVisitor`'s `CollectionShaperExpression` case — the array value is coalesced to empty immediately before being handed to `PopulateCollection`, which builds the materialized collection through the navigation's own `IClrCollectionAccessor`. Building it that way, rather than constructing a `List<T>` directly, is what makes a non-`List` navigation type (e.g. a `HashSet<T>`-backed collection) come out correct for free — the accessor already knows how to create and populate whatever concrete type the navigation declares.

throw` so a future violation is loud instead of silently reading the wrong array; that branch is provably unreachable for an alias node (it fires only when the injector emitted no `bsonArrayN` assignment, i.e. for a shaper nested inside another collection shaper's `InnerShaper`, and an alias node is only ever a top-level leaf of a terminal native projection). **The `Route == Projection` guard is load-bearing, same as this file's other instances:** registration happens in a new private `TryBindNativeArrayProjection`, called at the top of `MongoProjectionBindingExpressionVisitor`'s `VisitExtension` `MaterializeCollectionNavigationExpression` case — the same register-before-descending position the count leaf (`VisitMethodCall`) and the arithmetic leaf (`Visit`) already use. **The design's own Step-6 placement (inside `VisitMember`'s navigation switch) was MEASURED BROKEN and moved:** reaching that switch first visits the OWNER shaper, whose `StructuralTypeShaperExpression` case calls `AddToProjection`, and `ApplyProjection()` returns EARLY when `Projection.Any()` — so no projection member is ever rewritten to `Constant(index)` and every SIBLING leaf dies in `GetProjectionIndex` with an `InvalidOperationException` at shaper-compile time, in all modes.

> **THE GOVERNING HAZARD, which explains every guard below.** The shaper is built alias-addressed at **translation** time, but native-versus-fallback is decided **later**, by the compile-time gate. On any fallback path the emitted pipeline is `aggregate([])`, so that same alias-addressed shaper is handed a **WHOLE document** — and any read whose alias does not name a real top-level field simply misses. For a collection that miss is **SILENT**: `TypeAs` yields null and the EF-358 coalesce turns it into an empty collection, with no exception. So admissibility cannot depend on "are we native?"; it has to hold on an un-projected document too. Both rules below exist because a live bug was MEASURED, not because anyone reasoned ahead — but the two bugs were **not** the same kind, and this summary used to blur them: **rule (1) was found via a measured SILENT wrong-data bug; rule (2) via a measured THROW, whose silent variant is mechanism-derived (not executed) and is pinned by the colliding-alias test.** **(1) The alias-agreement rule** — `NativeProjectionBinder.IsNativeArrayProjectionLeaf(navigation, rootEntityType, alias)` requires the member to be an `INavigation`, `IsEmbedded()`, `IsCollection`, its `DeclaringEntityType` to be the query ROOT, **and the alias to equal the navigation target's `GetContainingElementName()`**. Together the root-declared and alias conjuncts give the invariant *"the alias-addressed read and the document-path read resolve to the same place"* (root-declared forces a single hop, so alias `==` array path identically — exact, not approximate). **The bug:** `Select(b => new { b.Title, P = b.Posts })` — a RENAMED alias — returned the correct 1 element under `Native`/`NativeOnly` and **0 elements, silently, under explicit `DriverLinq`**. The plain `new { b.Title, b.Posts }` spelling MASKED it, because an anonymous type's implicit member name *is* the property name and therefore happened to satisfy the invariant. A `MongoQueryMode` check was considered and rejected: it would not have covered a late fallback under `Native`. The two conjuncts are NOT independent — lifting only the alias one reopens the renamed-alias bug; lifting only the root-declared one reopens it for `b.Home.Notes` (alias `"Notes"` equals the element name but not the full path `"Home.Notes"`). Both are pinned by mutation-verified tripwire tests (`NativeArrayProjectionTests.Renamed_array_alias_is_declined_and_returns_correct_data_in_every_mode`, `.Array_leaf_under_a_nested_owner_is_declined_but_still_returns_correct_data`) meant to be flipped deliberately, never quietly. **(2) The sibling-readability rule** — when any array leaf is present, EVERY non-array sibling leaf must also be whole-document-readable (`IsWholeDocumentReadableLeaf`: a `MongoFieldExpression`, non-dotted, alias `==` its own `ElementName`); the whole projection declines otherwise, BEFORE any `AddLookup`/`AddProjection`, so a decline mutates nothing. **The bug, and it is a regression this slice itself introduced:** pre-slice, `Route == Projection` IMPLIED every leaf was scalar/computed, hence pushdownable, hence backed by a real `$project` with real aliases. Admitting an entity-collection leaf broke that implication — any entity/collection leaf makes EF's own `ProjectionAnalyzer.CanPushDown` refuse, forcing the MIXED path → `StripPushedDownSelect` → `aggregate([])` → whole documents. The array leaf survives (its alias-agreement invariant makes it a valid whole-document read) but its COMPUTED siblings do not: `Select(b => new { b.Title, N = b.Posts.Count, b.Posts })` **threw under explicit `DriverLinq`**, where pre-slice it returned correct values — i.e. `UseQueryMode(DriverLinq)` stopped restoring working behaviour, the exact property that mode exists to provide. **And the same mechanism can be SILENT:** when a computed leaf's alias COLLIDES with a real mapped element name, the whole-document read succeeds against the WRONG field — `Select(b => new { b.Posts, Rank = b.Rank * 2 })` would return the raw stored `Rank`, not `Rank*2`. That colliding case is pinned directly (asserting `2,4,6`, not the seeded `1,2,3`), so the silent variant is genuinely covered and not merely the benign throw. **The sibling rule is deliberately BROADER than the mechanism strictly requires:** `alias == field.ElementName` also declines a plain-member sibling whose alias merely differs (`new { Mine = b.Title, b.Posts }`, or a `HasElementName`-renamed property), which both shapers would in fact have handled — only a leaf resolving to NO property (a count or arithmetic expression) actually falls through to the alias-as-property-name lookup. That is an **optimization gap, not a defect**: it can only turn an admit into a decline, and a decline returns correct values via fallback. **Emit and shaper sides decline TOGETHER, by construction:** the binder declines before mutating `Select.Projection`, so `Route` is `Fallback` by the time the shaper visitor runs and none of the three `Route == Projection`-gated registrations (array, count, arithmetic) fires. Gating only one side is precisely the silent-wrong-data split these rules exist to prevent.

> **The owner `_id` is emitted whenever any array leaf is accepted, and it is mandatory.** `{ $project: { Title, Posts } }` alone has no `_id`, and an owned element with a **SHADOW** key (no explicit `HasKey`) materializes its OWNER's key out of the row it is handed — the element shaper resolves it through `_ownerMappings`, not from anything stored on the element. Drop the `_id` and materialization fails **per row** with `InvalidOperationException: Document element is missing for required non-nullable property '<Key>'` (from `BsonBinding.GetPropertyValue`, via `PopulateCollection`). An **explicit-`HasKey`** element never performs that owner-key read at all, so emitting `_id` alongside it is simply harmless — the emission is keyed on the LEAF KIND (`hasArrayLeaf`), not on the element's own key kind, because the binder has no cheap way to tell those apart from there and does not need to. The extra projection is inert for the result SHAPE (the shaper reads every result member by alias, never positionally, and `"_id"` is never bound to a `ProjectionMember`) and it correctly suppresses `MongoPipelineFactory.RenderProject`'s default `_id : 0` exclusion.

> **Non-canonical Skip/Take (EF-347).** Native now also covers filter/sort/paging compositions OUTSIDE the original fixed `$match → $sort → $skip → $limit` arrangement: a `Where`/`OrderBy`/`ThenBy` (or an aggregate-injected predicate) applied AFTER a `Skip`/`Take` already on the select, `Take` before `Skip`, and repeated/interleaved paging (`Skip(a).Take(b).Skip(c)`) — shapes that previously forced a driver-LINQ fallback purely because they didn't fit the one fixed slot arrangement. **Mechanism (Task 1):** `MongoSelectDefinition` replaced its single `Predicate`/`Orderings`/`Offset`/`Limit` slots with an ordered `PipelineOps` list (`MongoMatchOp`/`MongoSortOp`/`MongoSkipOp`/`MongoLimitOp`, in `Expressions/MongoSelectOp.cs`); **arrival order IS emission order** — `MongoSelectLowerer.AppendSelectOpStages` (renamed from `AppendCanonicalStages`) walks `PipelineOps` and emits each op verbatim, with no reordering or fixed-slot logic. **Merge rules**, all on `MongoSelectDefinition`: `AddPredicateConjunct` ANDs a `Where`/injected-predicate into the tail op if it is already a `MongoMatchOp` (so consecutive `Where`s still collapse to one `$match`, unchanged from before), else appends a new one; `StartOrReplaceSort` (`OrderBy`) REPLACES the tail op if it is a `MongoSortOp` (reproducing the old reset-orderings semantics for `OrderBy(a).OrderBy(b)`), else appends a fresh sort; `AppendThenBy` extends the tail sort; `AppendSkip`/`AppendLimit` (`Skip`/`Take`) always append. **Task 2** deleted the canonical-order rejection guards in `NativeSlotPopulator` (`PagingAlreadyApplied` on `Where`/`OrderBy`/`OrderByDescending`/`ThenBy`/`ThenByDescending`, and the single-slot `Skip`/`Take` checks) — each of the seven slot operators now just applies its merge rule unconditionally. **Task 3** deleted the symmetric guard in `NativeCardinalityBinder.TryBindAggregate` that forced fallback for a predicate-injecting aggregate (`All`, or predicate-bearing `Count`/`Any`) following `Take`/`Skip`: `AddPredicateConjunct` always ANDs into (or appends after) the CURRENT tail of `PipelineOps`, so the injected predicate lands after any already-recorded `$skip`/`$limit` — never hoisted ahead of it — meaning `Take(n).All(pred)`/`Count(pred)`/`Any(pred)` correctly evaluate only over the first `n` rows without a dedicated guard; a plain aggregate that injects no predicate (`Take(n).Count()`) was never affected either way. **This is coverage, not correctness:** every shape above already returned correct results via the driver-LINQ fallback (the oracle) — the change only widens which shapes execute via the native pipeline instead of falling back; no result changes. **The reorder is not a break:** faithful arrival-order emission means the MQL emitted for a shape that was ALREADY native before EF-347 can change stage order/shape versus a prior build (e.g. a merge landing differently once ops are recorded verbatim) — per the versioning rubric (see the top of this file) the exact emitted MQL for a supported, already-native query is an implementation detail, not part of the contract, so this is **not** a breaking change. **Retained boundaries, verified empirically (not just by inspection) via `MongoQueryMode.NativeOnly` probes:** `NativeGroupByBinder.TryBindGroupKey`'s pre-existing `select.HasPaging || select.HasOrdering` guard (line ~54; Task 1 only renamed `Orderings.Count > 0` → `HasOrdering`, the guard itself is untouched) still rejects **any** `GroupBy` — key or key+aggregate — reached after paging/ordering has already been recorded, canonical or non-canonical alike, so `Take(n).Skip(m).GroupBy(...)` still falls back gracefully exactly as before this slice. A plain projected `Select`, by contrast, was **never guarded on paging state** in either `TranslateSelect` or `NativeProjectionBinder` — so once Task 2 stopped forcing `Fallback` for the non-canonical paging itself, a projected `Select` composed after it (e.g. `OrderBy(...).Take(3).Skip(1).Select(new {...})`) goes native too, as an unplanned but harmless side effect of the paging relaxation, not a change to `NativeProjectionBinder` itself — `Select` simply never cared what paging shape preceded it. The `HasTerminalOperator` post-terminal gate (`IsGroupBy`/`IsDistinct`/`IsSetOp`/`Grouping`/`UnwindSource` — see the GroupBy as-built note above) is entirely orthogonal to this slice and unchanged: non-canonical Skip/Take is a *pre-terminal* relaxation only, and every post-terminal guard elsewhere in this document still applies exactly as documented.

In: top-level method-call translators **and native slot population**, the **query expression tree → stage IR → `BsonDocument[]` pipeline generator** (lowerer / renderer / pipeline factory), the compile-time **gate**, projection binding, the EF-to-driver-LINQ bridge (fallback), shaper compilation (native streaming + DOM, and driver-LINQ DOM), vector-search pre-extraction.
Out: BSON encoding/decoding of *values* (Serializers area — the renderer asks `BsonSerializerFactory` for serializers), change-tracking snapshots (ChangeTracking area), index/collection schema (Storage area), cursor execution itself (`MongoClientWrapper.Execute` in Storage), and aggregation-pipeline generation **for the fallback path** (still the driver's job).

## Pipeline at a glance

```
IQueryable<T>  (EF Core)
   │
   ▼  MongoQueryCompilationContext           (preserves the original LINQ tree; carries the MongoQueryMode)
   ▼  MongoQueryTranslationPreprocessor      (hoist final predicates; lift VectorSearch out before nav expansion)
   ▼  MongoQueryableMethodTranslatingExpressionVisitor (QMTEV)
   │      ├─ accepts only Queryable / MongoQueryableExtensions / MongoDB.Driver.Linq.MongoQueryable
   │      ├─ DELEGATES native slot population to NativeSlotPopulator.PopulateNativeSlots (the ordered
   │      │     PipelineOps list — match/sort/skip/limit ops recorded in arrival order, EF-347) and
   │      │     projection binding to NativeProjectionBinder.TryPopulateNativeProjection (Projection),
   │      │     both via MongoExpressionTranslator; either calls mongoQ.Select.MarkNotNativelyRepresentable()
   │      │     for any operator it does not lower into an op (catch-all) — see pitfalls
   │      └─ ALWAYS also captures the raw method chain (CapturedExpression) for the driver-LINQ fallback
   ▼  MongoQueryTranslationPostprocessor     (apply final ProjectionMapping)
   ▼  MongoShapedQueryCompilingExpressionVisitor  ── THE GATE (compile time, honors MongoQueryMode) ──
   │   if Native & Select.Route != Fallback & lower/render succeed → NATIVE PATH:
   │      MongoSelectLowerer  : PipelineOps → MongoPipelineStage[]  (emitted verbatim in arrival order, EF-347; then $lookup/$unwind/terminal)
   │      MongoQueryLanguageRenderer + PlaceholderTable : predicate → $match BSON; params → sentinels
   │      MongoPipelineFactory.Create : render ONCE into a template + placeholder table  (B2)
   │      compile streaming shaper (MongoStreamingEntityMaterializerRewriter) if StreamingEligibility, else DOM
   │   else (DriverLinq, or not representable, or NativeOnly→throws) → DRIVER-LINQ FALLBACK:
   │      MongoEFToLinqTranslatingExpressionVisitor rewrites CapturedExpression as driver-LINQ; DOM shaper
   ▼  MongoExecutableQuery + QueryingEnumerable
          ├─ NATIVE: factory.Build(parameterValues) → BsonDocument[] set as NativePipeline;
          │          MongoClientWrapper.Execute runs collection.Aggregate(pipeline) — streaming: Aggregate<TEntity> with the one-pass MongoEntityMaterializerSerializer (deserialize IS materialize, SP7); else BsonDocument DOM
          └─ FALLBACK: MongoClientWrapper.Execute hands the driver-LINQ expression to IMongoQueryProvider
          → IAsyncCursor; shaper turns each row into the requested CLR shape
```

B2 = the pipeline template is built **once at compile time** (lower + render → `MongoPipelineFactory`); only `factory.Build(parameterValues)` (clone-and-substitute the placeholder sentinels) runs per execution. The native-vs-driver and streaming-vs-DOM decisions are therefore **compile-time-deterministic** — there is exactly **one** shaper per query and **no** runtime dual-shaper dispatch.

## Key entry points

- `MongoQueryCompilationContext` — EF Core hook to preserve the original captured `IQueryable` so post-translation we can recover the user's intent (e.g. for diagnostics).
- `MongoQueryTranslationPreprocessor` — first phase. Notably, **`VectorSearch(...)` is extracted before EF's nav-expansion and re-inserted after** — nav expansion doesn't know about it.
- `Visitors/MongoQueryableMethodTranslatingExpressionVisitor` — the central LINQ-method dispatcher. Enforces the allowed-method-source set; **delegates native slot population and projection binding** to `NativeSlotPopulator`/`NativeProjectionBinder` (the `Translate*` overrides that would otherwise do this are inert — see pitfalls); captures the final method-chain expression on `MongoQueryExpression`.
- `Visitors/MongoShapedQueryCompilingExpressionVisitor` — **the compile-time gate**. Reads `MongoQueryMode`; consults `MongoSelectDefinition.Route` (the authoritative is-native decision for the slot/projection representability) to decide native vs. fallback; builds the `MongoPipelineFactory` and compiles the native (streaming/DOM) shaper when `Route != NativeRoute.Fallback`, else compiles the driver-LINQ fallback shaper. Splits scalar vs. entity result paths. **The full is-native decision is centralized (EF-334) in `ClassifyNativeDisposition`** → `NativeDisposition {Native, Fallback, HardDecline}`, which reads the three is-native signals in one place: `Route` (slot/projection representability), `IsGroupByFallbackUnsafe` (the GroupBy+Join wrong-data hard-decline), and vector search (`ContainsVectorSearch(CapturedExpression)` — the one signal not on `MongoSelectDefinition`, since the `VectorSearch(...)` call is lifted out by the preprocessor and never reaches slot population). `Route` stays "which native shape / slot representability"; the disposition is the superset. Cross-collection `$lookup` streamability (`AllPendingLookupsAreStreamable`) is **not** an is-native signal — it is the separate streaming-vs-DOM axis (it only picks the streaming shaper for a query that is already native), so it is deliberately outside the disposition.
- **Native translation (`NativeTranslation/` + `Expressions/`):**
  - `Expressions/MongoExpression` + subtypes (`MongoFieldExpression`/`MongoConstantExpression`/`MongoParameterExpression`/`MongoBinaryExpression`/`MongoUnaryExpression`) + `MongoOrdering` — the dialect-agnostic `SqlExpression`-analog node hierarchy.
  - `Expressions/MongoQueryExpression` (+ `.Lookup.cs`) — the structured query tree: it **has-a** `MongoSelectDefinition` (reached via `MongoQueryExpression.Select`) holding the native scalar IR, **plus** the cross-collection `$lookup`/inner-collection state (`Lookups`/`IsJoinQuery`/`InnerCollections`, on `.Lookup.cs`) and the retained `CapturedExpression` + `ProjectionMapping` for the fallback.
  - `Expressions/MongoSelectDefinition` — the native-translation logical query IR — an ordered `PipelineOps` list (`MongoMatchOp`/`MongoSortOp`/`MongoSkipOp`/`MongoLimitOp`, replacing the original single `Predicate`/`Orderings`/`Offset`/`Limit` slots as of EF-347 — see the Non-canonical Skip/Take note above); once a set op is attached, `MongoSelectDefinition` also holds a SECOND ordered op list, **`TrailingOps`** (EF-347 slice B — see the set-ops as-built notes below), populated by the SAME five merge methods (`AddPredicateConjunct`/`StartOrReplaceSort`/`AppendThenBy`/`AppendSkip`/`AppendLimit`) once they target the private **`ActiveOps`** property instead of `PipelineOps` directly — `ActiveOps` is `PipelineOps` normally and flips to `TrailingOps` the instant `SetOperation` is attached, so a `Where`/`OrderBy`/`ThenBy`/`Skip`/`Take` (or an aggregate-injected predicate) composed AFTER a set op records into `TrailingOps` and is emitted by the lowerer AFTER the set-op stage, over the COMBINED result; **`IsSetOpTerminalOnly`** (`IsSetOp && !IsGroupBy && !IsDistinct && Grouping == null && UnwindSource == null`) is the narrow predicate that relaxes the two post-terminal catch-all guard sites (`NativeSlotPopulator`'s slot guard, `NativeCardinalityBinder.TryBindReducer`/`TryBindAggregate`) to admit exactly those trailing operators while every other deferred own-`Translate`-override operator keeps its own untouched `HasTerminalOperator` check — plus **`Projection`** — extracted (EF-330) from `MongoQueryExpression` into a composed, dialect-neutral data-holder. `NativeSlotPopulator`/`NativeProjectionBinder` populate it via `mongoQ.Select`; the gate and lowerer read it. The `$lookup` state stays on `MongoQueryExpression` (entangled with the fallback shaper, slated for EF-317), so it was **not** moved here. **`Projection` (EF-331)** holds the dialect-neutral `MongoProjection` (alias → `MongoExpression` field-ref pairs) for a terminal anonymous-type/DTO member-access `Select`; it is populated by `NativeProjectionBinder.TryPopulateNativeProjection` (not by `NativeSlotPopulator.PopulateNativeSlots` — see the catch-all pitfall below) and stays empty for every other projection shape (bare scalar, computed, mixed, non-terminal), which still fall back to driver-LINQ. The single authoritative is-native decision is the computed property `Route` (enum `NativeRoute`: `Fallback`/`WholeEntity`/`Projection`/`ScalarAggregate`/`GroupBy`) — `Fallback` when an internal `_hasUnsupportedOperator` flag was set via `MarkNotNativelyRepresentable()`; otherwise `ScalarAggregate` (EF-SP4) when a scalar-aggregate `Cardinality` is set, `GroupBy` (EF-SP6) when a `Grouping` is set, `Projection` when `Projection` is non-empty (representable **and** has a pushed-down projection); otherwise `WholeEntity`. `Route` is the authoritative signal for **slot/projection** representability; the full is-native decision is the gate's `ClassifyNativeDisposition` (EF-334), which layers two further is-native signals onto `Route`: vector search (via `ContainsVectorSearch` over `CapturedExpression` — not on `MongoSelectDefinition`, as the `VectorSearch(...)` call is lifted out before slot population) and the GroupBy+Join hard-decline (`IsGroupByFallbackUnsafe`). `$lookup` streamability (`AllPendingLookupsAreStreamable`) is a **separate** axis (streaming-vs-DOM), not an is-native signal.
  - `NativeTranslation/MongoExpressionTranslator` — EF predicate / key-selector body → `MongoExpression` (`TryTranslate` / `TryTranslateField`); returns false for anything outside its acceptance set. As of EF-329 (predicate breadth) that set includes nullable equality/`== null` (IS NULL), `Enumerable.Contains`/`ICollection.Contains` → `MongoInExpression` (`$in`/`$nin`), `string.StartsWith`/`EndsWith`/`Contains` → `MongoRegexExpression` (`$regularExpression`), and field-to-field/arithmetic `MongoBinaryExpression`s (still parity-limited otherwise; the computed long tail — string transforms, date parts, `Math.*`, type-changing casts — remains unsupported and falls back).
  - `NativeTranslation/MongoSelectLowerer` — the native IR → `MongoPipelineStage[]` (typed IR under `NativeTranslation/Stages/`), BSON-free; emits the recorded `Select.PipelineOps` verbatim in arrival order (EF-347 — no fixed canonical order) + owns the lookup eligibility guards. When `MongoSelectDefinition.Projection` is populated, the lowerer appends a `NativeTranslation/Stages/MongoProjectStage` **last** in the pipeline (after `$match`/`$sort`/`$skip`/`$limit`), carrying the `MongoProjection` alias/field-ref pairs; `MongoPipelineFactory.Create`'s stage-walk renders it to a `$project` BSON body (explicit `_id: 0` plus one entry per alias) in the aggregation-expression field-ref dialect.
  - **`NativeTranslation/MongoQueryLanguageRenderer` + `NativeTranslation/MongoAggregationExpressionRenderer` — the dual-dialect renderer (EF-329 predicate breadth).** `MongoQueryLanguageRenderer` renders `MongoExpression` → `$match`-dialect BSON (`{field:{$gt:v}}`, `$and`/`$or`, bare-bool, `$ne`, `$in`/`$nin`, `$regularExpression`) — the query/filter dialect, and is usable directly as a `$match` stage body. `MongoAggregationExpressionRenderer` renders a `MongoExpression` subtree to the **aggregation-expression** dialect that lives inside `{ $expr: … }` (`$eq`/`$ne`/`$lt`/…, `$add`/`$subtract`/`$multiply`/`$divide`/`$mod`, field refs as `"$elementName"`) — the only dialect that can express field-to-field comparisons and arithmetic, which have no query-dialect form. `PlaceholderTable` (shared by both) records parameter placeholders. Both renderers share one value-rendering path, `NativeTranslation/MongoValueRenderer`, for `MongoConstantExpression`/`MongoParameterExpression` leaves, so a constant and a parameter of the same value always emit identical BSON regardless of which dialect is in play; `MongoAggregationExpressionRenderer` is a `static` class (no instance state, unlike `MongoQueryLanguageRenderer`).
    - **Per-subtree boundary is index-first, and the renderer — not the lowerer — owns it.** `MongoQueryLanguageRenderer.RenderNode` keeps `&&`/`||` (`AndAlso`/`OrElse`) at the query level always: each branch of an AND/OR is rendered (and combined via `CombineAnd`/`CombineOr`) independently, so a mixed predicate like `a.Age > 21 && a.X == a.Y` keeps the indexable `Age` clause as a plain `$match` term and wraps only the non-query-expressible `X == Y` subtree in `$expr` (`RenderAsExpr` delegates that one subtree to `MongoAggregationExpressionRenderer`). This maximizes index usage: `$expr` clauses can't use indexes as effectively as native `$match` operators, so it is scoped to the *smallest* subtree that actually needs it, not promoted to the whole predicate. A comparison is query-native (handled by `MongoQueryLanguageRenderer` directly) only when the left side is a bare field and the right side is a constant/parameter (`IsQueryNativeComparison`); anything else (field-to-field, arithmetic operands) falls through to `RenderAsExpr`.
    - **This is an intentional refinement over the original design doc.** `docs/superpowers/specs/2026-06-23-native-query-provider-design.md` (§"Lowering, rendering & the dialect boundary") states dialect choice is made in the lowerer, never in the QMTEV or the node types. With per-clause dialect *mixing* now required (a single predicate can straddle both dialects), that responsibility moved to the **renderer**, which walks the already-lowered, dialect-neutral `MongoExpression` tree and decides per-subtree which dialect applies. `MongoSelectLowerer` and the `MongoExpression` node types remain completely dialect-neutral, as originally designed — only the *renderer* is dialect-aware, and only it needed to move to support mixing.
  - `NativeTranslation/MongoPipelineFactory` — the B2 template: `Create(stages, renderer)` walks the stages into a `BsonDocument[]` template (+ placeholder table); `Build(parameterValues)` deep-clones and substitutes per execution. Validates `$limit>0`/`$skip≥0` (throws `ArgumentOutOfRangeException`, matching EF).
  - `NativeTranslation/MongoStreamingEntityMaterializerRewriter` + `StreamingEligibility` (+ the now-dormant `BsonRowReader`) — forward-only `IBsonReader` → POCO materialization for eligible entities (no DOM build). **One-pass materializer (SP7 / EF-322).** The rewriter compiles `Func<QueryContext, IBsonReader, BsonDeserializationContext, TEntity>` reading one document straight off the cursor's own reader, wrapped in a per-execution `MongoEntityMaterializerSerializer<TEntity>` that is supplied as the `Aggregate<TEntity>` **output serializer** (`PipelineDefinition.As<…,TEntity>`) — so deserialization *is* materialization, with **no** intermediate `RawBsonDocument` and **no** second reader/context (the pre-SP7 two-pass shape). Per-property reads reuse the incoming `BsonDeserializationContext` and call the generic `IBsonSerializer<T>.Deserialize` (no boxing). Because the driver eagerly deserializes cursor batch-1 during `.Aggregate()`, `QueryingEnumerable` initializes the state manager **before** creating the cursor (tracked-path correctness — see `QueryingEnumerable.MoveNextHelper`). Effect: native allocation ~−54–72% (whole-entity no-track 19.1→5.4 MB, ~1.73× the raw-driver floor; see `benchmarks/.../results/perf-baseline.md` SP7 section). **Which shapes are streaming-eligible is unchanged** (still `StreamingEligibility.IsEligible` + `AllPendingLookupsAreStreamable`) — SP7 changes only *how* an eligible shape materializes; the `NativeOnly` pass-set is identical to pre-SP7. The `RawBsonDocument` streaming branch + `BsonRowReader` are retained but now unreachable (candidate removal). At SP7 time, owned-nav whole-entity queries still fell back to driver-LINQ entirely (out of SP7 scope), so the one-pass path fired only for flat whole-entity shapes then. **As of EF-322 Task 2, an owned SINGLE-REFERENCE whole-entity query now also goes native and streams via this SAME one-pass path** (see the dedicated "Owned single-reference whole-entity queries" note above) — the rewriter's owned/collection recursion is no longer dormant for that shape. **The EF-322 owned-collection slice extends this further:** an owned COLLECTION whole-entity query (flat, mixed, shared-CLR-type, or empty) now also goes native and streams via this SAME one-pass path (see the dedicated "Owned-collection whole-entity queries (EF-322)" note above); only a collection whose element itself carries a further navigation, or a collection-of-collections, still routes to the DOM shaper instead of streaming (per that note's `StreamingEligibility` narrowing) — not a fallback, just the DOM floor.
  - `Infrastructure/MongoQueryMode` (`Native`/`DriverLinq`/`NativeOnly`) — the user-facing gate option (`UseQueryMode`).
  - `NativeTranslation/NativeCardinalityBinder` (EF-SP4) — populates `MongoSelectDefinition.Cardinality` for entity reducers (`TryBindReducer`: synthesizes the reducer `$limit`) and scalar aggregates (`TryBindAggregate`: synthesizes the aggregate, and for `All`/predicate-bearing `Count`/`Any` injects the (negated) predicate as a `$match` conjunct via `AddPredicateConjunct`). As of EF-347 Task 3, a predicate-injecting aggregate following a `Take`/`Skip` already on the same select goes native too — `AddPredicateConjunct` always ANDs into (or appends after) the TAIL of the ordered `PipelineOps` list, i.e. after any already-recorded `$skip`/`$limit`, never hoisted ahead of it — see the Non-canonical Skip/Take as-built note above. The only guard `TryBindReducer`/`TryBindAggregate` still own is the pre-existing `HasTerminalOperator` check (a reducer/aggregate after `GroupBy`/`Distinct`/a set-op/`SelectMany` still falls back) — see the scalar-cardinality as-built note above.
  - `Expressions/MongoCardinality` (on `MongoSelectDefinition.Cardinality`) — the dialect-neutral IR for "this select terminates in a reducer or aggregate rather than a row sequence": `Reducer`/`Aggregate` kind, `Selector` field-ref, `EmptyBehavior`/`EmptyValue`, `ResultType`.
  - `NativeTranslation/Stages/MongoCountStage` / `MongoGroupAccumulatorStage` — typed IR stages the lowerer appends for `Count`/`LongCount`/`Any` (`$count`) and `Sum`/`Min`/`Max`/`Average` (`$group` with the matching accumulator) respectively, mirroring how `MongoProjectStage` is appended for projections.
  - `NativeTranslation/NativeGroupByBinder` (EF-SP6) — populates `MongoSelectDefinition.Grouping` for `GroupBy(key).Select(aggregate)`, mirroring `NativeCardinalityBinder`'s role for scalar aggregates. `TryBindGroupKey` parses the key (scalar `MemberExpression` / composite anonymous `NewExpression`) into `PendingGroupKey`; `TryBindGroupProjection` + `TryBindAccumulator` parse the aggregate `Select`, finalize the `MongoGrouping`, and emit the flattening projections. Holds the two correctness guards — `HasDefaultKeySerialization` (reject value-converter / non-default-`BsonRepresentation` keys) and `IsGroupingSource` (accumulator source must be the grouping parameter `g`).
  - `Expressions/MongoGrouping` (on `MongoSelectDefinition.Grouping`) — dialect-neutral `$group` IR: `Key` parts (`MongoGroupingKeyPart`; null `Name` ⇒ scalar `_id`, named parts ⇒ composite `_id` sub-doc) + `Accumulators` (`MongoGroupAccumulator`: output field, operator `$sum`/`$avg`/`$min`/`$max`, null operand ⇒ `$sum:1`). Lowered by the `MongoSelectLowerer` group branch to `NativeTranslation/Stages/MongoGroupStage`, rendered by `MongoPipelineFactory.RenderKeyedGroup` (composite → `_id` sub-document, else bare field-ref) in the aggregation-expression dialect.
  - `Expressions/MongoElementRefExpression` (EF-SP6) — a raw document-element reference by (possibly dotted) path with **no** backing `IProperty`, rendering as `"$" + Path` in the aggregation-expression dialect. The GroupBy flattening `$project` uses it to read each group output — `_id` (scalar key), `_id.<Name>` (composite sub-key), or an accumulator output field — up into a top-level result alias for the DOM shaper.
  - `EnumerableMethods` (provider root, `src/MongoDB.EntityFrameworkCore/EnumerableMethods.cs`) — the provider's own port of EF Core's `internal` `EnumerableMethods`; **extended for EF-SP6** with the `Count`/`LongCount`/`Sum`/`Average`/`Min`/`Max` selector members (`IsSumWithSelector` etc.) that `NativeGroupByBinder.TryBindAccumulator` matches grouped aggregates against (both the `Enumerable` and the EF-lowered `Queryable`-over-`AsQueryable()` forms).
  - `Visitors/MongoShapedQueryCompilingExpressionVisitor.ExecuteAggregate` / `TryBuildAggregateFactory` — compile-time construction of the scalar-result execution path: builds the pipeline factory, applies `MongoCardinality.EmptyBehavior`/`EmptyValue` around the single-row-or-absent aggregate result, and deserializes via `DeserializeScalar<TResult>` (non-int scalar coverage, e.g. `decimal`/nullable numerics).
  - `SingleValueEnumerable` — the `IEnumerable<T>` wrapper the native reducer/aggregate path returns so EF Core's own base cardinality reduction (First/Single throw/empty semantics) runs unmodified over a zero-or-one-element sequence.
- `Visitors/MongoEFToLinqTranslatingExpressionVisitor` — converts the residual EF expression into a tree the driver's LINQ v3 provider understands (`Mql.Field`, parameter resolution, `As<T>(serializer)`).
- `Visitors/MongoProjectionBindingRemovingExpressionVisitor` — replaces `ProjectionBindingExpression` nodes with concrete index-based reads from a `BsonDocument`.
- `Visitors/MongoMixedProjectionBindingRemovingExpressionVisitor` — sibling of the above used on the mixed path (projection contains entity references LINQ v3 can't handle); `MongoShapedQueryCompilingExpressionVisitor` strips the trailing `Select` and dispatches to this visitor so the shaper runs client-side over full `BsonDocument`s.
- `Expressions/MongoCollectionExpression`, `EntityProjectionExpression`, `RootReferenceExpression`, `ObjectAccessExpression`, `ObjectArrayProjectionExpression` — provider-specific expression nodes for collection roots, nested-document access, and entity shape.
- `MongoExecutableQuery` + `QueryingEnumerable` — the compiled-query handoff. `QueryingEnumerable` calls `MongoClientWrapper.Execute(MongoExecutableQuery)` and applies the shaper. For the native path `MongoExecutableQuery` carries `NativePipeline` (the built `BsonDocument[]`), `Streaming`, and `Session` (internal); for the fallback it carries the driver-LINQ `Query` expression.
- `Factories/*` — EF Core DI factories registered in `MongoServiceCollectionExtensions.AddEntityFrameworkMongoDB()`.

## Boundaries with adjacent areas

- **vs Storage.** Query stops at the executable query — it produces *data*: either a native `BsonDocument[]` pipeline (`MongoExecutableQuery.NativePipeline`) or a driver-LINQ expression. `MongoClientWrapper.Execute(...)` (Storage) owns execution: it runs `collection.Aggregate(nativePipeline)` for the native path and hands the expression to `IMongoQueryProvider` for the fallback. Cursor lifecycle, transaction/session binding, retries are Storage + driver. Never call `IMongoCollection<>.Aggregate(...)` directly from Query — build the `BsonDocument[]` and let the wrapper run it.
- **vs Storage — bulk `ExecuteUpdate`/`ExecuteDelete` (EF9+) uses a *second*, deliberately different seam.** Reads cross to Storage as **data** (a `MongoExecutableQuery`); bulk crosses as **behavior** — `MongoShapedQueryCompilingExpressionVisitor.CreateBulkPlan<TSource>` builds a `MongoBulkPlan` (Storage) carrying `Func<QueryContext, …>` translation delegates, and `MongoBulkOperationExecutor` (Storage) invokes them at runtime. This is intentional: bulk filter/update translation is parameter-value-dependent, so it must be deferred and re-run per execution. The translation helpers (`BuildFilter`/`BuildUpdate`/`BuildIdDocumentQuery`) stay here in Query; only their rendered results cross the boundary. Don't "fix" the bulk seam to look like the read seam — they differ for this reason.
- **vs Serializers.** Query needs an `IBsonSerializer` for every materialized projection result — it asks `BsonSerializerFactory` (Serializers area). Query should never instantiate serializers directly.
- **vs Metadata.** `IEntityType`, `IProperty`, navigation info come from Metadata. Query reads `GetElementName()`, `GetBsonRepresentation()`, `GetDiscriminator*()` etc. — it doesn't write them.
- **vs the driver's LINQ v3 provider.** Only the **fallback** path uses it: Query produces a driver-LINQ expression (types from `MongoDB.Driver.Linq`) and hands it off, and the driver builds that pipeline. The **native** path bypasses the driver's LINQ provider entirely — the provider builds the `BsonDocument[]` itself (`MongoSelectLowerer` + `MongoQueryLanguageRenderer` + `MongoPipelineFactory`) and only uses the driver as a BSON/cursor/protocol library via `Aggregate`. The deliberate, stable boundary is **our query tree → `BsonDocument[]` → `Aggregate`**; we do **not** build on the driver's internal AST.

## Common pitfalls

- **Allowed method sources are strict.** Only `Queryable`, `MongoQueryableExtensions`, and `MongoDB.Driver.Linq.MongoQueryable` methods are accepted. Anything else throws `NotTranslatedExpression` early.
- **VectorSearch extraction.** `VectorSearch(...)` must be pulled out of the tree before EF's nav-expansion runs (it crashes nav-expansion otherwise) and stitched back in after. If you change preprocessor ordering, re-check this dance.
- **ProjectionMapping discipline.** The `_projectionMapping` keys (`ProjectionMember`s) must match exactly what the shaper expects. A mismatch between the post-processor mapping and the shaper compilation produces silent wrong-results, not crashes.
- **`MongoQueryExpression.CapturedExpression`** must be a *complete* method chain — set once at the tail of `MongoQueryableMethodTranslatingExpressionVisitor.VisitMethodCall`. Setting it mid-chain truncates the query.
- **Reference-equality on `MethodInfo`.** Translators that match by `MethodInfo` must use canonical constants — `QueryableMethods` for the top-level dispatch in `MongoQueryableMethodTranslatingExpressionVisitor`, `EnumerableMethods` inside the projection-binding visitors, and the driver's `*Method` reflection classes where the bridge to driver-LINQ needs them; open vs. constructed generic methods compare unequal.
- **Unsupported shapes are detected, not silently translated.** Two layers: the base visitor early-fails truly untranslatable shapes; and for the *native* path, anything `NativeSlotPopulator` does not lower into a slot calls `mongoQ.Select.MarkNotNativelyRepresentable()` (sets the internal `_hasUnsupportedOperator` flag, which drives `Route` to `NativeRoute.Fallback`) so the gate falls back (or throws under `NativeOnly`) rather than emitting a pipeline that silently drops the operator.
- **The native catch-all whitelist must stay in sync.** `NativeSlotPopulator.PopulateNativeSlots` lowers seven slot operators (`Where`/`OrderBy`/`OrderByDescending`/`ThenBy`/`ThenByDescending`/`Skip`/`Take`) into ops on `MongoSelectDefinition`'s ordered `PipelineOps` list (`MongoMatchOp`/`MongoSortOp`/`MongoSkipOp`/`MongoLimitOp` — replacing the original single `Predicate`/`Orderings`/`Offset`/`Limit` slots as of EF-347; see the Non-canonical Skip/Take as-built note above). The `else` catch-all in `PopulateNativeSlots` marks **everything else** non-native by default (correctness-safe: worst case is a missed optimization + fallback, never a wrong result), *unless* `IsNativeRepresentableSlotOperator` returns `true` for the operator. That predicate lists the seven slot operators **plus** the `Translate*`-override operators (`Select`, `OfType`, `Distinct`, `Union`, `Concat`, `SelectManyWithCollectionSelector`) **plus** the scalar-cardinality / `GroupBy` operators added by later sub-projects (`Count`/`LongCount`/`Sum`/`Min`/`Max`/`Average`/`Any`/`All`, the `First`/`Single` family, and `GroupBy*` — EF-336/EF-344/EF-347). Membership is exactly what suppresses the catch-all — for the seven slot operators it means "already populated into a slot," and for the `Translate*`-override operators it means "decided by its own `Translate*` override, don't clobber it." `Union`/`Concat` (EF-347 slice 2) follow the same pattern as `Select`/`OfType`/`Distinct`: `TryTranslateSetOperation` (backing both) always decides representability itself (attaching a `SetOperation` or calling `MarkNotNativelyRepresentable()`), so both are whitelisted here purely to stop the catch-all from re-deciding — see the set-ops as-built note above for the full mechanism. The QMTEV's `TranslateSelect` override calls `NativeProjectionBinder.TryPopulateNativeProjection`, which populates `MongoSelectDefinition.Projection` for a representable shape (terminal member-access anonymous/DTO projection) — leaving `Route` to resolve to `NativeRoute.Projection` — and otherwise calls `MarkNotNativelyRepresentable()`; `TranslateOfType` (EF-347) builds a discriminator `$eq`/`$in` conjunct via `TryBuildDiscriminatorPredicate` and adds it to the tail `$match` via `AddPredicateConjunct` for a representable TPH narrowing (the native DOM shaper already materializes derived types polymorphically via EF's own `MaterializationCondition`, so the conjunct is the only piece native was missing), falling back to `MarkNotNativelyRepresentable()` only when the target type has no discriminator property (non-TPH); `TranslateDistinct` (EF-347 Task 2) follows the same pattern — it calls `NativeGroupByBinder.TryBindDistinctFromProjection` to convert an already-populated `Projection` into a degenerate `Grouping` (key-only, zero accumulators), falling back to `MarkNotNativelyRepresentable()` when there is no native `Projection` to convert (bare-scalar or whole-entity `Distinct`) or a projected key fails `HasDefaultKeySerialization`. `TranslateSelectMany` (EF-347 slices 3–4, the 2-arg collection-selector + result-selector overload EF's nav-expansion always normalizes to) is whitelisted here for the same reason — it first tries `NativeSelectManyBinder.TryBindBareNavUnwind` (the slice-4 bare-nav shape, setting `UnwindSource` only) and, failing that, `NativeSelectManyBinder.TryBind` (the slice-3 inner-`Select` shape, setting `UnwindSource` + `Projection` together) to decide representability itself, but unlike every other `Translate*`-override operator listed here, EITHER binder returning `false` does **not** call `MarkNotNativelyRepresentable()` at all — `TranslateSelectMany` just returns `null`, so an unsupported SelectMany shape reaches EF Core's own translation-failure path directly rather than the graceful-fallback machinery this whitelist otherwise protects (see the SelectMany as-built note above for why that is intentional, not an oversight). The slice-4 bare-nav shape's real projection is bound later still, by the SEPARATE `TranslateSelect` pending-SelectMany branch described in the post-terminal-invariant note above — that branch is not part of this whitelist at all, since it runs inside the already-whitelisted `Select` operator's own override. **Adding a new native operator means:** for a slot-style operator, update BOTH `NativeSlotPopulator.PopulateNativeSlots` (populate the slot) *and* `IsNativeRepresentableSlotOperator` (add it to the whitelist); for a `Translate*`-override-style operator (like `Select`/`OfType`), add its override *and* add it to `IsNativeRepresentableSlotOperator` so the catch-all doesn't override its decision. Miss either path and the operator is silently dropped on the native pipeline or double-decided.
- **The QMTEV `Translate{Where,OrderBy,ThenBy,Skip,Take}` overrides are inert (`=> null`).** Native slot population is delegated to `NativeSlotPopulator.PopulateNativeSlots` at the `VisitMethodCall` fall-through, because routing these through `base.VisitMethodCall` rebuilds a fresh `MongoQueryExpression` per operator (slots don't accumulate). **Do not add these operators to the `VisitMethodCall` switch** without first removing their `NativeSlotPopulator.PopulateNativeSlots` handling — otherwise slots double-populate.
- **The lowerer is BSON-free; the renderer/factory own BSON.** `MongoSelectLowerer` produces only typed `MongoPipelineStage`s; all `BsonDocument` construction lives in `MongoQueryLanguageRenderer` (the `$match` body) and `MongoPipelineFactory.Create` (the stage-walk: `{$match}`/`$sort`/`$skip`/`$limit`/`$lookup`/`$unwind`).
- **Composite-PK key access is NOT native** (strict spike parity) — `MongoExpressionTranslator` rejects multi-property-PK member access, so such predicates/sort fall back. `LookupExpression.GetFieldPath` (`_id.<prop>`) exists for the (still-deferred) composite-PK Include `$lookup` only.
- **Non-positive paging matches EF's contract.** `MongoPipelineFactory.Build` validates `$limit > 0` / `$skip ≥ 0` and throws `ArgumentOutOfRangeException` (client-side, like the driver) — do not emit `{$limit: 0}` (MongoDB rejects it server-side). Property-less primitive values (Skip/Take counts have `forSerialization == null`) serialize via `BsonValue.Create`, not a property serializer.
- **MQL shape cannot prove a query went native.** For filter/sort/paging the native and driver-LINQ pipelines are structurally identical (`$match`/`$sort`/`$skip`/`$limit`), so asserting those substrings under `Native` mode passes even on fallback. The **only reliable "goes native" signal is `NativeOnly` mode**: native-capable ⇒ succeeds; otherwise ⇒ throws `NativeTranslationNotSupportedException`. (Several early gate tests were false positives masked by structurally-identical fallback MQL.)
- **EF Core query cache.** Compiled queries are cached by EF Core by expression-tree shape; if you change a translator's output for a previously-translatable tree, you've quietly invalidated user caches.
- **Multi-EF guards.** Some visitor signatures changed between EF8/EF9/EF10. For representative guard shapes elsewhere in the tree see `Storage/MongoTypeMappingSource.cs` (`#if EF8 || EF9`), the `ChangeTracking/StringDictionaryComparer*.cs` pair (legacy vs. EF10 split), and the `ChangeTracking/ListOf*Comparer.cs` files (`#if EF8`); in Query itself, `QueryingEnumerable.cs` has a `#if !EF8` block.

## How to test

Most query tests assert the **rendered MQL pipeline** rather than executing against a server. The functional and specification tests both have helpers (`AssertMql(...)`) that capture the MQL via `TestMqlLoggerFactory`. Unit tests use **plain xUnit `Assert.*`** (FluentAssertions is not referenced anywhere in the test projects).

**Proving the native path.** `AssertMql` shape does **not** distinguish native from driver-LINQ for filter/sort/paging (identical pipelines) — to assert a query genuinely goes native, run it under `MongoQueryMode.NativeOnly` and assert it **succeeds** (a fallback shape would throw `NativeTranslationNotSupportedException`); to assert a shape falls back, assert it **throws** under `NativeOnly` (or, for `Include`, assert the driver `_outer`/`_inner` shape under `Native`). The spec suite has a **test-only** coverage instrument: `MONGODB_EF_NATIVE_ONLY=1` flips all spec contexts to `NativeOnly` (via `MongoTestStore.AddProviderOptions`), so the pass/fail set is the "what runs native" report. Native unit tests live under `tests/MongoDB.EntityFrameworkCore.UnitTests/Query/NativeTranslation/`; the `QueryModeGate*` functional tests exercise the gate end-to-end.

```bash
dotnet test MongoDB.EFCoreProvider.sln -c "Debug EF10" --no-build \
  --filter "FullyQualifiedName~Query"
```

- Unit tests: `tests/MongoDB.EntityFrameworkCore.UnitTests/Query/`
- Functional tests (real DB): `tests/MongoDB.EntityFrameworkCore.FunctionalTests/Query/` — golden-path translations and end-to-end materialization.
- Specification tests (EF Core conformance, Northwind suite): `tests/MongoDB.EntityFrameworkCore.SpecificationTests/Query/` — pattern is to override the upstream test and assert the produced MQL.
