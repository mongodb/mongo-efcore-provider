# Query — AGENTS.md

## Scope

Translates `IQueryable<T>` against MongoDB-backed DbSets into MongoDB aggregation pipelines. There are **two translation paths**, chosen at compile time by the `MongoQueryMode` option (see *the gate* below):

1. **Native (default).** For the supported slice, the provider **generates the aggregation `BsonDocument[]` pipeline itself**, from a structured query expression tree, and runs it via `IMongoCollection<…>.Aggregate`. It does **not** go through the driver's LINQ provider for these.
2. **Driver-LINQ (gated fallback).** For everything outside the native slice, the provider hands a driver-LINQ expression to the MongoDB C# driver's LINQ v3 provider, exactly as it always did.

Per the versioning rubric (see the top-level `AGENTS.md`): which path a query takes, and the exact MQL a supported query emits, are implementation details, not contract. A fallback → native transition with unchanged results is never a breaking change. The exception *type* thrown for an unsupported shape is likewise not contract.

### What's native today (capability summary, not an exhaustive shape list)

- **Filter / sort / paging** over a whole-collection scan, always: predicate breadth includes nullable equality/`== null`, client-collection `Contains` → `$in`/`$nin` **and its mirror `arrayField.Contains(constant)`** (EF-382 — a distinct `MongoArrayContainsExpression` node, *not* a reused `Equal`, so the aggregation renderer refuses it rather than silently testing whole-array equality), `StartsWith`/`EndsWith`/`Contains` → `$regularExpression`, field-to-field and arithmetic comparisons → `$expr`, numeric casts, `Nullable<T>.Value`/`HasValue`, and owned-collection `Any`/`All` quantifiers and `.Count`/`.Count(pred)` comparisons. `Not` over a subtree with **no** query-dialect form (a field-to-field comparison, arithmetic, an `$in`, a conjunction of bare fields) no longer declines: `MongoQueryLanguageRenderer.RenderUnary` falls through to `MongoAggregationExpressionRenderer` and emits `{$expr: {$not: [...]}}` (EF-396). This is a *top-level* widening only — `IsQueryDialectRenderable` still rejects those shapes, because `$expr` is illegal inside `$elemMatch`. Non-canonical `Skip`/`Take` placement (not just the fixed `match → sort → skip → limit` shape) is native.
- **Projections.** A terminal anonymous-type/DTO `Select` over top-level member accesses, arithmetic, casts, and (filtered) collection counts goes native via `$project`. A **bare** (non-`new{}`) leaf also goes native when it is *path-addressable* — a non-dotted scalar, primitive-collection, owned-array, or computed (arithmetic/cast/count) leaf under a reserved `_v` alias; a bare **dotted** leaf, and a computed leaf whose subtree *contains* a count reached through a dotted path, still fall back. A **widening** numeric `Convert` (`(long)x.I`, `(double)x.I`) is admitted as a bare projection leaf (EF-410) — it is a lossless `$toX`, unlike a narrowing cast. A `Nullable<T>.Value` projection leaf is native on the **read** side too (EF-402): `TryResolveFieldAccess`/`MongoProjectionBindingRemovingExpressionVisitor` peel the `.Value` and resolve the *nullable* property's own serializer, so a value-converted `.Value` leaf reads back through its converter instead of the underlying-type default. A computed sort key (arithmetic, a constant, a captured parameter, an owned-collection count) goes native via a synthetic `$set → $sort → $unset` field.
- **Scalar cardinality.** Reducers (`First`/`FirstOrDefault`/`Single`/`SingleOrDefault`) and scalar aggregates (`Count`/`LongCount`/`Any`/`All`/`Sum`/`Min`/`Max`/`Average`) go native via `$limit`/`$count`/`$group`, materializing through the DOM shaper (not the streaming one — see `NativeCardinalityBinder`). A reducer composed after `Take`/`Skip` (`Take(3).First()`, `Skip(2).Take(2).First()`) is native: the reducer's `$limit` is appended to the *tail* of the ordered op list and consecutive `$limit` stages narrow monotonically, so it never fights an already-recorded one. Falls back: `Contains`/`ElementAt`/`Last`, and a computed aggregate selector (the selector must be a plain member access).
- **`OfType`, `Distinct`, `GroupBy`.** `OfType<TDerived>()` over TPH goes native via a discriminator `$eq`/`$in` conjunct, including when the discriminator has a value converter/non-default `BsonRepresentation` — the predicate is built by serializing through the discriminator property's serializer (`MongoConstantExpression.ForSerialization`), the same transform `MongoEFDiscriminator` now applies to the driver-LINQ filter (EF-349), so the two paths agree. A **projected** `Distinct` goes native via a degenerate `$group`, including a **bare-scalar** projection (`Select(o => o.Country).Distinct()` — EF-395 removed `NativeGroupByBinder.TryBindDistinctFromProjection`'s `IsBareProjection` decline; pinned by `NativeDistinctTests.Bare_scalar_projection_Distinct_goes_native`); a **whole-entity** `Distinct` still falls back. `GroupBy(key).Select(aggregate)` goes native via `$group` + a flattening `$project`, DOM shaper only; computed keys/accumulator operands, a bare `GroupBy` terminating on `IGrouping`, and a `GroupBy` with a `resultSelector` fall back — `GroupBy`/`Distinct` keys with a value converter/non-default `BsonRepresentation` also fall back (`NativeGroupByBinder.HasDefaultKeySerialization`), unlike `OfType`: their flattened `_id` readback has no backing `IProperty` to apply the conversion/representation through, so there's no serializer path to make them agree.
- **Set operations.** Whole-entity, terminal `Union`/`Concat`/`Intersect`/`Except` over the same entity type go native (`Union`/`Concat` via `$unionWith`; `Intersect`/`Except` via a source-tagging pipeline, since Mongo has no direct set-difference stage). `Intersect`/`Except` have **no driver-LINQ baseline at all** (the driver itself can't translate them either), so an out-of-scope shape there hard-fails in *every* `MongoQueryMode`, not a graceful fallback. Trailing operators (`Where`/`OrderBy`/`Skip`/`Take`/aggregates/reducers, and a trailing projection) after a set op, and set operations over already-projected operands, also go native — including a **bare** projected operand (`Select(c => c.CustomerID).Union(...)`), admitted on par with a wrapped one since EF-395: the separate `HasArrayProjectionLeaf` conjunct in `IsPlainProjectedSelect` is what actually protects the whole-projected-document dedup/source-tagging key, and it fires identically for a bare or wrapped array leaf. A single-level **collection `Include`** combined with a set op is native too: EF hoists the (necessarily identical) operand `Include`s to apply *after* the combinator, and the lowerer defers its whole `$lookup` block past the set-op stage and `TrailingOps` so the join runs once over the combined, already-deduped stream — emitting it before the `$unionWith` joined only source1's rows and left operand rows with an empty collection (and, because the joined array then differed per side, also defeated the `$$ROOT` dedup). A **reference** `Include` after a set op still falls back. Chained set ops, and `GroupBy`/`OfType`/`SelectMany` after a set op, still fall back.
- **`Include`.** Single-level collection `Include` is native via a flat `$lookup` (no `$unwind`) after the canonical filter/sort/paging stages, DOM shaper (collection navs aren't streaming-eligible). Single-level reference `Include` is native for a narrow recognized shape: a lone reference `Include` on the query root, single-property FK/PK, no sibling reference `Include`, no `ThenInclude` past the looked-up document, and no query filter on the target *in any spelling* (anonymous, TPH-inherited, or an EF10 named filter) — the query-filter decline is keyed on the join's inner select being a bare collection scan, not on target metadata (a metadata-only check was measured incomplete for TPH-inherited/EF10-named filters and returned silently wrong rows). `ThenInclude`/multi-level, sibling reference `Include`s, and a filtered/non-bare-scan inner still fall back. A multi-hop (3+) reference-join chain scopes its `$lookup` correctly by resolving each hop's join-hop kind (root vs. transitive) from the *structure* of the key-selector's receiver (see the join-hop classification invariant below), not from depth or CLR type. See `Ef372DeepReferenceIncludeTests`/`Ef373InterleavedPagingTests`/`Ef379RootNavigationMisroutingTests` for the exact boundary and its history of near-miss defects.
- **`SelectMany`.** Both owned (embedded) and reference (cross-collection, FK-correlated) collection `SelectMany` go native for a wide shape matrix: projected result, whole-inner-entity result, an inner-only filter, and a filter correlated back into the outer element (rendered via `$expr`). A **computed** projected leaf is native even when it mixes the outer/root scope and the inner/unwound-element scope (`(o.Rank * i.Price) + 1`), and the one-arg `SelectMany(o => o.Items).Select(i => i.Price * 2)` form — which EF folds to a *bare* computed body — has its own binder arm under the `_v` tier (EF-422; arithmetic bare bodies only, a bare member access still falls back). A **whole owned-collection element that itself carries nested owned members** is native (EF-353): the element shaper re-roots at the unwound document, so nested navigations resolve inside it. The owner-key/array-ordinal sentinels the `$replaceRoot` merges in are nested one level under a single reserved wrapper field (`MongoReplaceRootStage.ShadowField`, EF-428) so they can no longer collide with a real stored top-level element name — the wrapper name itself is the one remaining collidable name, and it is guarded. Reference-collection `SelectMany` has **no driver-LINQ oracle at all** (the driver's own LINQ v3 rejects cross-collection `SelectMany` outright), so every unsupported reference shape, and every operator composed after a native reference `SelectMany`, hard-fails in every mode. See `NativeSelectManyTests` for the exact supported/unsupported shape matrix (nesting depth, filtering, correlation, per-form composition rules all differ in ways too detailed to enumerate here).
- **Atlas Vector Search.** `VectorSearch(...)` is native by default; falls back only when the native predicate translator can't express the `preFilter`, or the query vector/limit/options argument is neither a query parameter nor a constant.
- **Owned navigations.** A whole-entity query over an entity with owned single-reference and/or owned-collection navigations (however nested/mixed) is native and — except where the collection element itself carries a further navigation, or is a collection-of-collections — streams via the one-pass materializer. A predicate/sort/projection leaf reaching through one or more owned single-reference hops to a scalar is native (single-scope only; not inside a two-scope `SelectMany`-unwind translator). This includes reaching through such a hop from INSIDE an owned-collection quantifier's (`Any`/`All`) or owned `SelectMany`'s element-scoped predicate (EF-424) — `TryResolveOwnedFieldPath` builds the dotted path relative to its own scope entity type (joining each hop's own containing element name, mirroring `TryResolveOwnedCollectionPath`), not via a document-root-relative path, so it composes correctly with the caller's own prefix regardless of how deep that scope is nested.

### Durable cross-cutting invariants

These are the rules a future implementor of a *different* native-query feature needs to know to avoid reintroducing a bug this file's history already paid for. (Bug provenance, ticket numbers, and measurement tables have been deliberately dropped — see git history / `NativeTranslation/*Tests` for that detail.)

- **Post-terminal gating.** Once a select has a *terminal* operator attached (`GroupBy`, `Distinct`, a set op, or a `SelectMany` unwind — collectively `MongoSelectDefinition.HasTerminalOperator`), every subsequent operator must explicitly decide whether it can still go native. Two catch-all sites already gate broadly (`NativeSlotPopulator.PopulateNativeSlots` for the seven slot operators; `NativeCardinalityBinder.TryBindAggregate`/`TryBindReducer`); every operator with its *own* `Translate*` override (`Select`, `GroupBy`, `OfType`, `SelectMany`) bypasses those catch-alls and must replicate the check itself, or a real navigation/property can be silently resolved against the wrong scope, or a `$group`/`$unwind` can be silently dropped from the pipeline while its shaper still expects it. `IsSetOpTerminalOnly` narrowly relaxes *only* the two catch-all sites, to admit operators trailing a set op. A gate must call the same structural predicate a companion rewrite relies on, not restate its own copy of "what's reachable" — a gate that is *wider* than what the rewrite actually handles is a silent-wrong-data trap that has recurred more than once in this codebase.
- **`SelectMany`/reference-collection/`Intersect`/`Except` have no driver-LINQ baseline.** For these three families, an out-of-scope shape returns `null` (EF Core's own translation-failure path) rather than calling `MarkNotNativelyRepresentable()` — because there is no working driver-LINQ pipeline to land gracefully on for that shape. Confusing the two dispositions either crashes on a `null` shaper rebuild the fallback can't perform, or silently pins a shape to the wrong exception family.
- **Scope must be resolved by parameter identity, never by member name.** Anywhere a translator must distinguish an "outer" scope from an "inner"/element scope (SelectMany two-scope binding, correlated-beyond-FK/outer filters, quantifier element predicates), a member access must be routed by `ReferenceEquals` against the scope's own parameter — not by matching the member's *name* against the target type's properties. Two types sharing a property name (`Item.Name` vs `Owner.Name`) is the standing regression test for this; a name-based router silently mis-scopes the access instead of resolving or declining it correctly.
- **Structural classification beats metadata/depth/CLR-type shortcuts.** Several gates were once written as "look at the model" or "count the nesting depth" or "compare CLR types," and each was later found incomplete: a TPH-inherited or EF10-named query filter isn't visible through `GetQueryFilter()`; join-hop depth doesn't distinguish a root-scoped hop from a transitive one; a self-referencing entity type defeats a CLR-type check. Where a shape needs classifying, prefer walking the actual expression-tree structure (e.g. the join's inner select shape, or the key selector's own receiver chain) over any of these shortcuts. These translation-time misclassifications are also **mode-independent** — they hit `Native` and `DriverLinq` identically, since the bug is in how the tree is built, before `MongoQueryMode` is even read; `UseQueryMode(DriverLinq)` is not an escape hatch for one.
- **The negator's contract is exact complement or decline, never an approximation** (`NativeTranslation/MongoExpressionNegator.cs`). The one fact worth restating here: `$eq`/`$ne` may be *inverted* because they partition every BSON value including missing/null, but the four relational operators must be `$not`-**wrapped**, never inverted, because `{$gt}`/`{$lte}` etc. match neither a missing nor an explicitly-null field — inverting one would silently flip what an `All` quantifier reports on an ordinary ragged array. An array-count comparison (rendered as an `$exists` index test) is the *documented exception in the other direction* — invert it, don't wrap it — because that rendered form **does** partition the value space. The general rule is "ask whether the *rendered* pair partitions the value space," not "relational operators are always wrapped." `MongoExpressionNegator` ↔ `MongoQueryLanguageRenderer.IsQueryDialectRenderable` ↔ `RenderNode` must change together (a node the negator can produce but the renderer/classifier don't agree on is a hard failure at execution time, not a decline) — see the negator's own class remarks for the full mechanism.
- **A node kind that needs different handling at 3+ existing call sites must be a sealed sibling type, not a bool flag** (`MongoFilteredSizeExpression` next to `MongoSizeExpression`; `ArrayAliasProjectionExpression` next to `ObjectArrayProjectionExpression`). A pattern that names the base type simply doesn't match the sibling, so the sites that must *not* treat it the same way fail closed by construction; a flag would leave each site wrong by default and correct only if a future editor remembered to check it.
- **`$expr` inside `$elemMatch` is a hard server error, not a slow path.** Anything that can end up nested inside an `$elemMatch` (a quantifier's element predicate, a negated one) must be rejected at the query-dialect classifier (`IsQueryDialectRenderable`) rather than allowed to fall through to the `$expr` aggregation-expression renderer — a field-to-field comparison or arithmetic expression has no query-dialect form and must decline, not render as `$expr`, in that position.
- **`$ifNull` around `$size`/`$filter` is mandatory, not defensive.** `$size` (and the `$filter` a predicated count wraps) is a hard server error — not a wrong answer — when evaluated against a missing or explicitly-null array. Every aggregation-dialect array-size expression must wrap the path in `$ifNull: [..., []]`.
- **Alias-agreement and sibling-readability for mixed projections** (`NativeProjectionBinder.IsNativeArrayProjectionLeaf`/`IsWholeDocumentReadableLeaf`). The native shaper is built alias-addressed at translation time, but native-vs-fallback is decided later; on a late fallback the pipeline degenerates to `aggregate([])` and that same alias-addressed shaper reads a *whole document* instead. So (1) an array projection leaf's alias must equal the navigation's own document path (a *renamed* alias breaks the late-fallback read, silently, returning an empty collection) — root-declared, single-hop only; and (2) once any array leaf is admitted, every sibling scalar/computed leaf in the same projection must *also* be whole-document-readable (alias equals its own element name) or the whole projection must decline before mutating anything — otherwise a computed sibling whose alias happens to collide with a real stored field name reads that field's raw value instead, silently, under a late fallback. Both rules exist because loosening either one independently reopened a real silent-wrong-data bug; see `NativeArrayProjectionTests`.
- **`Route == Projection` (or similarly-scoped state) is often load-bearing for exactly one of two reasons: confining a new native case away from a mixed shape, or letting a re-entrant visitor recognize its own prior output.** Both patterns recur in `MongoProjectionBindingExpressionVisitor` — an arithmetic-leaf registration gated on `Route == Projection` so a *mixed* entity+computed shape still falls through to the ordinary mixed shaper untouched; and a `ProjectionBindingExpression{Index:not null}` passthrough gated the same way so the mandatory EF-synthesized unwrap-`Select` after a native `SelectMany` can re-enter the shaper this visitor already built, without accidentally passing through a case `GroupBy`/`Distinct` had already declined.
- **Guards that decline a shape can later become routers instead of walls.** More than once, a check that used to simply reject a shape (a `ReferencesParameter`/`ReferencesEnclosingScope` check declining any predicate that reached outside the expected scope) became the *signal* a later feature uses to pick between two translation strategies (single-scope vs. two-scope) rather than being weakened or removed. When widening a feature that currently declines on such a check, look for this pattern before assuming the check itself needs loosening.
- **MQL shape cannot prove a query went native** — already covered in Common Pitfalls below; the reference-`Include` and set-operation families are two specific places where a fallback path was deliberately made to emit the *same* MQL shape as the native one, so this pitfall bites harder than usual there.

## Pipeline at a glance

```
IQueryable<T>  (EF Core)
   │
   ▼  MongoQueryCompilationContext           (preserves the original LINQ tree; carries the MongoQueryMode)
   ▼  MongoQueryTranslationPreprocessor      (hoist final predicates; lift VectorSearch out before nav expansion)
   ▼  MongoQueryableMethodTranslatingExpressionVisitor (QMTEV)
   │      ├─ accepts only Queryable / MongoQueryableExtensions / MongoDB.Driver.Linq.MongoQueryable
   │      ├─ DELEGATES native slot population to NativeSlotPopulator.PopulateNativeSlots (the ordered
   │      │     PipelineOps list — match/sort/skip/limit ops recorded in arrival order, EF-347) and
   │      │     projection binding to NativeProjectionBinder.TryPopulateNativeProjection (Projection),
   │      │     both via MongoExpressionTranslator; either calls mongoQ.Select.MarkNotNativelyRepresentable()
   │      │     for any operator it does not lower into an op (catch-all) — see pitfalls
   │      └─ ALWAYS also captures the raw method chain (CapturedExpression) for the driver-LINQ fallback
   ▼  MongoQueryTranslationPostprocessor     (apply final ProjectionMapping)
   ▼  MongoShapedQueryCompilingExpressionVisitor  ── THE GATE (compile time, honors MongoQueryMode) ──
   │   if Native & Select.Route != Fallback & lower/render succeed → NATIVE PATH:
   │      MongoSelectLowerer  : PipelineOps → MongoPipelineStage[]  (emitted verbatim in arrival order, EF-347; then $lookup/$unwind/terminal)
   │      MongoQueryLanguageRenderer + PlaceholderTable : predicate → $match BSON; params → sentinels
   │      MongoPipelineFactory.Create : render ONCE into a template + placeholder table  (B2)
   │      compile streaming shaper (MongoStreamingEntityMaterializerRewriter) if StreamingEligibility, else DOM
   │   else (DriverLinq, or not representable, or NativeOnly→throws) → DRIVER-LINQ FALLBACK:
   │      MongoEFToLinqTranslatingExpressionVisitor rewrites CapturedExpression as driver-LINQ; DOM shaper
   ▼  MongoExecutableQuery + QueryingEnumerable
          ├─ NATIVE: factory.Build(parameterValues) → BsonDocument[] set as NativePipeline;
          │          MongoClientWrapper.Execute runs collection.Aggregate(pipeline) — streaming: Aggregate<TEntity> with the one-pass MongoEntityMaterializerSerializer (deserialize IS materialize, SP7); else BsonDocument DOM
          └─ FALLBACK: MongoClientWrapper.Execute hands the driver-LINQ expression to IMongoQueryProvider
          → IAsyncCursor; shaper turns each row into the requested CLR shape
```

B2 = the pipeline template is built **once at compile time** (lower + render → `MongoPipelineFactory`); only `factory.Build(parameterValues)` (clone-and-substitute the placeholder sentinels) runs per execution. The native-vs-driver and streaming-vs-DOM decisions are therefore **compile-time-deterministic** — there is exactly **one** shaper per query and **no** runtime dual-shaper dispatch.

## Key entry points

- `MongoQueryCompilationContext` — EF Core hook to preserve the original captured `IQueryable` so post-translation we can recover the user's intent (e.g. for diagnostics).
- `MongoQueryTranslationPreprocessor` — first phase. Notably, **`VectorSearch(...)` is extracted before EF's nav-expansion and re-inserted after** — nav expansion doesn't know about it.
- `Visitors/MongoQueryableMethodTranslatingExpressionVisitor` — the central LINQ-method dispatcher. Enforces the allowed-method-source set; **delegates native slot population and projection binding** to `NativeSlotPopulator`/`NativeProjectionBinder` (the `Translate*` overrides that would otherwise do this are inert — see pitfalls); captures the final method-chain expression on `MongoQueryExpression`.
- `Visitors/MongoShapedQueryCompilingExpressionVisitor` — **the compile-time gate**. Reads `MongoQueryMode`; consults `MongoSelectDefinition.Route` (the authoritative is-native decision for slot/projection representability) to decide native vs. fallback; builds the `MongoPipelineFactory` and compiles the native (streaming/DOM) shaper when `Route != NativeRoute.Fallback`, else compiles the driver-LINQ fallback shaper. Splits scalar vs. entity result paths. **The full is-native decision is centralized in `ClassifyNativeDisposition`** → `NativeDisposition {Native, Fallback, HardDecline}`, which reads three signals: `Route` (slot/projection representability), `IsGroupByFallbackUnsafe` (the GroupBy+Join wrong-data hard-decline), and an **unbound** vector search (present in the captured chain but not yet attached to `Select.VectorSearch`). Cross-collection `$lookup` streamability (`AllPendingLookupsAreStreamable`) is a **separate** streaming-vs-DOM axis, not an is-native signal — it only picks the streaming shaper for a query that is already native.
- **Native translation (`NativeTranslation/` + `Expressions/`):**
  - `Expressions/MongoExpression` + subtypes (`MongoFieldExpression`/`MongoConstantExpression`/`MongoParameterExpression`/`MongoBinaryExpression`/`MongoUnaryExpression`) + `MongoOrdering` — the dialect-agnostic `SqlExpression`-analog node hierarchy.
  - `Expressions/MongoQueryExpression` (+ `.Lookup.cs`) — the structured query tree: it **has-a** `MongoSelectDefinition` (reached via `MongoQueryExpression.Select`) holding the native scalar IR, **plus** the cross-collection `$lookup`/inner-collection state (`Lookups`/`IsJoinQuery`/`InnerCollections`, on `.Lookup.cs`) and the retained `CapturedExpression` + `ProjectionMapping` for the fallback.
  - `Expressions/MongoSelectDefinition` — the native-translation logical query IR: an ordered `PipelineOps` list (`MongoMatchOp`/`MongoSortOp`/`MongoSkipOp`/`MongoLimitOp`); once a set op is attached, a second ordered op list, `TrailingOps`, takes over for anything composed after it (`ActiveOps` flips between the two — see the post-terminal-gating invariant above); a dedicated `VectorSearch` slot (deliberately not part of `HasTerminalOperator` — a vector search is a root anchor, not a terminal, so ops keep recording into `PipelineOps` after it); and `Projection`, the dialect-neutral `MongoProjection` (alias → field-ref pairs) for a terminal projected `Select`. The `$lookup` state stays on `MongoQueryExpression` (entangled with the fallback shaper). The single authoritative is-native signal for slot/projection representability is the computed `Route` property (`NativeRoute`: `Fallback`/`WholeEntity`/`Projection`/`ScalarAggregate`/`GroupBy`).
  - `NativeTranslation/MongoExpressionTranslator` — EF predicate/key-selector body → `MongoExpression` (`TryTranslate`/`TryTranslateField`/`TryTranslateValue`); returns `false` for anything outside its acceptance set (the computed long tail — string transforms, date parts, `Math.*` — remains unsupported and falls back).
  - `NativeTranslation/MongoSelectLowerer` — the native IR → `MongoPipelineStage[]` (typed IR under `NativeTranslation/Stages/`), BSON-free; emits `Select.PipelineOps` verbatim in arrival order, then `TrailingOps`, then set-op/lookup/terminal stages; owns the lookup eligibility guards.
  - **`NativeTranslation/MongoQueryLanguageRenderer` + `NativeTranslation/MongoAggregationExpressionRenderer` — the dual-dialect renderer.** `MongoQueryLanguageRenderer` renders `MongoExpression` → `$match`-dialect BSON — the query/filter dialect, usable directly as a `$match` stage body. `MongoAggregationExpressionRenderer` renders to the **aggregation-expression** dialect inside `{ $expr: … }` — the only dialect that can express field-to-field comparisons and arithmetic. `PlaceholderTable` (shared by both) records parameter placeholders; both share one value-rendering path, `MongoValueRenderer`. The aggregation renderer also has arms for `MongoInExpression` (array-form `{$in: [needle, haystack]}`) and `MongoUnaryExpression` (`{$not: [...]}`) (EF-413), which is what lets those nodes appear as *values* — a computed sort key, a projection leaf, a filtered-count element predicate — not only as query-dialect predicates. Both carry a **truthiness** guard: a bare non-default-serialized bool field under `$not` or as an `$and`/`$or` operand renders fine but answers the wrong boolean, so `MongoExpressionTranslator.AllFieldsDefaultSerialized` gates it at four sites (`CanRender`'s `Not` arm, `CanRenderLogicalOperand`, `RenderUnary`, `CheckLogicalOperandSerialization`) — the render-time pair exists for callers that reach `Render` without `CanRender`.
    - **Per-subtree dialect selection is index-first, and the renderer — not the lowerer — owns it.** `RenderNode` keeps `&&`/`||` at the query level always, rendering each branch independently and combining via `CombineAnd`/`CombineOr`, so a mixed predicate like `a.Age > 21 && a.X == a.Y` keeps the indexable `Age` clause as a plain `$match` term and wraps only the non-query-expressible subtree in `$expr`. A comparison is query-native only when the left side is a bare field and the right side is a constant/parameter (`IsQueryNativeComparison`). This is a deliberate refinement over the original design (which put dialect choice in the lowerer) — with per-clause mixing required, only the renderer, walking the already-lowered dialect-neutral tree, can decide per-subtree; `MongoSelectLowerer` and the node types stay dialect-neutral. Note the query dialect is preferred *when it exists and is exact*, not unconditionally — several native shapes (`All` quantifiers, owned-array `.Count` comparisons) accept a full collection scan over an available index-friendly form specifically because the index-friendly alternative would require an operator inversion that returns wrong rows (see the negator invariant above); correctness always wins that trade.
  - `NativeTranslation/MongoPipelineFactory` — the B2 template: `Create(stages, renderer)` walks the stages into a `BsonDocument[]` template (+ placeholder table); `Build(parameterValues)` deep-clones and substitutes per execution. Validates `$limit>0`/`$skip≥0` (throws `ArgumentOutOfRangeException`, matching EF).
  - `NativeTranslation/MongoStreamingEntityMaterializerRewriter` + `StreamingEligibility` (+ the now-dormant `BsonRowReader`) — forward-only `IBsonReader` → POCO materialization for eligible entities (no DOM build). **One-pass materializer (SP7).** The rewriter compiles a delegate reading one document straight off the cursor's own reader, supplied as the `Aggregate<TEntity>` output serializer — deserialization *is* materialization, with no intermediate `RawBsonDocument`. Because the driver eagerly deserializes cursor batch-1 during `.Aggregate()`, `QueryingEnumerable` initializes the state manager **before** creating the cursor (tracked-path correctness). The `RawBsonDocument` streaming branch + `BsonRowReader` are retained but currently unreachable dead code (removal tracked separately, since it spans Query and Storage).
  - `Infrastructure/MongoQueryMode` (`Native`/`DriverLinq`/`NativeOnly`) — the user-facing gate option (`UseQueryMode`).
  - `NativeTranslation/NativeCardinalityBinder` — populates `MongoSelectDefinition.Cardinality` for entity reducers (`TryBindReducer`) and scalar aggregates (`TryBindAggregate`, which for `All`/predicate-bearing `Count`/`Any` injects the negated predicate as a `$match` conjunct, always appended to the *tail* of `PipelineOps`, never hoisted ahead of an already-recorded `$skip`/`$limit`).
  - `Expressions/MongoCardinality` — dialect-neutral IR for "this select terminates in a reducer or aggregate": `Reducer`/`Aggregate` kind, selector field-ref, `EmptyBehavior`/`EmptyValue`, result type.
  - `NativeTranslation/Stages/MongoCountStage` / `MongoGroupAccumulatorStage` — typed IR stages the lowerer appends for `Count`/`LongCount`/`Any` and `Sum`/`Min`/`Max`/`Average` respectively.
  - `NativeTranslation/NativeGroupByBinder` — populates `MongoSelectDefinition.Grouping` for `GroupBy(key).Select(aggregate)` and (via `TryBindDistinctFromProjection`) converts a projected `Distinct` into a degenerate `$group`. Holds the two correctness guards: `HasDefaultKeySerialization` (reject a grouping/distinct key with a value converter or non-default `BsonRepresentation` — the flattened `_id` readback has no backing `IProperty` to apply one through) and `IsGroupingSource` (an accumulator's source must be the grouping parameter itself, not a correlated subquery/navigation/different collection).
  - `Expressions/MongoGrouping` — dialect-neutral `$group` IR: key parts + accumulators, lowered to `MongoGroupStage`, rendered by `MongoPipelineFactory.RenderKeyedGroup`.
  - `Expressions/MongoElementRefExpression` — a raw document-element reference by (possibly dotted) path with no backing `IProperty`, rendering as `"$" + Path`; used by the GroupBy/Distinct flattening `$project` to lift `_id`/`_id.<Name>`/accumulator fields up to top-level result aliases.
  - `EnumerableMethods` (provider root) — the provider's own port of EF Core's `internal` `EnumerableMethods`, extended with `Count`/`LongCount`/`Sum`/`Average`/`Min`/`Max` selector members for matching grouped/counted aggregates.
  - `Visitors/MongoShapedQueryCompilingExpressionVisitor.ExecuteAggregate`/`TryBuildAggregateFactory` — compile-time construction of the scalar-result execution path, applying `MongoCardinality.EmptyBehavior`/`EmptyValue` and deserializing via `DeserializeScalar<TResult>`.
  - `SingleValueEnumerable` — the `IEnumerable<T>` wrapper the native reducer/aggregate path returns so EF Core's own base cardinality reduction (First/Single throw/empty semantics) runs unmodified.
- `Visitors/MongoEFToLinqTranslatingExpressionVisitor` — converts the residual EF expression into a tree the driver's LINQ v3 provider understands (`Mql.Field`, parameter resolution, `As<T>(serializer)`).
- `Visitors/MongoProjectionBindingRemovingExpressionVisitor` — replaces `ProjectionBindingExpression` nodes with concrete index-based reads from a `BsonDocument`.
- `Visitors/MongoMixedProjectionBindingRemovingExpressionVisitor` — sibling of the above used on the mixed path (projection contains entity references LINQ v3 can't handle); `MongoShapedQueryCompilingExpressionVisitor` strips the trailing `Select` and dispatches to this visitor so the shaper runs client-side over full `BsonDocument`s.
- `Expressions/MongoCollectionExpression`, `EntityProjectionExpression`, `RootReferenceExpression`, `ObjectAccessExpression`, `ObjectArrayProjectionExpression` — provider-specific expression nodes for collection roots, nested-document access, and entity shape.
- `MongoExecutableQuery` + `QueryingEnumerable` — the compiled-query handoff. `QueryingEnumerable` calls `MongoClientWrapper.Execute(MongoExecutableQuery)` and applies the shaper. For the native path `MongoExecutableQuery` carries `NativePipeline` (the built `BsonDocument[]`), `Streaming`, and `Session` (internal); for the fallback it carries the driver-LINQ `Query` expression.
- `Factories/*` — EF Core DI factories registered in `MongoServiceCollectionExtensions.AddEntityFrameworkMongoDB()`.

> **`Reverse`/`Last`/`LastOrDefault` for an explicit trailing sort (EF-411).** Native now also covers
> `Reverse()`, `Last()`, and `LastOrDefault()` when the select has an explicit trailing `$sort` — MQL has no
> "reverse row order" stage, so the only sound native form is flipping that sort's direction (the exact
> complement of the original order) via the new `MongoSelectDefinition.TryFlipTrailingSortDirection()`, which
> flips every `MongoOrdering` in the TAIL op if it is a `MongoSortOp` and returns `false` (no mutation)
> otherwise. `Reverse` (in `NativeSlotPopulator.PopulateNativeSlots`) just flips and stops there;
> `Last`/`LastOrDefault` (two new `MongoReducerKind` members, dispatched through the existing
> `TryGetReducerKind`/`NativeCardinalityBinder.TryBindReducer` path First/FirstOrDefault already use) flip
> first and then append the ordinary `$limit: 1` — the first row of the reversed order is the last row of
> the original order, so this is a pure reuse of the existing reducer machinery, not new shaper/lowerer code.
> Both flip via `ActiveOps` (not `PipelineOps` directly), so a set-op-terminal `Last`/`LastOrDefault` flips the
> TRAILING sort, matching where a trailing `OrderBy` would itself have been recorded. **Ordered-case only,
> deliberately:** an unordered source has no defined LINQ row order to complement, and the tail op must be
> LITERALLY the sort (a `Where`/other op after it makes the tail a `$match`, not a `$sort`) — no attempt is
> made to search back through the op list or synthesize a `$natural` order. **`HasLimit` (pre-existing First/
> Single guard, unchanged) still declines a reducer once a user `Take`/`Skip` already occupies the limit
> slot** — `Last`/`LastOrDefault` inherit this for free, not a new guard.
>
> **Reverse has NO driver-LINQ oracle at all — MEASURED, and this is the one asymmetry worth remembering.**
> The C# driver's own LINQ v3 provider does not translate `Queryable.Reverse()` in ANY shape, ordered or not
> (`MongoDB.Driver.Linq.ExpressionNotSupportedException`, confirmed live both ways) — tracked upstream as
> **CSHARP-5836**. So a `Reverse()` this slice cannot route natively (unordered, or composed after a

## Boundaries with adjacent areas

- **vs Storage.** Query stops at the executable query — it produces *data*: either a native `BsonDocument[]` pipeline (`MongoExecutableQuery.NativePipeline`) or a driver-LINQ expression. `MongoClientWrapper.Execute(...)` (Storage) owns execution: it runs `collection.Aggregate(nativePipeline)` for the native path and hands the expression to `IMongoQueryProvider` for the fallback. Cursor lifecycle, transaction/session binding, retries are Storage + driver. Never call `IMongoCollection<>.Aggregate(...)` directly from Query — build the `BsonDocument[]` and let the wrapper run it.
- **vs Storage — bulk `ExecuteUpdate`/`ExecuteDelete` (EF9+) uses a *second*, deliberately different seam.** Reads cross to Storage as **data** (a `MongoExecutableQuery`); bulk crosses as **behavior** — `MongoShapedQueryCompilingExpressionVisitor.CreateBulkPlan<TSource>` builds a `MongoBulkPlan` (Storage) carrying `Func<QueryContext, …>` translation delegates, and `MongoBulkOperationExecutor` (Storage) invokes them at runtime. This is intentional: bulk filter/update translation is parameter-value-dependent, so it must be deferred and re-run per execution. The translation helpers (`BuildFilter`/`BuildUpdate`/`BuildIdDocumentQuery`) stay here in Query; only their rendered results cross the boundary. Don't "fix" the bulk seam to look like the read seam — they differ for this reason.
- **vs Serializers.** Query needs an `IBsonSerializer` for every materialized projection result — it asks `BsonSerializerFactory` (Serializers area). Query should never instantiate serializers directly.
- **vs Metadata.** `IEntityType`, `IProperty`, navigation info come from Metadata. Query reads `GetElementName()`, `GetBsonRepresentation()`, `GetDiscriminator*()` etc. — it doesn't write them.
- **vs the driver's LINQ v3 provider.** Only the **fallback** path uses it: Query produces a driver-LINQ expression (types from `MongoDB.Driver.Linq`) and hands it off, and the driver builds that pipeline. The **native** path bypasses the driver's LINQ provider entirely — the provider builds the `BsonDocument[]` itself (`MongoSelectLowerer` + `MongoQueryLanguageRenderer` + `MongoPipelineFactory`) and only uses the driver as a BSON/cursor/protocol library via `Aggregate`. The deliberate, stable boundary is **our query tree → `BsonDocument[]` → `Aggregate`**; we do **not** build on the driver's internal AST.

## Common pitfalls

- **Allowed method sources are strict.** Only `Queryable`, `MongoQueryableExtensions`, and `MongoDB.Driver.Linq.MongoQueryable` methods are accepted. Anything else throws `NotTranslatedExpression` early.
- **VectorSearch extraction.** `VectorSearch(...)` must be pulled out of the tree before EF's nav-expansion runs (it crashes nav-expansion otherwise) and stitched back in after. If you change preprocessor ordering, re-check this dance.
- **ProjectionMapping discipline.** The `_projectionMapping` keys (`ProjectionMember`s) must match exactly what the shaper expects. A mismatch between the post-processor mapping and the shaper compilation produces silent wrong-results, not crashes.
- **`MongoQueryExpression.CapturedExpression`** must be a *complete* method chain — set once at the tail of `MongoQueryableMethodTranslatingExpressionVisitor.VisitMethodCall`. Setting it mid-chain truncates the query.
- **Reference-equality on `MethodInfo`.** Translators that match by `MethodInfo` must use canonical constants — `QueryableMethods` for the top-level dispatch in `MongoQueryableMethodTranslatingExpressionVisitor`, `EnumerableMethods` inside the projection-binding visitors, and the driver's `*Method` reflection classes where the bridge to driver-LINQ needs them; open vs. constructed generic methods compare unequal.
- **Unsupported shapes are detected, not silently translated.** Two layers: the base visitor early-fails truly untranslatable shapes; and for the *native* path, anything `NativeSlotPopulator` does not lower into a slot calls `mongoQ.Select.MarkNotNativelyRepresentable()` (sets the internal `_hasUnsupportedOperator` flag, which drives `Route` to `NativeRoute.Fallback`) so the gate falls back (or throws under `NativeOnly`) rather than emitting a pipeline that silently drops the operator.
- **The native catch-all whitelist must stay in sync.** `NativeSlotPopulator.PopulateNativeSlots` lowers seven slot operators (`Where`/`OrderBy`/`OrderByDescending`/`ThenBy`/`ThenByDescending`/`Skip`/`Take`) into ops on `MongoSelectDefinition`'s ordered `PipelineOps` list. The `else` catch-all marks **everything else** non-native by default (correctness-safe: worst case is a missed optimization + fallback, never a wrong result), *unless* `IsNativeRepresentableSlotOperator` returns `true` — which lists the seven slot operators plus every operator with its own `Translate*` override (`Select`, `OfType`, `Distinct`, `Union`, `Concat`, `SelectManyWithCollectionSelector`, `GroupBy*`) purely to stop the catch-all from re-deciding what that override already decided for itself. **Adding a new native operator means:** for a slot-style operator, update BOTH `NativeSlotPopulator.PopulateNativeSlots` *and* `IsNativeRepresentableSlotOperator`; for a `Translate*`-override-style operator, add its override *and* add it to `IsNativeRepresentableSlotOperator`. Miss either half and the operator is silently dropped on the native pipeline or double-decided. (`SelectMany` is the one exception: its own binders return `null` directly on decline rather than calling `MarkNotNativelyRepresentable()`, per the no-driver-LINQ-baseline invariant above.)
- **The QMTEV `Translate{Where,OrderBy,ThenBy,Skip,Take}` overrides are inert (`=> null`).** Native slot population is delegated to `NativeSlotPopulator.PopulateNativeSlots` at the `VisitMethodCall` fall-through, because routing these through `base.VisitMethodCall` rebuilds a fresh `MongoQueryExpression` per operator (slots don't accumulate). **Do not add these operators to the `VisitMethodCall` switch** without first removing their `NativeSlotPopulator.PopulateNativeSlots` handling — otherwise slots double-populate.
- **The lowerer is BSON-free; the renderer/factory own BSON.** `MongoSelectLowerer` produces only typed `MongoPipelineStage`s; all `BsonDocument` construction lives in `MongoQueryLanguageRenderer` (the `$match` body) and `MongoPipelineFactory.Create` (the stage-walk: `{$match}`/`$sort`/`$skip`/`$limit`/`$lookup`/`$unwind`).
- **Composite-PK key access is native** (EF-394) — `MongoExpressionTranslator` resolves multi-property-PK member access via the `_id.<element>` dotted path, so predicates/sort over composite-PK components go native.
- **Non-positive paging matches EF's contract.** `MongoPipelineFactory.Build` validates `$limit > 0` / `$skip ≥ 0` and throws `ArgumentOutOfRangeException` (client-side, like the driver) — do not emit `{$limit: 0}` (MongoDB rejects it server-side). Property-less primitive values (Skip/Take counts have `forSerialization == null`) serialize via `BsonValue.Create`, not a property serializer.
- **MQL shape cannot prove a query went native.** For filter/sort/paging the native and driver-LINQ pipelines are structurally identical (`$match`/`$sort`/`$skip`/`$limit`), so asserting those substrings under `Native` mode passes even on fallback. The **only reliable "goes native" signal is `NativeOnly` mode**: native-capable ⇒ succeeds; otherwise ⇒ throws `NativeTranslationNotSupportedException`. (Several early gate tests were false positives masked by structurally-identical fallback MQL.) This bites hardest for reference `Include` and set operations, where the fallback path was deliberately made to emit the *same* MQL shape as the native path.
- **EF Core query cache.** Compiled queries are cached by EF Core by expression-tree shape; if you change a translator's output for a previously-translatable tree, you've quietly invalidated user caches.
- **TPH `$lookup` joins narrow by discriminator when the target is a derived type.** `LookupExpression`'s constructor builds the FK-equality `$lookup` for cross-collection Include (`Visitors/MongoProjectionBindingExpressionVisitor.Lookup.cs`, `MongoProjectionBindingExpressionVisitor.cs`). In a TPH hierarchy the target collection also holds sibling-type documents that satisfy the same FK equality (e.g. a principal-side collection nav whose FK is shared across every subtype's rows). When `navigation.TargetEntityType` is not the hierarchy's root, the constructor forces the pipeline form of `$lookup` and adds a `$match` on the discriminator (`$in` the target type's own value plus its derived types') so sibling-type rows aren't admitted. Skipping this for a new $lookup call site would reintroduce EF-374's gap.
- **Multi-EF guards.** Some visitor signatures changed between EF8/EF9/EF10. For representative guard shapes elsewhere in the tree see `Storage/MongoTypeMappingSource.cs` (`#if EF8 || EF9`), the `ChangeTracking/StringDictionaryComparer*.cs` pair (legacy vs. EF10 split), and the `ChangeTracking/ListOf*Comparer.cs` files (`#if EF8`); in Query itself, `QueryingEnumerable.cs` has a `#if !EF8` block.

## How to test

Most query tests assert the **rendered MQL pipeline** rather than executing against a server. The functional and specification tests both have helpers (`AssertMql(...)`) that capture the MQL via `TestMqlLoggerFactory`. Unit tests use **plain xUnit `Assert.*`** (FluentAssertions is not referenced anywhere in the test projects).

**Proving the native path.** `AssertMql` shape does **not** distinguish native from driver-LINQ for filter/sort/paging (identical pipelines) — to assert a query genuinely goes native, run it under `MongoQueryMode.NativeOnly` and assert it **succeeds** (a fallback shape would throw `NativeTranslationNotSupportedException`); to assert a shape falls back, assert it **throws** under `NativeOnly` (or, for `Include`, assert the driver `_outer`/`_inner` shape under `Native`). The spec suite has a **test-only** coverage instrument: `MONGODB_EF_NATIVE_ONLY=1` flips all spec contexts to `NativeOnly` (via `MongoTestStore.AddProviderOptions`), so the pass/fail set is the "what runs native" report. Native unit tests live under `tests/MongoDB.EntityFrameworkCore.UnitTests/Query/NativeTranslation/`; the `QueryModeGate*` functional tests exercise the gate end-to-end. For a differential-correctness gate on a native shape that can *change* results (not just fall back vs. not), prefer a `[Theory]` asserting the native result equals an in-memory LINQ oracle evaluated over the *same* `Expression` object, across a fixture deliberately covering ragged/missing/null/empty states — see `NativeOwnedCollectionAllTests`/`NativeOwnedCollectionCountTests` for the pattern.

```bash
dotnet test MongoDB.EFCoreProvider.sln -c "Debug EF10" --no-build \
  --filter "FullyQualifiedName~Query"
```

- Unit tests: `tests/MongoDB.EntityFrameworkCore.UnitTests/Query/`
- Functional tests (real DB): `tests/MongoDB.EntityFrameworkCore.FunctionalTests/Query/` — golden-path translations and end-to-end materialization.
- Specification tests (EF Core conformance, Northwind suite): `tests/MongoDB.EntityFrameworkCore.SpecificationTests/Query/` — pattern is to override the upstream test and assert the produced MQL.
