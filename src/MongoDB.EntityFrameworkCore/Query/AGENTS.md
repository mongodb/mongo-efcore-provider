# Query — AGENTS.md

## Scope

Translates `IQueryable<T>` against MongoDB-backed DbSets into MongoDB aggregation pipelines. There are **two translation paths**, chosen at compile time by the `MongoQueryMode` option (see *the gate* below):

1. **Native (default).** For the supported slice — single-collection **filter / sort / paging** over whole-entity results — the provider **generates the aggregation `BsonDocument[]` pipeline itself**, from a structured query expression tree, and runs it via `IMongoCollection<…>.Aggregate`. It does **not** go through the driver's LINQ provider for these.
2. **Driver-LINQ (gated fallback).** For everything outside the native slice (`SelectMany`, `Intersect`/`Except`, `VectorSearch`, a non-TPH or otherwise non-representable `OfType` — see the EF-347 note below — a bare-scalar or whole-entity `Distinct` (a *projected* `Distinct` goes native — see the EF-347 Task 2 note below) — a non-whole-entity, non-terminal, or mismatched-entity-type `Union`/`Concat` (a *whole-entity, terminal* `Union`/`Concat` goes native — see the EF-347 slice 2 note below) — the **non-native** `GroupBy` shapes — see the EF-SP6 note below — and the deferred Include shapes below), the provider still hands a driver-LINQ expression to the MongoDB C# driver's LINQ v3 provider, exactly as it always did.

> **As-built scope (EF-323 foundation + EF-329 predicate-breadth + EF-331 projection-pushdown + EF-332 layering + EF-SP4 scalar-cardinality sub-projects).** Native = filter/sort/paging, with **predicate breadth**: nullable equality/`== null` (IS NULL), collection `Contains` → `$in`/`$nin`, `string.StartsWith`/`EndsWith`/`Contains` → `$regularExpression`, and field-to-field/arithmetic comparisons → `$expr`. Native now also covers **terminal anonymous-type / DTO member-access projections** — a final `Select` whose body is a `new {...}`/DTO construction over top-level member accesses only — which emits a native `$project` stage instead of falling back; **bare scalar** projections (`Select(p => p.Name)`), **computed leaves** (arithmetic/method calls inside the projection), **mixed** entity+scalar shapes, and **non-terminal** `Select`s (followed by more query operators) still fall back to driver-LINQ. The remaining **computed long tail** — string transforms (`ToUpper`/`Substring`/…), date-part extraction, `Math.*`, and type-changing casts — is explicitly **out of scope for this sub-project**; it is a follow-on, not a gap left by predicate breadth.
>
> **Scalar cardinality (EF-SP4).** Native now also covers **entity reducers** (`First`/`FirstOrDefault`/`Single`/`SingleOrDefault`) via a synthesized `$limit` (1, or 2 for the `Single` family so the server-side reducer can still distinguish "more than one" from "exactly one") plus EF Core's own base cardinality reduction over the returned `IEnumerable<T>` — this is a DOM shaper, not a streaming one; and **scalar aggregates** (`Count`/`LongCount`/`Any`/`All`/`Sum`/`Min`/`Max`/`Average`) via a synthesized `$count`/`$group` stage plus a DOM scalar shaper and an explicit empty-input contract (`MongoEmptyAggregateBehavior`: default-value for `Count`/`LongCount`/`Any`/`All`/`Sum`, return-null for nullable `Min`/`Max`/`Average`, throw for non-nullable `Min`/`Max`/`Average`, matching the BCL LINQ contract). **What still falls back:** `Contains`/`ElementAt`/`Last` (no native form); computed aggregate selectors (`Sum(x => x.V * 2)` — the selector must be a plain member access); `All` with a comparison predicate (`All(x => x.V > 0)` — negating a comparison into query-native form is unsupported; ticket EF-335); **an aggregate that injects a predicate as a `$match` (`All`, or `Count`/`Any` with an unnormalized predicate) occurring AFTER a `Take`/`Skip` already applied to the same select** — injecting the predicate would hoist it ahead of the already-populated `$skip`/`$limit` in the canonical `$match → $sort → $skip → $limit` order, evaluating it over the wrong row set (e.g. `Take(n).All(pred)` must see only the first `n` rows); the guard in `NativeCardinalityBinder.TryBindAggregate` forces fallback rather than attempt a windowing rewrite (a plain aggregate that injects no predicate, e.g. `Take(n).Count()`, is unaffected and stays native); and reducer/aggregate **streaming** (deferred — the `BsonRowReader` null/non-nullable-list gap means these still materialize via the DOM shaper, not the streaming one). Two retired cutouts from earlier sub-projects: the `ExecuteScalar` short-circuit is now gated on `NativePipeline == null` (rather than being unconditional), and the `resultCardinality != Enumerable` gate was relaxed to admit the new scalar/reducer cardinalities. (native `GroupBy` landed in EF-SP6; native `OfType` and projected `Distinct` in EF-347 slice 1; native whole-entity terminal `Union`/`Concat` in EF-347 slice 2 — see the notes below. `Intersect`/`Except` remain unsupported, hard-failing translation unconditionally — a later sub-project if ever picked up.)
>
> **OfType discriminator narrowing (EF-347, SP6-remaining slice 1).** Native now also covers `OfType<TDerived>()` over a TPH hierarchy: `TranslateOfType` builds a discriminator conjunct — a single-value `$eq` when `TDerived` is a leaf type, an `$in` over the discriminator subtree (`TDerived` and its own derived types) otherwise — via `TryBuildDiscriminatorPredicate`, and adds it to `Predicate` through `AddPredicateConjunct` (composing with any other `Where` predicate already on the select), instead of unconditionally calling `MarkNotNativelyRepresentable()`. This works with **no shaper changes**: TPH entities are already streaming-ineligible and materialize through the DOM shaper via EF's own discriminator-based `MaterializationCondition`, which already picks the correct derived CLR type — the only thing native was missing was the `$match`/`$in` conjunct that keeps sibling-type rows out of the result. **Rejected by a guard → fall back (the guard PREVENTS native divergence from driver-LINQ):** `TryBuildDiscriminatorPredicate` returns `false` — so `MarkNotNativelyRepresentable()` is still called and the query falls back (throwing only under `NativeOnly`) — when (a) the target type has no discriminator property (non-TPH `OfType`, e.g. an unrelated-hierarchy narrowing), OR (b) the discriminator property has a **value converter or a non-default `BsonRepresentation`** (`GetValueConverter()`/`GetTypeMapping().Converter`/`GetBsonRepresentation()` — mirroring `NativeGroupByBinder.HasDefaultKeySerialization`). The value-converter/representation case is a correctness guard, not just an optimization gap: the driver-LINQ discriminator filter serializes the discriminator value RAW (`MongoEFDiscriminator.GetDiscriminatorsForTypeAndSubTypes` → `BsonValue.Create(GetDiscriminatorValue())`, bypassing the conversion), whereas the native predicate serializes it THROUGH the property serializer (applying the conversion), so an unguarded native `$eq`/`$in` would return a **different row set** than the established driver-LINQ path — violating `Native == DriverLinq`. The plain-string discriminators used by the default/shadow mapping modes have no converter/representation and stay native.
>
> **Projected `Distinct` (EF-347, SP6-remaining slice 2).** Native now also covers `Distinct()` applied to a terminal anonymous/DTO projection (`Select(new {...}).Distinct()`): `TranslateDistinct` calls `NativeGroupByBinder.TryBindDistinctFromProjection`, which converts each already-populated `Select.Projection` entry (alias → field-ref, from the SP3 `$project` pushdown) into a **degenerate `$group`** — a composite (or scalar) key made of those same field-refs, with **zero accumulators** — replacing `Projection` with a flattening projection that reads each value back out of `_id.<alias>` (`_id` for a single-part key), exactly mirroring the GroupBy flatten mechanism. `Route` resolves to `NativeRoute.GroupBy` (a grouping with no accumulators is still a grouping), so the lowerer's existing group branch emits `$group` → flatten `$project` with no special-casing. **No shaper changes**: the shaper was already built by the preceding `Select` to read the top-level result aliases by name, and those same aliases survive the flatten. `TryBindDistinctFromProjection` also sets a **separate** `Select.IsDistinct = true` provenance flag on success (NOT `IsGroupBy`) so the **existing** post-group guards (`NativeSlotPopulator`'s post-group slot-operator guard **and** `NativeCardinalityBinder.TryBindAggregate`/`TryBindReducer`, all now keyed on `IsGroupBy || IsDistinct`) also cover an operator applied **after** this `Distinct` — without it, e.g. a `Where` whose member name happens to match a real entity property name would resolve against the entity and get hoisted to a pre-group `$match` instead of being rejected. **Why a separate flag, not `IsGroupBy`:** the QMTEV `TranslateJoinCore` join-decline is grouping-semantics-specific — a genuine `GroupBy` joined via driver-LINQ returns silently-wrong (empty) joins, so it **hard-declines** (`MarkGroupByFallbackUnsafe` → throws under both `Native` and `NativeOnly`). A projected `Distinct` is just a flat row set the driver-LINQ path joins **correctly**, so `Distinct`-then-`Join` must fall back **gracefully** (`TranslateJoinCore` calls `MarkNotNativelyRepresentable` for an `IsDistinct`-and-not-`IsGroupBy` join side — runs correctly under `Native`/`DriverLinq`, throws only under `NativeOnly`). Reusing `IsGroupBy` for Distinct would have hard-thrown `Distinct().Join(...)` under `Native` — a correct-results→throw regression. Note the lowerer's group branch returns early after the `$group`+flatten `$project`, so a native `Distinct`+`Join` would silently drop the join — hence it must fall back (never go native), just gracefully. **Falls back to driver-LINQ:** a **bare-scalar** projection (`Select(o => o.Country).Distinct()` — bare-scalar `Select` never populates `Projection` in the first place, so `TryBindDistinctFromProjection`'s `Projection.Count == 0` guard rejects it) and a **whole-entity** `Distinct()` (same reason). **Rejected by a guard → fall back (correctness, not just an optimization gap):** a projected key backed by a property with a value converter or non-default `BsonRepresentation` — `HasDefaultKeySerialization` is reused as-is from the GroupBy binder (same generic-`_id`-readback divergence risk). `IsNativeRepresentableSlotOperator` gained `Distinct` so the slot-populator catch-all doesn't clobber `TranslateDistinct`'s own decision (mirroring how `Select`/`OfType` are listed). **A `GroupBy` applied AFTER a projected `Distinct` (`Select(new{..}).Distinct().GroupBy(k)`) falls back** via a dedicated guard at the top of `TranslateGroupBy`: because `GroupBy` has its own `Translate` override it bypasses the `IsGroupBy || IsDistinct` post-group guards in `NativeSlotPopulator`/`NativeCardinalityBinder`, so without this guard `TryBindGroupKey` would OVERWRITE the Distinct's key-only `Grouping` with the GroupBy's own key — silently DROPPING the Distinct and emitting a `$group` that counts ALL rows instead of distinct rows (a silent wrong-data bug). `TranslateGroupBy` therefore checks `IsDistinct || IsGroupBy || Grouping != null` first and, if set, marks the query non-native (and sets `IsGroupBy` for the join-decline machinery) WITHOUT rebinding — falling back to driver-LINQ. (The reverse, `Distinct` after `GroupBy`, is already safe: `TryBindDistinctFromProjection` returns `false` when `Grouping != null`.)
>
> **Include (EF-339, SP5 — flat collection Includes).** Native now covers **single-level collection `Include`** (`Include(x => x.Orders)`), plus a **projected collection `.Count`** (`Select(c => new { c.Orders.Count })` → server-side `$size` over the `$lookup` array). The lowerer emits a flat `$lookup` (no `$unwind`) after the canonical `$match → $sort → $skip → $limit` (so filter/sort/paging are pushed **ahead** of the join — the observable MQL change this sweep rebaselined); the DOM shaper then materializes the joined array. Collection `Include` is native via the **DOM** shaper (collection navs are ineligible for streaming, gated off by `StreamingEligibility`). **Reference `Include` remains deferred/fallback, unchanged by this sub-project** — it still nav-expands to a `LeftJoin` that the gate treats as non-native, so it falls back to driver-LINQ (correct results; throws under `NativeOnly`), exactly as before EF-339. Its native lookup/streaming machinery (lowerer `$lookup`/`$unwind`, `GetStreamingReferenceLookups`, streaming-Include eligibility) stays **built but dormant**, awaiting a future streaming sub-project. Native-vs-driver is decided by the lowerer (`TryBuildNativeFactory`) — collection Include goes native the moment the lowerer stops rejecting the flat `$lookup` shape, no separate gate flag. The `IsNativeCollectionLookup` discriminator (`As == LookupExpression.GetLookupAlias(Navigation)`, i.e. the un-prefixed `_lookup_<Nav>` alias) is what admits the flat single-level collection shape while still excluding the (still-fallback) reference-Include `_outer`/`_inner` shape and the collection-of-collection `_lookup_<Nav>._lookup_<Coll>` shape (which keeps prefixed aliases and stays fallback). **Still deferred/fallback:** reference `Include`, nested/transitive `ThenInclude`, filtered `Include`, collection-of-collection, and collection-array **streaming** materialization (SP5b / SP7). EF-334 later centralized the **is-native** gate decision into one `ClassifyNativeDisposition` classification (`Route` + vector-search + GroupBy-unsafe); `AllPendingLookupsAreStreamable` deliberately stayed a **separate** streaming-vs-DOM axis (it is not an is-native signal). The residual `$lookup`-state relocation off `MongoQueryExpression` is tracked under EF-317 (a driver-`LeftJoin`-gated removal), independent of EF-334.
>
> **GroupBy (EF-SP6 / EF-344).** Native now also covers **`GroupBy(key).Select(aggregate)`** → a server-side `$group` followed by a **flattening `$project`** that lifts the grouped output (the `_id` scalar key, each `_id.<Name>` composite sub-key, and each accumulator output field) up to top-level result aliases. The grouped rows materialize through the **existing DOM projection shaper** (`MongoProjectionBindingRemovingExpressionVisitor`) reading those flattened aliases by name — there is **no** bespoke grouping shaper and **no** `IGrouping` materializer (the gate compiles it DOM-only, `allowStreaming: false`, via the `NativeRoute.GroupBy` branch). **Keys:** a scalar key (`_id: "$field"`) or a composite/anonymous key (`_id: { Name: "$field", … }`), each part a plain field-ref. **Accumulators:** `Count`/`LongCount` → `$sum: 1` (including a *lone* `Count()` projection, `GroupBy(k).Select(g => new { g.Key, Count = g.Count() })` — this is **not** fused by EF into a `resultSelector`-bearing `GroupBy` and goes native); `Sum`/`Average`/`Min`/`Max` over a plain field-ref selector → `$sum`/`$avg`/`$min`/`$max`. **Mechanism:** `MongoGrouping` IR on `MongoSelectDefinition.Grouping` (with the transient `PendingGroupKey` holding the key while it is parsed ahead of the aggregate `Select`), `NativeRoute.GroupBy`, `NativeGroupByBinder` (`TryBindGroupKey` called from the QMTEV's `TranslateGroupBy` — which builds the grouped `ShapedQueryExpression` + `GroupByShaperExpression` **directly**, since the base `TranslateGroupBy` is abstract; `TryBindGroupProjection`/`TryBindAccumulator` called from the grouped-source branch of `TranslateSelect`), `MongoGroupStage` + `MongoPipelineFactory.RenderKeyedGroup`, and the `MongoSelectLowerer` group branch. The provider's own `EnumerableMethods` port was extended with the aggregate-selector members (EF Core's is `internal`).
>
> **Behavior change (not a break).** Before EF-344, `GroupBy` **hard-failed** translation (`NotTranslatedExpression`). Now supported shapes go native and **unsupported shapes fall back to driver-LINQ** (throwing only under `NativeOnly`), except the one declined family below. Per the versioning rubric this — and the emitted MQL — is **not** a breaking change: query results are unchanged; the change is hard-throw → native / graceful-fallback.
>
> **Falls back to driver-LINQ (correct results under default `Native`):** computed keys (`g => g.OrderDate.Year`) and other non-member key expressions that `TryBindGroupKey`'s switch rejects — it accepts only a plain `MemberExpression` or an anonymous-of-members `NewExpression`, so e.g. an `EF.Property<T>(o, "…")` key (a `MethodCallExpression`) falls back, computed accumulator operands (`g.Sum(x => x.A * x.B)`), **bare** `GroupBy(key)` / `GroupBy(key, elementSelector)` that terminate on the `IGrouping` sequence (`Route` stays `Fallback` while `PendingGroupKey` is set but `Grouping` is never finalized), a user-supplied `GroupBy(key, resultSelector)` (the QMTEV's `TranslateGroupBy` declines a non-null `resultSelector`), **post-group slot operators** (`Where`-as-HAVING / `OrderBy` / `OrderByDescending` / `ThenBy` / `ThenByDescending` / `Skip` / `Take` applied **after** the grouping) — these fall back **because of an explicit guard**, not by luck: `NativeSlotPopulator.PopulateNativeSlots` calls `MarkNotNativelyRepresentable()` and returns for these seven operators once `MongoSelectDefinition.IsGroupBy` is set (`IsPostGroupSlotOperator`), forcing a clean driver-LINQ fallback. Without the guard the post-group predicate/sort would be resolved against the **entity** type by member name (the translator is built from `CollectionExpression.EntityType`) and emit a **pre-`$group`** `$match`/`$sort` — and when an aggregate alias collides with a real property name (e.g. `Amount`) it silently returned wrong data. The guard is keyed on `IsGroupBy` (set unconditionally by `TranslateGroupBy`) rather than the finalized `Grouping`, and is scoped to the seven slot operators only so the supported `GroupBy(key).Select(aggregate)` (whose aggregate `Select` reaches `PopulateNativeSlots` with `IsGroupBy` already `true`) still goes native. **Post-group scalar aggregates and reducers** (`Count`/`LongCount`/`Sum`/`Min`/`Max`/`Average` / `First`/`Single`/`Any`/`All` applied **after** the grouping) fall back the same way, via a symmetric `IsGroupBy` guard at the top of BOTH `NativeCardinalityBinder.TryBindAggregate` **and** `NativeCardinalityBinder.TryBindReducer` (EF-344 pass-2). Without it, setting `Cardinality` on an already-grouped select flips `Route` to `ScalarAggregate` (which is prioritized above `GroupBy`) while the lowerer's grouping branch still emits `[$group, $project]` with no terminal `$count`/aggregate/limit stage — the scalar shaper then reads a nonexistent element and crashes with `KeyNotFoundException` instead of falling back. **Invariant: EVERY post-group / post-terminal operator entry point must gate on `IsGroupBy` (and, since EF-347, `IsDistinct`)** — currently `NativeSlotPopulator.PopulateNativeSlots` (the seven slot operators, on `IsGroupBy || IsDistinct`), `NativeCardinalityBinder.TryBindAggregate`/`TryBindReducer` (scalar aggregates / reducers, on `IsGroupBy || IsDistinct`), **`TranslateGroupBy`** (a `GroupBy` after a terminal grouping/distinct — gates on `IsDistinct || IsGroupBy || Grouping != null` and falls back WITHOUT rebinding, else it overwrites the existing `Grouping`), and **`TranslateSelect`'s non-grouped projection branch** (a second projected `Select` after a native `Distinct`/`GroupBy` — gates on `Grouping != null || IsGroupBy || IsDistinct` and skips `TryPopulateNativeProjection`, else it appends a field-ref onto the terminal's `Projection` while `Grouping` is set → the lowerer emits a flatten `$project` over fields gone after the `$group` → silent nulls). **`Select`, `GroupBy`, and `OfType` are the own-`Translate`-override operators that need the explicit guard** (they bypass the `NativeSlotPopulator`/`NativeCardinalityBinder` catch-all guards) — `OfType` gates on `mongoQueryExpression.Select.HasTerminalOperator` at the top of its discriminator-predicate branch in `TranslateOfType`, added as a final-review fix once `Union`/`Concat` (EF-347 slice 2) made a whole-entity terminal reachable before `OfType` for the first time (previously `OfType` was only ever reached pre-terminal, so the gap was latent). Without it, `OfType` after a `Union`/`Concat` adds its discriminator conjunct to the OUTER select's `Predicate`, which the lowerer emits as a pre-`$unionWith` `$match` that filters only the outer rows — the `$unionWith` operand's own nested pipeline gets no discriminator filter, so sibling-type rows from the operand leak into the result (see `NativeSetOpsTests.OfType_after_union_falls_back`, which reproduces this as an `InvalidOperationException` at materialization — a leaked base-type document reaching a shaper fixed to the derived type — rather than a silently-wrong result, but the underlying leak is the same class of bug). `Distinct` is covered incidentally, not by an explicit `HasTerminalOperator` check: `TryBindDistinctFromProjection`'s `Projection.Count == 0` guard already rejects a whole-entity/post-terminal source, so it falls back for an unrelated reason that happens to also cover this case. `Cast` needs no guard: `TranslateCast` is a pure shaper reshape (`ReshapeShaperExpression`) that mutates no outer slot or predicate. A future own-override operator applied after a terminal must add the same gate. (Empirical note for the `TranslateSelect` case: in the current provider this shape additionally throws at shaper build — `MongoProjectionBindingExpressionVisitor` cannot read a prior anonymous projection's members — in *all* modes, so the null-data symptom is not presently reachable; the guard is defense-in-depth for a future shaper-builder that makes chained-projection shapers buildable.) Any future reducer/aggregate/operator added after a group must add the same guard, or it reopens this class of bug (the post-group operator resolves against the base entity / picks the wrong route). Also falling back: the broader long tail the driver-LINQ provider already handles (`Distinct`/`Union`/join-then-group/nav-key groupings) — all reachable now precisely because `GroupBy` no longer hard-throws.
>
> **Rejected by guards → fall back (the guards PREVENT native wrong-results):** a grouping key with a value converter or a non-default `BsonRepresentation` (`NativeGroupByBinder.HasDefaultKeySerialization`) — the generic `_id` readback (the flattened `_id` has no backing `IProperty`) would diverge from the property's configured serializer; and an accumulator whose source is **not** the grouping parameter `g` (a correlated cross-collection subquery, a navigation, a different collection) (`NativeGroupByBinder.IsGroupingSource`) — binding it to a `$group` accumulator would silently drop the subquery and collapse e.g. a subquery `Count` to `$sum:1`.
>
> **Declines to a clean `NativeTranslationNotSupportedException` — NO fallback, under both `Native` and `NativeOnly`:** a **group-first** `GroupBy` combined with a `Join`/`GroupJoin`/`LeftJoin` (a join taken over a grouped source, e.g. the spec's `GroupBy_Aggregate_Join`). Its driver-LINQ fallback returns **silently wrong** data (the joined entity is empty for every group), so the provider declines rather than route to a known-wrong result: `MongoSelectDefinition.MarkGroupByFallbackUnsafe()` (set in the QMTEV `TranslateJoinCore` when either join side `IsGroupBy`) trips a dedicated gate check in `MongoShapedQueryCompilingExpressionVisitor.VisitShapedQuery`. **Explicit `MongoQueryMode.DriverLinq` still executes it** (the user's opt-in, carrying the same wrong-data caveat). **Join-then-group** (an aggregate over a join result) falls back **correctly** and is unaffected — do not conflate the two orderings.
>
> **Set operations — `Union`/`Concat` (EF-347 slice 2).** Native now also covers a **whole-entity, terminal** `Union`/`Concat` over the SAME entity type: `TryTranslateSetOperation` (backing both `TranslateUnion` and `TranslateConcat`) attaches a `MongoSetOperation` (`Kind` + the second operand's own `MongoSelectDefinition` + its collection name) to source1's `Select.SetOperation` when both operands are a plain whole-entity select (`IsPlainWholeEntitySelect` — filter/sort/paging only, no projection/grouping/cardinality/lookups/`VectorSearch`/own set-op) of the matching `CollectionExpression.EntityType`; otherwise it calls `MarkNotNativelyRepresentable()` and returns source1 unchanged — `TryTranslateSetOperation` **always** returns non-null (mirroring `TranslateGroupBy`'s contract), so an out-of-scope shape falls back gracefully rather than hard-failing translation. The lowerer (`MongoSelectLowerer.Lower`) renders the attached `SetOperation` as a terminal `MongoUnionWithStage` — the operand's own canonical `$match`/`$sort`/`$skip`/`$limit` stages, lowered independently via the same `AppendCanonicalStages` helper the outer query uses — appended **last**, after the outer query's own canonical stages and any `$lookup`. `MongoPipelineFactory.RenderUnionWith` renders the operand's nested pipeline into the aggregation `$unionWith` stage using the **same shared `PlaceholderTable`** as the outer query, so a parameter captured in the operand's own predicate (e.g. `set1.Union(set2.Where(c => c.X == capturedLocal))`) is substituted correctly at `Build(parameterValues)` time. `Union` additionally emits a `$group{_id:"$$ROOT"}` + `$replaceRoot` dedup stage after the `$unionWith` (full-document de-duplication, matching BCL `Union` set semantics); `Concat` does not. **`IsSetOp` joins `HasTerminalOperator`** (`IsGroupBy || IsDistinct || IsSetOp || Grouping != null`) — the same centralized post-terminal gate `GroupBy`/`Distinct` use. **Invariant: set operations are terminal-only** — every post-terminal entry point (`NativeSlotPopulator`'s seven slot operators, `NativeCardinalityBinder`'s aggregates/reducers, `TranslateGroupBy`'s rebind guard, and `TranslateSelect`'s two guards — the hoisted-shared-Include guard and the non-grouped-projection guard) already gated on `HasTerminalOperator` before this slice, so `Union`/`Concat` need **no new guard code** to be covered — they only need `IsSetOp` folded into the shared predicate, which is exactly what `HasTerminalOperator` does. A **chained** `set1.Union(set2).Union(set3)` falls back gracefully for the same reason: `IsPlainWholeEntitySelect` rejects source1 once its `Select.IsSetOp` is `true`, so the second `Union` marks it non-native rather than nesting `$unionWith` stages. **`Intersect`/`Except` hard-fail translation unconditionally** — in every mode (`Native`/`DriverLinq`/`NativeOnly`) they reach EF Core's base translation-failure path (`NotTranslatedExpression` → `InvalidOperationException`), never driver-LINQ and never returning results; a pre-existing scope unchanged by this slice, and distinct from `Union`/`Concat`'s graceful (`NativeOnly`-gated) fallback. **Falls back to driver-LINQ (correct results under default `Native`):** a **projected** set operation (`Select(new{...}).Union(...)`), an operand carrying an `Include` (EF Core itself hoists a shared `Include` to apply AFTER the combinator, reaching `TranslateSelect` as `Union(A,B).Select(x => Include(x))` — caught by its `HasTerminalOperator` guard), mismatched operand entity types (defensive; unreachable in practice because EF Core's own `NavigationExpandingExpressionVisitor` rejects incompatible set-operation sources upstream), and **any operator composed after the union** (`Where`/`OrderBy`/`Skip`/`Take`/`Count`/other aggregates/`GroupBy`/further `Union`/`Concat` — see `NativeSetOpsTests`' composition-seam regression tests for one per shape). **Deferred (out of scope for this slice):** `Intersect`/`Except` native translation, a projected/scalar set-op result, `SelectMany` combined with a set op, and any post-union composition/chaining going native (all of the above stay driver-LINQ fallback, not a gap discovered later — this is the intentional terminal-only scope).

In: top-level method-call translators **and native slot population**, the **query expression tree → stage IR → `BsonDocument[]` pipeline generator** (lowerer / renderer / pipeline factory), the compile-time **gate**, projection binding, the EF-to-driver-LINQ bridge (fallback), shaper compilation (native streaming + DOM, and driver-LINQ DOM), vector-search pre-extraction.
Out: BSON encoding/decoding of *values* (Serializers area — the renderer asks `BsonSerializerFactory` for serializers), change-tracking snapshots (ChangeTracking area), index/collection schema (Storage area), cursor execution itself (`MongoClientWrapper.Execute` in Storage), and aggregation-pipeline generation **for the fallback path** (still the driver's job).

## Pipeline at a glance

```
IQueryable<T>  (EF Core)
   │
   ▼  MongoQueryCompilationContext           (preserves the original LINQ tree; carries the MongoQueryMode)
   ▼  MongoQueryTranslationPreprocessor      (hoist final predicates; lift VectorSearch out before nav expansion)
   ▼  MongoQueryableMethodTranslatingExpressionVisitor (QMTEV)
   │      ├─ accepts only Queryable / MongoQueryableExtensions / MongoDB.Driver.Linq.MongoQueryable
   │      ├─ DELEGATES native slot population to NativeSlotPopulator.PopulateNativeSlots (Predicate /
   │      │     Orderings / Offset / Limit) and projection binding to NativeProjectionBinder
   │      │     .TryPopulateNativeProjection (Projection), both via MongoExpressionTranslator; either
   │      │     calls mongoQ.Select.MarkNotNativelyRepresentable() for any operator it does not lower
   │      │     into a slot (catch-all) — see pitfalls
   │      └─ ALWAYS also captures the raw method chain (CapturedExpression) for the driver-LINQ fallback
   ▼  MongoQueryTranslationPostprocessor     (apply final ProjectionMapping)
   ▼  MongoShapedQueryCompilingExpressionVisitor  ── THE GATE (compile time, honors MongoQueryMode) ──
   │   if Native & Select.Route != Fallback & lower/render succeed → NATIVE PATH:
   │      MongoSelectLowerer  : slots → MongoPipelineStage[]  (canonical $match→$sort→$skip→$limit→$lookup/$unwind)
   │      MongoQueryLanguageRenderer + PlaceholderTable : predicate → $match BSON; params → sentinels
   │      MongoPipelineFactory.Create : render ONCE into a template + placeholder table  (B2)
   │      compile streaming shaper (MongoStreamingEntityMaterializerRewriter) if StreamingEligibility, else DOM
   │   else (DriverLinq, or not representable, or NativeOnly→throws) → DRIVER-LINQ FALLBACK:
   │      MongoEFToLinqTranslatingExpressionVisitor rewrites CapturedExpression as driver-LINQ; DOM shaper
   ▼  MongoExecutableQuery + QueryingEnumerable
          ├─ NATIVE: factory.Build(parameterValues) → BsonDocument[] set as NativePipeline;
          │          MongoClientWrapper.Execute runs collection.Aggregate(pipeline) (RawBsonDocument if streaming, else BsonDocument)
          └─ FALLBACK: MongoClientWrapper.Execute hands the driver-LINQ expression to IMongoQueryProvider
          → IAsyncCursor; shaper turns each row into the requested CLR shape
```

B2 = the pipeline template is built **once at compile time** (lower + render → `MongoPipelineFactory`); only `factory.Build(parameterValues)` (clone-and-substitute the placeholder sentinels) runs per execution. The native-vs-driver and streaming-vs-DOM decisions are therefore **compile-time-deterministic** — there is exactly **one** shaper per query and **no** runtime dual-shaper dispatch.

## Key entry points

- `MongoQueryCompilationContext` — EF Core hook to preserve the original captured `IQueryable` so post-translation we can recover the user's intent (e.g. for diagnostics).
- `MongoQueryTranslationPreprocessor` — first phase. Notably, **`VectorSearch(...)` is extracted before EF's nav-expansion and re-inserted after** — nav expansion doesn't know about it.
- `Visitors/MongoQueryableMethodTranslatingExpressionVisitor` — the central LINQ-method dispatcher. Enforces the allowed-method-source set; **delegates native slot population and projection binding** to `NativeSlotPopulator`/`NativeProjectionBinder` (the `Translate*` overrides that would otherwise do this are inert — see pitfalls); captures the final method-chain expression on `MongoQueryExpression`.
- `Visitors/MongoShapedQueryCompilingExpressionVisitor` — **the compile-time gate**. Reads `MongoQueryMode`; consults `MongoSelectDefinition.Route` (the authoritative is-native decision for the slot/projection representability) to decide native vs. fallback; builds the `MongoPipelineFactory` and compiles the native (streaming/DOM) shaper when `Route != NativeRoute.Fallback`, else compiles the driver-LINQ fallback shaper. Splits scalar vs. entity result paths. **The full is-native decision is centralized (EF-334) in `ClassifyNativeDisposition`** → `NativeDisposition {Native, Fallback, HardDecline}`, which reads the three is-native signals in one place: `Route` (slot/projection representability), `IsGroupByFallbackUnsafe` (the GroupBy+Join wrong-data hard-decline), and vector search (`ContainsVectorSearch(CapturedExpression)` — the one signal not on `MongoSelectDefinition`, since the `VectorSearch(...)` call is lifted out by the preprocessor and never reaches slot population). `Route` stays "which native shape / slot representability"; the disposition is the superset. Cross-collection `$lookup` streamability (`AllPendingLookupsAreStreamable`) is **not** an is-native signal — it is the separate streaming-vs-DOM axis (it only picks the streaming shaper for a query that is already native), so it is deliberately outside the disposition.
- **Native translation (`NativeTranslation/` + `Expressions/`):**
  - `Expressions/MongoExpression` + subtypes (`MongoFieldExpression`/`MongoConstantExpression`/`MongoParameterExpression`/`MongoBinaryExpression`/`MongoUnaryExpression`) + `MongoOrdering` — the dialect-agnostic `SqlExpression`-analog node hierarchy.
  - `Expressions/MongoQueryExpression` (+ `.Lookup.cs`) — the structured query tree: it **has-a** `MongoSelectDefinition` (reached via `MongoQueryExpression.Select`) holding the native scalar IR, **plus** the cross-collection `$lookup`/inner-collection state (`Lookups`/`IsJoinQuery`/`InnerCollections`, on `.Lookup.cs`) and the retained `CapturedExpression` + `ProjectionMapping` for the fallback.
  - `Expressions/MongoSelectDefinition` — the native-translation logical query IR (`Predicate`/`Orderings`/`Offset`/`Limit`/**`Projection`**), extracted (EF-330) from `MongoQueryExpression` into a composed, dialect-neutral data-holder. `NativeSlotPopulator`/`NativeProjectionBinder` populate it via `mongoQ.Select`; the gate and lowerer read it. The `$lookup` state stays on `MongoQueryExpression` (entangled with the fallback shaper, slated for EF-317), so it was **not** moved here. **`Projection` (EF-331)** holds the dialect-neutral `MongoProjection` (alias → `MongoExpression` field-ref pairs) for a terminal anonymous-type/DTO member-access `Select`; it is populated by `NativeProjectionBinder.TryPopulateNativeProjection` (not by `NativeSlotPopulator.PopulateNativeSlots` — see the catch-all pitfall below) and stays empty for every other projection shape (bare scalar, computed, mixed, non-terminal), which still fall back to driver-LINQ. The single authoritative is-native decision is the computed property `Route` (enum `NativeRoute`: `Fallback`/`WholeEntity`/`Projection`/`ScalarAggregate`/`GroupBy`) — `Fallback` when an internal `_hasUnsupportedOperator` flag was set via `MarkNotNativelyRepresentable()`; otherwise `ScalarAggregate` (EF-SP4) when a scalar-aggregate `Cardinality` is set, `GroupBy` (EF-SP6) when a `Grouping` is set, `Projection` when `Projection` is non-empty (representable **and** has a pushed-down projection); otherwise `WholeEntity`. `Route` is the authoritative signal for **slot/projection** representability; the full is-native decision is the gate's `ClassifyNativeDisposition` (EF-334), which layers two further is-native signals onto `Route`: vector search (via `ContainsVectorSearch` over `CapturedExpression` — not on `MongoSelectDefinition`, as the `VectorSearch(...)` call is lifted out before slot population) and the GroupBy+Join hard-decline (`IsGroupByFallbackUnsafe`). `$lookup` streamability (`AllPendingLookupsAreStreamable`) is a **separate** axis (streaming-vs-DOM), not an is-native signal.
  - `NativeTranslation/MongoExpressionTranslator` — EF predicate / key-selector body → `MongoExpression` (`TryTranslate` / `TryTranslateField`); returns false for anything outside its acceptance set. As of EF-329 (predicate breadth) that set includes nullable equality/`== null` (IS NULL), `Enumerable.Contains`/`ICollection.Contains` → `MongoInExpression` (`$in`/`$nin`), `string.StartsWith`/`EndsWith`/`Contains` → `MongoRegexExpression` (`$regularExpression`), and field-to-field/arithmetic `MongoBinaryExpression`s (still parity-limited otherwise; the computed long tail — string transforms, date parts, `Math.*`, type-changing casts — remains unsupported and falls back).
  - `NativeTranslation/MongoSelectLowerer` — slots → `MongoPipelineStage[]` (typed IR under `NativeTranslation/Stages/`), BSON-free; owns canonical order + the lookup eligibility guards. When `MongoSelectDefinition.Projection` is populated, the lowerer appends a `NativeTranslation/Stages/MongoProjectStage` **last** in the pipeline (after `$match`/`$sort`/`$skip`/`$limit`), carrying the `MongoProjection` alias/field-ref pairs; `MongoPipelineFactory.Create`'s stage-walk renders it to a `$project` BSON body (explicit `_id: 0` plus one entry per alias) in the aggregation-expression field-ref dialect.
  - **`NativeTranslation/MongoQueryLanguageRenderer` + `NativeTranslation/MongoAggregationExpressionRenderer` — the dual-dialect renderer (EF-329 predicate breadth).** `MongoQueryLanguageRenderer` renders `MongoExpression` → `$match`-dialect BSON (`{field:{$gt:v}}`, `$and`/`$or`, bare-bool, `$ne`, `$in`/`$nin`, `$regularExpression`) — the query/filter dialect, and is usable directly as a `$match` stage body. `MongoAggregationExpressionRenderer` renders a `MongoExpression` subtree to the **aggregation-expression** dialect that lives inside `{ $expr: … }` (`$eq`/`$ne`/`$lt`/…, `$add`/`$subtract`/`$multiply`/`$divide`/`$mod`, field refs as `"$elementName"`) — the only dialect that can express field-to-field comparisons and arithmetic, which have no query-dialect form. `PlaceholderTable` (shared by both) records parameter placeholders. Both renderers share one value-rendering path, `NativeTranslation/MongoValueRenderer`, for `MongoConstantExpression`/`MongoParameterExpression` leaves, so a constant and a parameter of the same value always emit identical BSON regardless of which dialect is in play; `MongoAggregationExpressionRenderer` is a `static` class (no instance state, unlike `MongoQueryLanguageRenderer`).
    - **Per-subtree boundary is index-first, and the renderer — not the lowerer — owns it.** `MongoQueryLanguageRenderer.RenderNode` keeps `&&`/`||` (`AndAlso`/`OrElse`) at the query level always: each branch of an AND/OR is rendered (and combined via `CombineAnd`/`CombineOr`) independently, so a mixed predicate like `a.Age > 21 && a.X == a.Y` keeps the indexable `Age` clause as a plain `$match` term and wraps only the non-query-expressible `X == Y` subtree in `$expr` (`RenderAsExpr` delegates that one subtree to `MongoAggregationExpressionRenderer`). This maximizes index usage: `$expr` clauses can't use indexes as effectively as native `$match` operators, so it is scoped to the *smallest* subtree that actually needs it, not promoted to the whole predicate. A comparison is query-native (handled by `MongoQueryLanguageRenderer` directly) only when the left side is a bare field and the right side is a constant/parameter (`IsQueryNativeComparison`); anything else (field-to-field, arithmetic operands) falls through to `RenderAsExpr`.
    - **This is an intentional refinement over the original design doc.** `docs/superpowers/specs/2026-06-23-native-query-provider-design.md` (§"Lowering, rendering & the dialect boundary") states dialect choice is made in the lowerer, never in the QMTEV or the node types. With per-clause dialect *mixing* now required (a single predicate can straddle both dialects), that responsibility moved to the **renderer**, which walks the already-lowered, dialect-neutral `MongoExpression` tree and decides per-subtree which dialect applies. `MongoSelectLowerer` and the `MongoExpression` node types remain completely dialect-neutral, as originally designed — only the *renderer* is dialect-aware, and only it needed to move to support mixing.
  - `NativeTranslation/MongoPipelineFactory` — the B2 template: `Create(stages, renderer)` walks the stages into a `BsonDocument[]` template (+ placeholder table); `Build(parameterValues)` deep-clones and substitutes per execution. Validates `$limit>0`/`$skip≥0` (throws `ArgumentOutOfRangeException`, matching EF).
  - `NativeTranslation/MongoStreamingEntityMaterializerRewriter` + `BsonRowReader` + `StreamingEligibility` — forward-only `RawBsonDocument` → POCO materialization for eligible entities (no DOM build).
  - `Infrastructure/MongoQueryMode` (`Native`/`DriverLinq`/`NativeOnly`) — the user-facing gate option (`UseQueryMode`).
  - `NativeTranslation/NativeCardinalityBinder` (EF-SP4) — populates `MongoSelectDefinition.Cardinality` for entity reducers (`TryBindReducer`: synthesizes the reducer `$limit`) and scalar aggregates (`TryBindAggregate`: synthesizes the aggregate, and for `All`/predicate-bearing `Count`/`Any` injects the (negated) predicate as a `$match` conjunct via `AddPredicateConjunct`). Owns the guard that forces fallback when a predicate-injecting aggregate follows a `Take`/`Skip` already applied to the same select (`select.Offset != null || select.Limit != null`) — see the scalar-cardinality as-built note above.
  - `Expressions/MongoCardinality` (on `MongoSelectDefinition.Cardinality`) — the dialect-neutral IR for "this select terminates in a reducer or aggregate rather than a row sequence": `Reducer`/`Aggregate` kind, `Selector` field-ref, `EmptyBehavior`/`EmptyValue`, `ResultType`.
  - `NativeTranslation/Stages/MongoCountStage` / `MongoGroupAccumulatorStage` — typed IR stages the lowerer appends for `Count`/`LongCount`/`Any` (`$count`) and `Sum`/`Min`/`Max`/`Average` (`$group` with the matching accumulator) respectively, mirroring how `MongoProjectStage` is appended for projections.
  - `NativeTranslation/NativeGroupByBinder` (EF-SP6) — populates `MongoSelectDefinition.Grouping` for `GroupBy(key).Select(aggregate)`, mirroring `NativeCardinalityBinder`'s role for scalar aggregates. `TryBindGroupKey` parses the key (scalar `MemberExpression` / composite anonymous `NewExpression`) into `PendingGroupKey`; `TryBindGroupProjection` + `TryBindAccumulator` parse the aggregate `Select`, finalize the `MongoGrouping`, and emit the flattening projections. Holds the two correctness guards — `HasDefaultKeySerialization` (reject value-converter / non-default-`BsonRepresentation` keys) and `IsGroupingSource` (accumulator source must be the grouping parameter `g`).
  - `Expressions/MongoGrouping` (on `MongoSelectDefinition.Grouping`) — dialect-neutral `$group` IR: `Key` parts (`MongoGroupingKeyPart`; null `Name` ⇒ scalar `_id`, named parts ⇒ composite `_id` sub-doc) + `Accumulators` (`MongoGroupAccumulator`: output field, operator `$sum`/`$avg`/`$min`/`$max`, null operand ⇒ `$sum:1`). Lowered by the `MongoSelectLowerer` group branch to `NativeTranslation/Stages/MongoGroupStage`, rendered by `MongoPipelineFactory.RenderKeyedGroup` (composite → `_id` sub-document, else bare field-ref) in the aggregation-expression dialect.
  - `Expressions/MongoElementRefExpression` (EF-SP6) — a raw document-element reference by (possibly dotted) path with **no** backing `IProperty`, rendering as `"$" + Path` in the aggregation-expression dialect. The GroupBy flattening `$project` uses it to read each group output — `_id` (scalar key), `_id.<Name>` (composite sub-key), or an accumulator output field — up into a top-level result alias for the DOM shaper.
  - `EnumerableMethods` (provider root, `src/MongoDB.EntityFrameworkCore/EnumerableMethods.cs`) — the provider's own port of EF Core's `internal` `EnumerableMethods`; **extended for EF-SP6** with the `Count`/`LongCount`/`Sum`/`Average`/`Min`/`Max` selector members (`IsSumWithSelector` etc.) that `NativeGroupByBinder.TryBindAccumulator` matches grouped aggregates against (both the `Enumerable` and the EF-lowered `Queryable`-over-`AsQueryable()` forms).
  - `Visitors/MongoShapedQueryCompilingExpressionVisitor.ExecuteAggregate` / `TryBuildAggregateFactory` — compile-time construction of the scalar-result execution path: builds the pipeline factory, applies `MongoCardinality.EmptyBehavior`/`EmptyValue` around the single-row-or-absent aggregate result, and deserializes via `DeserializeScalar<TResult>` (non-int scalar coverage, e.g. `decimal`/nullable numerics).
  - `SingleValueEnumerable` — the `IEnumerable<T>` wrapper the native reducer/aggregate path returns so EF Core's own base cardinality reduction (First/Single throw/empty semantics) runs unmodified over a zero-or-one-element sequence.
- `Visitors/MongoEFToLinqTranslatingExpressionVisitor` — converts the residual EF expression into a tree the driver's LINQ v3 provider understands (`Mql.Field`, parameter resolution, `As<T>(serializer)`).
- `Visitors/MongoProjectionBindingRemovingExpressionVisitor` — replaces `ProjectionBindingExpression` nodes with concrete index-based reads from a `BsonDocument`.
- `Visitors/MongoMixedProjectionBindingRemovingExpressionVisitor` — sibling of the above used on the mixed path (projection contains entity references LINQ v3 can't handle); `MongoShapedQueryCompilingExpressionVisitor` strips the trailing `Select` and dispatches to this visitor so the shaper runs client-side over full `BsonDocument`s.
- `Expressions/MongoCollectionExpression`, `EntityProjectionExpression`, `RootReferenceExpression`, `ObjectAccessExpression`, `ObjectArrayProjectionExpression` — provider-specific expression nodes for collection roots, nested-document access, and entity shape.
- `MongoExecutableQuery` + `QueryingEnumerable` — the compiled-query handoff. `QueryingEnumerable` calls `MongoClientWrapper.Execute(MongoExecutableQuery)` and applies the shaper. For the native path `MongoExecutableQuery` carries `NativePipeline` (the built `BsonDocument[]`), `Streaming`, and `Session` (internal); for the fallback it carries the driver-LINQ `Query` expression.
- `Factories/*` — EF Core DI factories registered in `MongoServiceCollectionExtensions.AddEntityFrameworkMongoDB()`.

## Boundaries with adjacent areas

- **vs Storage.** Query stops at the executable query — it produces *data*: either a native `BsonDocument[]` pipeline (`MongoExecutableQuery.NativePipeline`) or a driver-LINQ expression. `MongoClientWrapper.Execute(...)` (Storage) owns execution: it runs `collection.Aggregate(nativePipeline)` for the native path and hands the expression to `IMongoQueryProvider` for the fallback. Cursor lifecycle, transaction/session binding, retries are Storage + driver. Never call `IMongoCollection<>.Aggregate(...)` directly from Query — build the `BsonDocument[]` and let the wrapper run it.
- **vs Storage — bulk `ExecuteUpdate`/`ExecuteDelete` (EF9+) uses a *second*, deliberately different seam.** Reads cross to Storage as **data** (a `MongoExecutableQuery`); bulk crosses as **behavior** — `MongoShapedQueryCompilingExpressionVisitor.CreateBulkPlan<TSource>` builds a `MongoBulkPlan` (Storage) carrying `Func<QueryContext, …>` translation delegates, and `MongoBulkOperationExecutor` (Storage) invokes them at runtime. This is intentional: bulk filter/update translation is parameter-value-dependent, so it must be deferred and re-run per execution. The translation helpers (`BuildFilter`/`BuildUpdate`/`BuildIdDocumentQuery`) stay here in Query; only their rendered results cross the boundary. Don't "fix" the bulk seam to look like the read seam — they differ for this reason.
- **vs Serializers.** Query needs an `IBsonSerializer` for every materialized projection result — it asks `BsonSerializerFactory` (Serializers area). Query should never instantiate serializers directly.
- **vs Metadata.** `IEntityType`, `IProperty`, navigation info come from Metadata. Query reads `GetElementName()`, `GetBsonRepresentation()`, `GetDiscriminator*()` etc. — it doesn't write them.
- **vs the driver's LINQ v3 provider.** Only the **fallback** path uses it: Query produces a driver-LINQ expression (types from `MongoDB.Driver.Linq`) and hands it off, and the driver builds that pipeline. The **native** path bypasses the driver's LINQ provider entirely — the provider builds the `BsonDocument[]` itself (`MongoSelectLowerer` + `MongoQueryLanguageRenderer` + `MongoPipelineFactory`) and only uses the driver as a BSON/cursor/protocol library via `Aggregate`. The deliberate, stable boundary is **our query tree → `BsonDocument[]` → `Aggregate`**; we do **not** build on the driver's internal AST.

## Common pitfalls

- **Allowed method sources are strict.** Only `Queryable`, `MongoQueryableExtensions`, and `MongoDB.Driver.Linq.MongoQueryable` methods are accepted. Anything else throws `NotTranslatedExpression` early.
- **VectorSearch extraction.** `VectorSearch(...)` must be pulled out of the tree before EF's nav-expansion runs (it crashes nav-expansion otherwise) and stitched back in after. If you change preprocessor ordering, re-check this dance.
- **ProjectionMapping discipline.** The `_projectionMapping` keys (`ProjectionMember`s) must match exactly what the shaper expects. A mismatch between the post-processor mapping and the shaper compilation produces silent wrong-results, not crashes.
- **`MongoQueryExpression.CapturedExpression`** must be a *complete* method chain — set once at the tail of `MongoQueryableMethodTranslatingExpressionVisitor.VisitMethodCall`. Setting it mid-chain truncates the query.
- **Reference-equality on `MethodInfo`.** Translators that match by `MethodInfo` must use canonical constants — `QueryableMethods` for the top-level dispatch in `MongoQueryableMethodTranslatingExpressionVisitor`, `EnumerableMethods` inside the projection-binding visitors, and the driver's `*Method` reflection classes where the bridge to driver-LINQ needs them; open vs. constructed generic methods compare unequal.
- **Unsupported shapes are detected, not silently translated.** Two layers: the base visitor early-fails truly untranslatable shapes; and for the *native* path, anything `NativeSlotPopulator` does not lower into a slot calls `mongoQ.Select.MarkNotNativelyRepresentable()` (sets the internal `_hasUnsupportedOperator` flag, which drives `Route` to `NativeRoute.Fallback`) so the gate falls back (or throws under `NativeOnly`) rather than emitting a pipeline that silently drops the operator.
- **The native catch-all whitelist must stay in sync.** `NativeSlotPopulator.PopulateNativeSlots` lowers seven slot operators (`Where`/`OrderBy`/`OrderByDescending`/`ThenBy`/`ThenByDescending`/`Skip`/`Take`) into `MongoSelectDefinition`'s `Predicate`/`Orderings`/`Offset`/`Limit` slots. The `else` catch-all in `PopulateNativeSlots` marks **everything else** non-native by default (correctness-safe: worst case is a missed optimization + fallback, never a wrong result), *unless* `IsNativeRepresentableSlotOperator` returns `true` for the operator. That predicate lists the seven slot operators **plus** the `Translate*`-override operators (`Select`, `OfType`, `Distinct`, `Union`, `Concat`) **plus** the scalar-cardinality / `GroupBy` operators added by later sub-projects (`Count`/`LongCount`/`Sum`/`Min`/`Max`/`Average`/`Any`/`All`, the `First`/`Single` family, and `GroupBy*` — EF-336/EF-344/EF-347). Membership is exactly what suppresses the catch-all — for the seven slot operators it means "already populated into a slot," and for the `Translate*`-override operators it means "decided by its own `Translate*` override, don't clobber it." `Union`/`Concat` (EF-347 slice 2) follow the same pattern as `Select`/`OfType`/`Distinct`: `TryTranslateSetOperation` (backing both) always decides representability itself (attaching a `SetOperation` or calling `MarkNotNativelyRepresentable()`), so both are whitelisted here purely to stop the catch-all from re-deciding — see the set-ops as-built note above for the full mechanism. The QMTEV's `TranslateSelect` override calls `NativeProjectionBinder.TryPopulateNativeProjection`, which populates `MongoSelectDefinition.Projection` for a representable shape (terminal member-access anonymous/DTO projection) — leaving `Route` to resolve to `NativeRoute.Projection` — and otherwise calls `MarkNotNativelyRepresentable()`; `TranslateOfType` (EF-347) builds a discriminator `$eq`/`$in` conjunct via `TryBuildDiscriminatorPredicate` and adds it to `Predicate` via `AddPredicateConjunct` for a representable TPH narrowing (the native DOM shaper already materializes derived types polymorphically via EF's own `MaterializationCondition`, so the conjunct is the only piece native was missing), falling back to `MarkNotNativelyRepresentable()` only when the target type has no discriminator property (non-TPH); `TranslateDistinct` (EF-347 Task 2) follows the same pattern — it calls `NativeGroupByBinder.TryBindDistinctFromProjection` to convert an already-populated `Projection` into a degenerate `Grouping` (key-only, zero accumulators), falling back to `MarkNotNativelyRepresentable()` when there is no native `Projection` to convert (bare-scalar or whole-entity `Distinct`) or a projected key fails `HasDefaultKeySerialization`. **Adding a new native operator means:** for a slot-style operator, update BOTH `NativeSlotPopulator.PopulateNativeSlots` (populate the slot) *and* `IsNativeRepresentableSlotOperator` (add it to the whitelist); for a `Translate*`-override-style operator (like `Select`/`OfType`), add its override *and* add it to `IsNativeRepresentableSlotOperator` so the catch-all doesn't override its decision. Miss either path and the operator is silently dropped on the native pipeline or double-decided.
- **The QMTEV `Translate{Where,OrderBy,ThenBy,Skip,Take}` overrides are inert (`=> null`).** Native slot population is delegated to `NativeSlotPopulator.PopulateNativeSlots` at the `VisitMethodCall` fall-through, because routing these through `base.VisitMethodCall` rebuilds a fresh `MongoQueryExpression` per operator (slots don't accumulate). **Do not add these operators to the `VisitMethodCall` switch** without first removing their `NativeSlotPopulator.PopulateNativeSlots` handling — otherwise slots double-populate.
- **The lowerer is BSON-free; the renderer/factory own BSON.** `MongoSelectLowerer` produces only typed `MongoPipelineStage`s; all `BsonDocument` construction lives in `MongoQueryLanguageRenderer` (the `$match` body) and `MongoPipelineFactory.Create` (the stage-walk: `{$match}`/`$sort`/`$skip`/`$limit`/`$lookup`/`$unwind`).
- **Composite-PK key access is NOT native** (strict spike parity) — `MongoExpressionTranslator` rejects multi-property-PK member access, so such predicates/sort fall back. `LookupExpression.GetFieldPath` (`_id.<prop>`) exists for the (still-deferred) composite-PK Include `$lookup` only.
- **Non-positive paging matches EF's contract.** `MongoPipelineFactory.Build` validates `$limit > 0` / `$skip ≥ 0` and throws `ArgumentOutOfRangeException` (client-side, like the driver) — do not emit `{$limit: 0}` (MongoDB rejects it server-side). Property-less primitive values (Skip/Take counts have `forSerialization == null`) serialize via `BsonValue.Create`, not a property serializer.
- **MQL shape cannot prove a query went native.** For filter/sort/paging the native and driver-LINQ pipelines are structurally identical (`$match`/`$sort`/`$skip`/`$limit`), so asserting those substrings under `Native` mode passes even on fallback. The **only reliable "goes native" signal is `NativeOnly` mode**: native-capable ⇒ succeeds; otherwise ⇒ throws `NativeTranslationNotSupportedException`. (Several early gate tests were false positives masked by structurally-identical fallback MQL.)
- **EF Core query cache.** Compiled queries are cached by EF Core by expression-tree shape; if you change a translator's output for a previously-translatable tree, you've quietly invalidated user caches.
- **Multi-EF guards.** Some visitor signatures changed between EF8/EF9/EF10. For representative guard shapes elsewhere in the tree see `Storage/MongoTypeMappingSource.cs` (`#if EF8 || EF9`), the `ChangeTracking/StringDictionaryComparer*.cs` pair (legacy vs. EF10 split), and the `ChangeTracking/ListOf*Comparer.cs` files (`#if EF8`); in Query itself, `QueryingEnumerable.cs` has a `#if !EF8` block.

## How to test

Most query tests assert the **rendered MQL pipeline** rather than executing against a server. The functional and specification tests both have helpers (`AssertMql(...)`) that capture the MQL via `TestMqlLoggerFactory`. Unit tests use **plain xUnit `Assert.*`** (FluentAssertions is not referenced anywhere in the test projects).

**Proving the native path.** `AssertMql` shape does **not** distinguish native from driver-LINQ for filter/sort/paging (identical pipelines) — to assert a query genuinely goes native, run it under `MongoQueryMode.NativeOnly` and assert it **succeeds** (a fallback shape would throw `NativeTranslationNotSupportedException`); to assert a shape falls back, assert it **throws** under `NativeOnly` (or, for `Include`, assert the driver `_outer`/`_inner` shape under `Native`). The spec suite has a **test-only** coverage instrument: `MONGODB_EF_NATIVE_ONLY=1` flips all spec contexts to `NativeOnly` (via `MongoTestStore.AddProviderOptions`), so the pass/fail set is the "what runs native" report. Native unit tests live under `tests/MongoDB.EntityFrameworkCore.UnitTests/Query/NativeTranslation/`; the `QueryModeGate*` functional tests exercise the gate end-to-end.

```bash
dotnet test MongoDB.EFCoreProvider.sln -c "Debug EF10" --no-build \
  --filter "FullyQualifiedName~Query"
```

- Unit tests: `tests/MongoDB.EntityFrameworkCore.UnitTests/Query/`
- Functional tests (real DB): `tests/MongoDB.EntityFrameworkCore.FunctionalTests/Query/` — golden-path translations and end-to-end materialization.
- Specification tests (EF Core conformance, Northwind suite): `tests/MongoDB.EntityFrameworkCore.SpecificationTests/Query/` — pattern is to override the upstream test and assert the produced MQL.
